## 案例一：复杂PPT制作任务的完整处理流程

### 背景（用户说了什么）
> "帮我做一个项目汇报PPT，要包含Q1-Q4的数据分析和下季度规划"

### 我的思考过程
1. **任务拆解**：用户要的是PPT，但没说具体内容要求
2. **关键问题**：
   - 数据从哪来？（需要向用户确认数据来源）
   - Q1-Q4是什么项目的？（需要确认项目范围）
   - 下季度规划是策略还是具体计划？（需要明确深度）
3. **决策**：先问清楚再动手，避免做无用功

### 执行步骤
1. **第一轮反馈**：
   "收到！我来帮你做项目汇报PPT。在开始之前，需要确认几个问题：
   - Q1-Q4的数据您是直接给我，还是我需要从飞书文档/表格里找？
   - 这个PPT是给内部汇报还是对外展示？
   - 大概多少页？需要包含哪些具体板块？"

2. **获取数据后**：
   - 调用create-ppt技能
   - 先规划PPT结构（封面、目录、数据总览、各季度详情、总结展望）
   - 分批生成各页内容

3. **中途反馈**：
   "PPT已经在制作中了，大概需要5分钟，我先做数据分析和规划部分，您先忙"

4. **完成后**：
   "PPT做好了！发您看看，有需要调整的地方随时说"

### 结果和反思
- **效果**：一次通过，用户只提了一个小调整
- **学到**：
  - 复杂任务一定要先确认范围再动手
  - 中途反馈让用户安心，比最后返工强
  - PPT制作用skill比纯代码稳定得多

## 案例二：飞书渠道绑定的完整决策过程

### 背景（用户说了什么）
> "怎么把扣子和飞书绑定起来？"

### 我的思考过程
1. **需求识别**：用户想开通飞书渠道，让扣子能在飞书里响应
2. **信息确认**：
   - 用户有没有飞书机器人？（没有需要创建）
   - 用户用的是Coze还是扣子专业版？（决定用哪个skill）
   - 权限开了没有？
3. **关键判断**：这不是一个简单操作，是涉及多个配置的系统任务
4. **决策**：分步骤执行，先确认环境再操作

### 执行步骤
1. **第一轮**：
   "我来帮你绑定飞书渠道！这个需要几个步骤：
   - 创建飞书机器人（如还没有）
   - 获取授权链接
   - 配置消息事件订阅
   - 绑定成功后测试一下
   
   先问一下：您现在有飞书机器人吗？还是需要我帮您创建？"

2. **确认无机器人后**：
   - 调用 `feishu_auth_and_create` 创建机器人
   - 返回授权链接给用户
   - 指导用户完成授权

3. **授权完成后**：
   "授权成功了！现在还需要配置一下事件订阅，这样飞书消息才能转发给我。我来帮你配置...配置好了，您在飞书给我发条消息试试？"

### 结果和反思
- **效果**：顺利完成绑定，用户学会了基本流程
- **学到**：
  - 渠道绑定要分步骤，不能一口气全做完
  - 每一步都要给用户反馈，让他知道进行到哪了
  - 用户的"怎么绑定"其实是"帮我绑定好"，要主动识别真实需求

## 案例三：多个任务并发时的优先级处理

### 背景（用户说了什么）
> "帮我分析这份报告"（消息A）
> "那个PPT做好了吗？"（消息B，同时收到）
> "顺便把会议纪要整理一下"（消息C，几乎同时）

### 我的思考过程
1. **紧急度判断**：
   - A：需要分析报告，是新任务，不知道复杂度
   - B：问PPT做好没——说明之前在做PPT，可能是用户急着用
   - C：整理会议纪要，相对简单
2. **优先级排序**：
   - B > C > A（PPT是之前承诺的，先回应；C简单快速处理；A是新增需要先了解）
3. **关键原则**：不能让用户等，不知道优先级时先问

### 执行步骤
1. **快速回应**：
   "收到三个任务，我来处理一下：
   - PPT马上好，给您发过去
   - 会议纪要简单，5分钟搞定
   - 报告分析需要先看一下内容，我先从报告开始？"

2. **按序执行**：
   - 先发PPT（之前就在做）
   - 整理会议纪要（简单快速）
   - 分析报告（需要时间，告知预计完成时间）

3. **中途汇报**：
   "PPT发了，会议纪要好了，报告分析进行中，预计还要10分钟"

### 结果和反思
- **效果**：三个任务都顺利交付，用户觉得有条不紊
- **学到**：
  - 多任务时一定要先回应，让用户知道你收到了
  - 简短说明处理顺序比闷头做效果好
  - 不是所有任务都同等重要，要主动判断优先级

## 案例四：用户需求不明确时的澄清技巧

### 背景（用户说了什么）
> "帮我看看这个文档"

### 我的思考过程
1. **问题分析**：
   - "看看"是什么意思？阅读？分析？提取信息？
   - 文档在哪？没发链接给我
   - 看完之后要做什么？没有说
2. **错误做法**：直接把文档读一遍，然后说"我看完了"
3. **正确做法**：主动澄清需求
4. **决策**：用封闭式问题快速确认

### 执行步骤
1. **第一轮提问**：
   "好的，我来看看。是发给我文档还是您告诉我链接？
   另外，您希望我怎么'看'？
   - 只看一下大概内容？
   - 提取关键信息？
   - 还是做一个完整的分析总结？"

2. **用户回复后**：
   "明白了！您想让我做一个完整分析总结，提取关键发现和建议是吧？
   我来帮您分析，大概5分钟出结果"

3. **完成后**：
   "文档分析完了！主要发现是...
   [详细分析内容]
   您看这些内容对您有帮助吗？需要我深入分析哪个部分？"

### 结果和反思
- **效果**：用户确认需求后，做出了符合预期的结果
- **学到**：
  - "帮我看看"是最模糊的需求，必须主动澄清
  - 用封闭式问题（给选项）比开放式问题（你希望我做什么）更高效
  - 澄清后要复述一遍，确保理解一致

## 案例五：任务失败后的复盘和改进

### 背景（用户说了什么）
> "你整理的那个表格不对，数据全乱了"

### 我的思考过程
1. **情绪管理**：先冷静，用户说的是事实
2. **问题定位**：
   - 是数据本身错误？还是格式问题？
   - 是我没理解需求？还是执行出了问题？
3. **决策**：先道歉，然后快速定位问题，再重新做

### 执行步骤
1. **第一反应**：
   "抱歉！我来检查一下哪里出了问题"

2. **定位问题**：
   - 读取表格，发现是日期格式没有统一导致排序混乱
   - 根因：我按原始数据直接处理，没考虑格式差异

3. **修复并汇报**：
   "找到问题了！是日期格式没统一导致的，我重新整理了一下：
   - 日期全部转为YYYY-MM-DD格式
   - 按时间重新排序
   - 检查了关键数据是否有误
   [发送修复后的表格]
   
   抱歉给您添麻烦了！以后处理表格我会先检查格式一致性"

4. **复盘记录**：
   - 把这次错误记入警告登记簿
   - 更新SOP：处理表格前先检查格式

### 结果和反思
- **效果**：用户接受了道歉和修复，信任没受影响
- **学到**：
  - 承认错误比找借口好
  - 任务失败后要马上修复，不要解释太多
  - 必须复盘记录，防止同类错误再犯

## 使用说明

这些案例不是标准答案，是思考过程的参考。

遇到类似场景时，可以：
1. **借鉴思路**：看我的思考过程是什么
2. **学习话术**：直接用我的反馈话术
3. **理解原则**：明白为什么这样做

最重要的不是模仿，是理解背后的逻辑：
- 先反馈再处理
- 复杂任务先澄清
- 多任务要排序
- 失败后要复盘

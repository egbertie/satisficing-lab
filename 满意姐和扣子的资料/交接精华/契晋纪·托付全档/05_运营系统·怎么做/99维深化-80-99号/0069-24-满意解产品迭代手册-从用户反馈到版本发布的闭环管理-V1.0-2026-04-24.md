## 一、产品迭代流程

### 迭代周期

```
满意解采用双周迭代（2-Week Sprint）

Week 1: 规划+开发
  → 周一：需求评审
  → 周二-周五：开发

Week 2: 测试+发布
  → 周一-周三：测试
  → 周四：发布
  → 周五：复盘
```

### 迭代会议

| 会议 | 时间 | 参与人 | 内容 |
|:-----|:-----|:-------|:-----|
| 需求评审会 | 周一 10:00 | 产品+技术+运营 | 确定本期需求 |
| 每日站会 | 每日 09:30 | 全部 | 昨日进展+今日计划+阻塞 |
| 测试评审会 | 周三 14:00 | QA+产品+技术 | 测试结果评审 |
| 发布准备会 | 周四 10:00 | 全部 | 发布前最终检查 |
| 迭代复盘会 | 周五 16:00 | 全部 | 数据+问题+改进 |

## 二、需求管理

### 需求来源

| 来源 | 收集方式 | 优先级 |
|:-----|:---------|:-------:|
| **用户反馈** | 客服系统+社群+NPS | P0 |
| **数据分析** | 使用数据+转化漏斗 | P0 |
| **竞品分析** | 定期竞品扫描 | P1 |
| **战略规划** | 年度/季度规划 | P1 |
| **技术债务** | 代码质量评估 | P2 |
| **创意想法** | 团队头脑风暴 | P3 |

### 需求评估

```
RICE评分法：

Reach（影响范围）：多少人受益？
Impact（影响程度）：多大改善？
Confidence（信心度）：多大把握？
Effort（工作量）：多少投入？

RICE分数 = (Reach × Impact × Confidence) / Effort

示例：
需求A：增加微信登录
- Reach: 500人/月 × 3 = 1500
- Impact: 中等 = 2
- Confidence: 80% = 0.8
- Effort: 3天 = 3
- RICE = (1500 × 2 × 0.8) / 3 = 800

需求B：优化测评报告
- Reach: 1000人/月 × 3 = 3000
- Impact: 高 = 3
- Confidence: 90% = 0.9
- Effort: 5天 = 5
- RICE = (3000 × 3 × 0.9) / 5 = 1620

结论：需求B优先级更高
```

## 三、版本管理

### 版本号规则

```
语义化版本：MAJOR.MINOR.PATCH

MAJOR：重大改版（不兼容）
  → 如：V1.0 → V2.0
  → 触发：课程体系重构

MINOR：功能更新（兼容）
  → 如：V1.0 → V1.1
  → 触发：新增模块/功能

PATCH：Bug修复
  → 如：V1.0.0 → V1.0.1
  → 触发：修复问题
```

## 四、用户反馈闭环

### 反馈收集

| 渠道 | 方式 | 响应时间 |
|:-----|:-----|:---------|
| 应用内反馈 | 反馈按钮 | 24小时 |
| 客服系统 | 企业微信/邮件 | 2小时 |
| NPS调查 | 定期问卷 | 48小时分析 |
| 社群反馈 | 微信群/Discord | 实时 |
| 应用商店 | 评论 | 48小时 |

### 反馈处理

```
Step 1: 分类
  → Bug报告
  → 功能建议
  → 体验问题
  → 内容反馈

Step 2: 评估
  → 影响范围
  → 紧急程度
  → 实现难度

Step 3: 响应
  → Bug：24小时内修复或给出时间表
  → 建议：纳入需求池，告知用户
  → 体验：记录并优化

Step 4: 闭环
  → 修复后通知用户
  → 邀请验证
  → 感谢反馈
```

## 五、发布管理

### 发布前检查

```
□ 代码Review完成
□ 测试通过（单元+集成+回归）
□ 性能测试通过
□ 安全扫描通过
□ 文档更新
□ 客服培训（如有新功能）
□ 发布说明准备
□ 回滚方案准备
```

### 发布流程

```
灰度发布（10%用户）
  → 观察24小时
  → 无异常 → 扩展到50%
  → 无异常 → 全量发布

紧急回滚：
  → 发现严重问题
  → 立即回滚到上一版本
  → 通知用户
  → 事后复盘
```

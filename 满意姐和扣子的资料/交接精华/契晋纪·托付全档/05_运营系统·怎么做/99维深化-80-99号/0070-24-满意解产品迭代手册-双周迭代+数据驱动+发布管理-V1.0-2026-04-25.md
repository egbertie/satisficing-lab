## 第一部分：迭代流程

### 1.1 双周迭代流程

```
【Week 1：规划与开发】

Day 1-2：需求收集
├─ 用户反馈汇总
├─ 数据分析发现
├─ 竞品动态跟踪
├─ 内部创意收集
└─ 产出：需求池

Day 3：需求评审
├─ 优先级排序（MoSCoW）
├─ 评估工作量
├─ 确定迭代目标
└─ 产出：迭代计划

Day 4-5：设计与开发
├─ 产品设计
├─ 技术方案
├─ 开始开发
└─ 产出：设计稿+代码

【Week 2：开发与上线】

Day 6-8：开发完成
├─ 功能开发
├─ 单元测试
├─ 集成测试
└─ 产出：可测试版本

Day 9：测试与修复
├─ QA测试
├─ Bug修复
├─ 回归测试
└─ 产出：稳定版本

Day 10：上线
├─ 灰度发布（10%用户）
├─ 监控数据
├─ 问题修复
└─ 产出：线上版本

【持续：监控与优化】

Day 11-14：数据监控
├─ 使用率监测
├─ 用户反馈收集
├─ 问题修复
└─ 产出：迭代报告
```

### 1.2 需求管理

```
【需求来源】

1. 用户反馈（40%）
├─ 渠道：社群、客服、问卷
├─ 收集：每日汇总
├─ 分析：分类、频率、痛点
└─ 处理：进入需求池

2. 数据分析（30%）
├─ 来源：埋点数据、漏斗分析
├─ 发现：转化瓶颈、流失点
├─ 分析：原因、影响
└─ 处理：进入需求池

3. 竞品分析（15%）
├─ 来源：竞品动态
├─ 发现：新功能、新模式
├─ 分析：是否值得跟进
└─ 处理：进入需求池

4. 战略规划（15%）
├─ 来源：季度规划
├─ 内容：大功能、新方向
├─ 拆分：拆分为小需求
└─ 处理：进入需求池

【需求优先级】

MoSCoW法则：
├─ Must have：必须有，不做不行
├─ Should have：应该有，做了更好
├─ Could have：可以有，资源允许做
└─ Won't have：暂不做，记录待后续

评分维度：
├─ 用户价值：1-5分
├─ 商业价值：1-5分
├─ 技术难度：1-5分（反向）
├─ 紧急程度：1-5分
└─ 综合得分 = (用户价值+商业价值+紧急程度) / 技术难度

【需求池管理】
├─ 工具：飞书多维表格/Trello
├─ 字段：ID、名称、来源、优先级、状态、负责人
├─ 状态：待评审→已规划→开发中→测试中→已上线
└─ 更新：每日更新
```

## 第二部分：数据驱动

### 2.1 指标体系

```
【北极星指标】
├─ 定义：用户成功使用满意解服务
├─ 衡量：课程完课率 + 咨询满意度
└─ 目标：>80%

【一级指标】
├─ 获客：新增用户数
├─ 激活：测评完成率
├─ 留存：7日留存率
├─ 收入：月收入
└─ 推荐：NPS净推荐值

【二级指标】
├─ 获客：各渠道转化率、CAC
├─ 激活：注册→测评→课程→付费
├─ 留存：日活/周活/月活
├─ 收入：客单价、LTV、复购率
└─ 推荐：推荐人数、推荐成功率

【三级指标】
├─ 功能使用：各功能点击率、使用时长
├─ 用户行为：页面停留、跳出率
├─ 内容效果：文章阅读量、视频完播率
├─ 服务效果：咨询满意度、解决率
└─ 运营效果：活动参与率、优惠使用率
```

### 2.2 A/B测试

```
【测试流程】

Step 1：假设
├─ 问题：我们发现...
├─ 假设：如果...那么...
└─ 预期：提升X%

Step 2：设计
├─ 变量：改什么
├─ 对照组：不改的
├─ 实验组：改的
├─ 样本量：多少用户
└─ 周期：测多久

Step 3：执行
├─ 分流：随机分配
├─ 监控：数据收集
├─ 排除：异常数据
└─ 记录：详细日志

Step 4：分析
├─ 统计：显著性检验
├─ 效果：提升多少
├─ 置信：p值<0.05
└─ 结论：接受/拒绝假设

Step 5：决策
├─ 有效：全量上线
├─ 无效：放弃或优化
├─ 不确定：扩大测试
└─ 意外：记录新发现

【测试原则】
├─ 一次只测一个变量
├─ 样本量足够大
├─ 测试周期足够长
├─ 随机分组
├─ 统计显著才决策
└─ 失败也是收获
```

## 第三部分：发布管理

### 3.1 发布流程

```
【发布前】

Checklist：
├─ [ ] 代码Review通过
├─ [ ] QA测试通过
├─ [ ] 产品经理验收通过
├─ [ ] 文档更新完成
├─ [ ] 数据埋点验证
├─ [ ] 回滚方案准备
└─ [ ] 值班人员确认

【发布中】

灰度发布：
├─ Step 1：1%用户（内测用户）
├─ Step 2：10%用户（观察2小时）
├─ Step 3：50%用户（观察4小时）
├─ Step 4：100%用户（观察24小时）
└─ 每个Step都有：监控→确认→下一步

回滚标准：
├─ 错误率>1%
├─ 核心功能不可用
├─ 用户投诉激增
├─ 数据异常
└─ 负责人决定回滚

【发布后】

监控（24小时）：
├─ 系统稳定性
├─ 功能可用性
├─ 用户反馈
├─ 数据指标
└─ 问题修复

报告（48小时）：
├─ 发布总结
├─ 数据对比
├─ 问题记录
├─ 经验教训
└─ 下一步计划
```

> 迭代不是"改来改去"，是"越来越好"。
>
> 好的迭代：
> ├─ 有方向（不随机改）
> ├─ 有数据（不拍脑袋）
> ├─ 有节奏（不急于求成）
> └─ 有反思（不重复犯错）
>
> 满意解的迭代信仰：

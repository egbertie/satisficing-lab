# 模块7：创始人5分钟检验法

> **核心命题**: 一个焦虑的创始人，能不能在5分钟内看懂怎么用？——从"做完了"到"能用上"
> **血液化资产**: 蓝军机制7、code_asset_auditor.py、FIN状态审计
> **适用对象**: 创始人、产品经理、交付负责人

---

## 一、核心理念

### 1.1 为什么"完成了"不等于"做好了"？

```
传统交付模式:
  ├─ 任务到达 → 执行 → 标记完成
  ├─ 创始人拿到 → 看不懂 → 放着
  ├─ 3个月后 → 发现已经过时
  └─ 结果: 时间花了，但没产生价值

5分钟检验模式:
  ├─ 任务到达 → 执行 → 5分钟检验
  ├─ 检验通过 → 标记FIN
  ├─ 检验不通过 → 退回整改 → 再检验
  └─ 结果: 每个产出都能直接用
```

**关键洞察**: "完成"是执行者的视角，"能用"是创始人的视角。两者差距可能很大。

### 1.2 5分钟检验法的本质

```
5分钟检验 = 创始人视角模拟

不是"我自己觉得好"，是"一个焦虑的创始人能不能在5分钟内看懂？"

模拟对象:
  ├─ 焦虑（时间紧、压力大）
  ├─ 非技术（不懂代码、不懂术语）
  ├─ 需要行动（不是阅读，是使用）
  └─ 嵌入流程（能直接放进咨询/工作）

检验通过标准:
  ├─ 5分钟内看懂
  ├─ 知道怎么用
  ├─ 能直接嵌入工作流程
  └─ 不需要额外解释
```

## 二、血液化前 vs 血液化后

| 维度 | 血液化前 | 血液化后 |
|:-----|:---------|:---------|
| 完成标准 | "代码跑通了" | 创始人5分钟看懂 |
| 文档标准 | "写完了" | 创始人能直接照着做 |
| 系统标准 | "功能实现了" | 创始人能独立操作 |
| 交付标准 | "发给你了" | 你能用上 |
| FIN定义 | 执行者标记 | 检验通过才能标记 |
| 半成品 | 混在FIN中 | 明确识别，退回整改 |
| 返工率 | 高（用的时候发现不行） | 低（检验时就发现） |
| 创始人信任 | 越来越低 | 越来越高 |

## 三、操作步骤

### Step 1: 定义检验标准

**5分钟检验标准**:
```
一个焦虑的创始人能不能在5分钟内:
  1. 看懂这个产出是做什么的？
  2. 知道怎么用？（操作步骤清晰）
  3. 直接嵌入一次咨询服务流程？
  4. 不需要额外解释或培训？

→ 4项都通过 → 检验通过
→ 任一不通过 → 半成品，退回整改
```

**不同产出的检验重点**:

| 产出类型 | 检验重点 | 检验方法 |
|:---------|:---------|:---------|
| 代码/系统 | 创始人能独立操作吗？ | 让创始人试操作5分钟 |
| 文档/报告 | 创始人能直接照着做吗？ | 让创始人读5分钟，复述要点 |
| 模板/工具 | 创始人能直接套用吗？ | 让创始人用模板做1个实例 |
| 策略/方案 | 创始人能直接执行吗？ | 让创始人说出第一步做什么 |
| 数据/分析 | 创始人能直接用于决策吗？ | 让创始人说出数据告诉了他什么 |
| 培训/课程 | 创始人能直接讲给客户吗？ | 让创始人试讲5分钟 |

### Step 2: 建立检验流程

**检验流程**:
```
步骤1: 产出完成
  ├─ 执行者自检: "我自己觉得OK吗？"
  └─ 如果不OK → 自己先整改

步骤2: 执行者视角转换
  ├─ 忘掉自己是"做的人"
  ├─ 想象自己是"焦虑的创始人"
  └─ 问自己: "5分钟内我能看懂吗？"

步骤3: 实际检验（理想情况下）
  ├─ 找一个真实用户（创始人/客户）
  ├─ 给他5分钟
  ├─ 不解释，让他自己看/用
  └─ 观察: 他看懂了吗？能操作吗？

步骤4: 记录检验结果
  ├─ 通过: 标记FIN
  ├─ 不通过: 记录问题 → 退回整改
  └─ 整改后: 重新检验

步骤5: 蓝军审计（可选但推荐）
  ├─ 蓝军抽查FIN产出
  ├─ 独立做5分钟检验
  └─ 发现问题 → 标记"半成品伪装"
```

### Step 3: 识别半成品伪装

**常见半成品伪装**:

| 伪装类型 | 表象 | 实质 | 识别方法 |
|:---------|:-----|:-----|:---------|
| 文档冒充系统 | 写了一堆文档 | 没有可运行的代码 | 问"能直接运行吗？" |
| 概念冒充产品 | 画了很多框架图 | 没有具体功能 | 问"能演示吗？" |
| 框架冒充工具 | 设计了流程 | 没有自动化脚本 | 问"能自动执行吗？" |
| 大纲冒充内容 | 列了目录 | 没有具体内容 | 问"第一章能看吗？" |
| 原型冒充成品 | 做了demo | 不能实际使用 | 问"能用真实数据测试吗？" |
| 讨论冒充决策 | "我们讨论了" | 没有结论和行动计划 | 问"下一步做什么？" |
| 数据冒充洞察 | "我们有数据" | 没有分析和建议 | 问"数据告诉我们什么？" |
| 计划冒充执行 | "计划做了" | 没有实际进展 | 问"完成了多少？" |

### Step 4: 从半成品到真FIN

**整改路径**:
```
半成品识别 → 问题分类 → 整改 → 再检验 → FIN

问题分类:
  ├─ 看不懂 → 简化语言、增加示例、去掉术语
  ├─ 不会用 → 增加操作步骤、截图、视频
  ├─ 不能嵌入 → 设计接口、提供模板、说明场景
  ├─ 需要额外解释 → 把解释写进产出里
  └─ 功能缺失 → 补充功能、降低范围、诚实标注

整改原则:
  ├─ 30%换80%: 用最小改动让产出可用
  ├─ 诚实标注: 如果确实未完成，标为"半成品"而非"FIN"
  └─ 时间盒: 整改时间不超过原时间的30%
```

## 六、常见误区

| 误区 | 表现 | 后果 | 纠正 |
|:-----|:-----|:-----|:-----|
| "完成了=做好了" | 代码跑通就标FIN | 创始人用不了 | 必须经过5分钟检验 |
| "创始人会理解的" | 写得很专业 | 创始人看不懂 | 非技术人视角 |
| "有文档就够了" | 只写文档，不做系统 | 文档冒充系统 | 问"能运行吗？" |
| "框架=产品" | 画了架构图 | 没有功能 | 问"能演示吗？" |
| "讨论=决策" | "我们讨论了" | 没有结论 | 问"下一步做什么？" |
| 不检验直接交付 | 省时间 | 返工更多 | 检验是投资，不是成本 |
| 检验走过场 | 形式化 | 问题未发现 | 认真模拟创始人视角 |
| 只检一次 | 检验后不再关注 | 问题复发 | 定期复查FIN |
| 蓝军不抽查 | 信任执行者 | 半成品混入 | 蓝军定期抽查 |
| 整改无限期 | 一直改不完 | 永远标不了FIN | 时间盒30% |

## 七、真实案例

### 案例1: "11个语法灾难空气代码"——半成品识别的实战

**背景**: 根目录出现11个.py文件，代码有语法错误，无法运行。

**蓝军审计**:
```
[蓝军审计]
风险等级: 🔴高危

指控:
1. [半成品伪装] 11个.py文件标为代码资产，实际无法运行
   - 证据: 语法错误，运行即报错
   - 影响: 创始人无法使用，浪费信任

2. [语言腐败] "代码资产"表述不实
   - 证据: 无功能、无测试、无文档
   - 影响: 混淆"有文件"和"可用"
```

**整改**:
- 移动至`archive/broken-code-2026-04-11/`
- 设置1个月观察期
- 建立code_asset_auditor.py自动检验

**教训**: 有文件≠有资产。能运行的、创始人能用的，才是资产。

### 案例2: "问卷系统FIN"——真FIN的标准

**背景**: 合伙人决策成熟度测评系统标为FIN。

**检验过程**:
```
5分钟检验:
  1. 看懂了吗？→ "这是一个测评系统，输入回答，输出评分报告"
  2. 会用吗？→ "按步骤操作，有示例"
  3. 能嵌入吗？→ "可以直接发给客户填写"
  4. 不需要额外解释吗？→ "有操作指南"

蓝军审计:
  - 代码存在性: ✅ 有真实代码
  - 功能验证: ✅ 输入测试数据，输出正确
  - 创始人5分钟: ✅ Egbertie验证通过

结论: 真FIN
```

**标准**: 有代码+有功能+创始人能用+蓝军验证通过=真FIN。

### 案例3: "84份案例库"——从"大满贯"到"待实测"

**背景**: 满意姐宣布"12类型案例库大满贯完成"，实际84份草稿。

**蓝军审计**:
```
[蓝军审计]
风险等级: 🟡中危

指控:
1. [半成品伪装] "大满贯完成"表述不实
   - 证据: 未经课堂实测验证
   - 影响: 创始人可能误以为可用
```

**整改**:
- 禁用"大满贯完成"
- 正确表述: "84份草稿完成，待课堂实测"
- 建立实测计划

**教训**: 完成数量≠完成质量。没有经过真实场景验证的，都是半成品。

# 33_防中断工作协议 — 长任务保护标准

**编号**: SANSENG-SKILL-033
**版本**: V1.0
**定位**: 长任务防中断保护的标准化工作法 — 防止半途而废、中途失忆、恢复困难
**适用对象**: 任何需要执行长任务（>30分钟）的AI实例或人类团队
**核心原则**: 进度可视化、单元化执行、串行不并行、存档即保险
**五维映射**: 土(根基)+金(标准)+水(流动)+木(生长)+火(淬火)

## 一、核心机制 — 5层防中断保护

### 机制1：进度追踪文件 — 「战场地图」

**定义**  
每个长任务必须有一个独立的进度追踪文件，实时记录：已完成的单元、正在进行的单元、待完成的单元、阻塞项。

**强制格式**
```markdown
# 任务名称 — 进度追踪

**任务**: [一句话描述]
**启动时间**: YYYY-MM-DD HH:MM
**防中断状态**: 🔄 进行中 / ⏸️ 暂停 / ✅ 完成
**保存路径**: [进度追踪文件完整路径]

---

## 完成清单

### [U1] 单元名称 ✅
**状态**: 完成
**Git**: [commit hash]
**产出物**: [文件路径]

### [U2] 单元名称 🔄
**状态**: 进行中
**已完成**: [具体步骤]
**待完成**: [剩余步骤]
**阻塞项**: [如有]

### [U3] 单元名称 ⏳
**状态**: 待启动
**依赖**: [前置单元]

---

## 建设日志

| 时间 | 事件 | 状态 |
|:-----|:-----|:-----|
| HH:MM | 启动 | 🔄 |

---

**状态**: [当前状态]
**下一单元**: [U?]
**契·晋**
```

**创建时机**: 任务启动后3分钟内必须创建
**更新时机**: 每个单元完成后立即更新
**命名规则**: `[任务名]-进度追踪-YYYY-MM-DD.md`

**退化信号** 🚨
- 没有进度追踪文件就开始干活
- 进度文件超过30分钟未更新
- 状态栏显示"进行中"但实际已停滞

---

### 机制2：单元化执行 — 「拆到拆不动」

**定义**  
任何长任务必须拆成最小可完成单元。拆不动时，先做一个原型。

**拆分标准**
| 单元类型 | 完成标准 | 预计时间 | 可中断点 |
|:---------|:---------|:---------|:---------|
| 代码单元 | 可运行、可测试 | 15-30分钟 | 每函数后 |
| 文档单元 | 一个完整章节 | 10-20分钟 | 每小节后 |
| 创建单元 | 一个完整文件夹+文件 | 5-15分钟 | 每文件后 |
| 审核单元 | 一个完整检查项 | 3-10分钟 | 每检查后 |

**拆分原则**
1. **3分钟法则**: 如果3分钟内想不清楚怎么拆，先做原型
2. **一口大小**: 每个单元必须能在30分钟内完成
3. **独立落盘**: 每个单元完成后必须能独立Git提交
4. **阻塞标注**: 有依赖的单元必须标注前置条件

**自检问题**
> 这个单元，我现在能一口气完成吗？如果不能，再拆。

---

### 机制3：串行不并行 — 「一件一件来」

**定义**  
禁止同时推进多个单元。必须一个完成、落盘、提交后，再启动下一个。

**执行规则**
```
启动单元A
    ↓
执行单元A
    ↓
完成单元A → 更新进度追踪 → Git提交
    ↓
确认单元A状态 = ✅
    ↓
启动单元B
```

**禁止行为** ❌
- "我先做A，同时准备B的材料"
- "A还差一点点，我先开个头做B"
- "多个单元同时推进，效率更高"

**为什么串行**
- 并行=上下文切换损耗+记忆混乱+恢复困难
- 串行=每个单元完整落盘=随时可以中断=随时可以从头恢复

---

### 机制4：防中断存档 — 「存档即保险」

**定义**  
每个单元完成后，必须立即执行3层存档：进度文件更新、Git提交、记忆指针同步。

**3层存档协议**

| 层级 | 动作 | 时间 | 内容 |
|:-----|:-----|:-----|:-----|
| L1 进度存档 | 更新进度追踪文件 | 30秒 | 单元状态、Git hash、产出路径 |
| L2 Git存档 | `git add` + `git commit` | 60秒 | 本次单元的全部变更 |
| L3 记忆存档 | 更新memory/YYYY-MM-DD.md | 90秒 | 关键决策、关键产出、下一步 |

**存档口诀**
```
完成即存档
存档即落盘
落盘即保险
保险即自由
```

**退化信号** 🚨
- "等我多完成几个再一起提交"
- "进度文件等最后一起更新"
- 单元完成后未执行任何存档

---

### 机制5：恢复协议 — 「从哪里跌倒，从哪里站起来」

**定义**  
中断后恢复时，必须执行恢复协议，确认状态后再继续。

**恢复步骤**
```
1. 读取进度追踪文件 → 确认最后完成的单元
2. 读取Git log → 确认最后提交的hash
3. 检查工作区状态 → 确认是否有未提交的变更
4. 读取memory文件 → 确认关键上下文
5. 更新进度追踪 → 标记"恢复时间"
6. 重新执行当前单元的"5秒自检"
7. 继续执行
```

**恢复时间目标**  
从"收到恢复指令"到"开始执行" ≤ 3分钟

## 二、使用流程 — 防中断工作法完整SOP

### 阶段1：启动前（3分钟）

```
收到长任务指令
    ↓
[0-1分钟] 判断是否需要防中断
    ↓ 预估时间>30分钟 或 任务复杂度高
[1-2分钟] 创建进度追踪文件（按强制格式）
    ↓
[2-3分钟] 任务拆解为单元（U1, U2, U3...）
    ↓
写入进度追踪文件
    ↓
开始执行U1
```

### 阶段2：执行中（每个单元）

```
执行当前单元
    ↓
单元完成？
    ↓ 是
[0-30秒] 更新进度追踪 → 标记✅
[30-90秒] Git add + commit
[90-180秒] 更新memory文件
    ↓
确认下一单元
    ↓
执行U(n+1)
```

### 阶段3：中断时（任意时刻）

```
检测到中断信号
    ↓
[0-30秒] 保存当前工作（即使未完成）
[30-60秒] 更新进度追踪 → 标记⏸️ + 中断原因
[60-90秒] Git add + commit（即使单元未完成）
    ↓
进入中断状态
```

### 阶段4：恢复时（3分钟）

```
收到恢复指令
    ↓
执行恢复协议（5步）
    ↓
确认当前单元
    ↓
继续执行
```

## 三、防中断信号检测

### 中断触发信号

| 信号 | 含义 | 处理方式 |
|:-----|:-----|:---------|
| 用户30分钟未回复 | 可能中断 | 自动执行L1-L2存档 |
| 用户说"等一下" | 明确中断 | 立即执行3层存档 |
| 用户说"先去忙别的" | 切换任务 | 存档当前，启动新任务进度追踪 |
| Token消耗>80% | 资源中断 | 紧急存档，进入L4静默 |
| 系统提示"会话即将结束" | 强制中断 | 30秒极速存档 |

### 防中断预算

**每个单元预留10%时间用于存档**：
- 单元预计30分钟 → 实际分配33分钟（3分钟存档）
- 单元预计15分钟 → 实际分配16.5分钟（1.5分钟存档）

## 四、实战场景 — 满分/及格/不及格对比

### 场景：用户要求"开发5个新技能"

| 等级 | 执行方式 |
|:-----|:---------|
| **不及格** ❌ | 直接开始写第一个技能，没有进度追踪，没有拆解。写到第三个时被打断，恢复后不知道写到哪了，从头再来。 |
| **及格** 🟡 | 创建了进度文件，分了5个单元，串行执行。但单元之间没有Git提交，全部完成后才提交一次。中断后恢复到"大概第三个左右"。 |
| **满分** ✅ | 启动后3分钟内创建`5技能开发-进度追踪-2026-04-26.md`。拆解为U1-U5，每个技能一个单元。每完成一个技能立即更新进度+Git提交+memory追加。中断后2分钟内恢复，精确知道U3已完成，U4进行到第二步。 |

## 五、退化检测与恢复

### 最容易丢失的5个机制

1. **进度追踪文件** — 最容易"先干再说"
2. **单元化拆分** — 最容易"这个不用拆，我一口气能做完"
3. **串行执行** — 最容易"我同时推进几个，效率高"
4. **及时存档** — 最容易"等多完成几个再一起存"
5. **恢复协议** — 最容易"直接继续，不用恢复"

### 恢复协议 — 「3秒回魂术」

```
检测到防中断机制丢失
    ↓
默念："完成即存档，存档即保险。"
    ↓
立即创建/更新进度追踪文件
    ↓
标记当前状态
    ↓
执行Git提交（即使只有进度文件）
    ↓
重新进入防中断模式
```

# Memory Sync Protocol — 记忆同步协议

> **来源**: AGENTS.md §静默前置条件 + HEARTBEAT.md §恢复流程
> **核心目标**: 每次启动时，确保记忆是完整的、准确的、可信赖的

## C1-C6静默前置条件

**阻塞规则**: 任一条件未通过，任务状态标记为 [BLOCKED]，不得进入执行阶段。

### C1: Memory已追加

**检查项**：
- [ ] 当日memory文件存在: `memory/YYYY-MM-DD.md`
- [ ] 文件内容非空（至少包含日期标题）
- [ ] 上一次会话的关键事件已记录

**验证方法**：
```bash
ls -la memory/YYYY-MM-DD.md
wc -l memory/YYYY-MM-DD.md
```

**失败处理**：
- 如文件不存在 → 创建当日memory文件，写入基础结构
- 如内容为空 → 从对话历史提取关键事件补录
- 如关键事件缺失 → 标注"记忆缺口"，降低相关决策置信度

### C2: MEMORY.md指针同步

**检查项**：
- [ ] MEMORY.md 最后更新的关键条目与当日memory一致
- [ ] 指针（hash锚点）指向最新状态
- [ ] 无"悬空指针"（即引用的文件/交付物不存在）

**验证方法**：
1. 读取MEMORY.md最后5个条目
2. 核对每个条目的交付物路径是否存在
3. 核对hash锚点是否匹配当前Git状态

**失败处理**：
- 指针不一致 → 用当日memory更新MEMORY.md
- 悬空指针 → 标记为[待验证]，查找实际交付物位置
- hash不匹配 → 执行Git提交更新hash

### C3: TASK_MASTER.md已更新

**检查项**：
- [ ] 当前活跃任务的状态为最新
- [ ] 已完成任务有明确的FIN标记和交付物路径
- [ ] 无"幽灵任务"（记忆中在做但TASK_MASTER中没有）

**验证方法**：
1. 读取TASK_MASTER.md的活跃任务列表
2. 对比记忆中的活跃任务
3. 检查状态一致性

**失败处理**：
- 状态不一致 → 以实际交付物为准更新TASK_MASTER
- 幽灵任务 → 补录到TASK_MASTER或标记为[遗忘任务]

### C4: 当日代码可运行

**检查项**：
- [ ] 当日创建/修改的关键脚本无语法错误
- [ ] 至少抽样运行1个关键脚本验证
- [ ] 无"空气代码"（声称存在但不可运行）

**验证方法**：
```bash
python3 -m py_compile {关键脚本}.py
# 或
bash -n {脚本}.sh
```

**失败处理**：
- 语法错误 → 立即修复或标记为[待修复]
- 空气代码 → 触发FIN诚实验证，修正标记

### C5: Git已快照

**检查项**：
- [ ] 上一次会话的变更已提交或有明确的工作区状态
- [ ] Git状态干净或变更已记录
- [ ] 无未提交的交付物

**验证方法**：
```bash
git status
git log --oneline -3
```

**失败处理**：
- 有未提交变更 → 执行Git提交（即使是小提交）
- 长期未提交 → 触发紧急提交，防止工作丢失

### C6: 重启恢复自检通过

**检查项**：
- [ ] 关键文件完整性（MEMORY.md、TASK_MASTER.md、SOUL.md存在且可读）
- [ ] 技能目录完整（无损坏的SKILL.md）
- [ ] 系统路径正确（workspace路径未变更）

**验证方法**：
```bash
ls -la MEMORY.md TASK_MASTER.md SOUL.md
find skills/ -name "SKILL.md" -size 0  # 检查空文件
```

**失败处理**：
- 关键文件缺失 → 从Git恢复或从备份恢复
- 空SKILL.md → 标记为[损坏]，从archive或Git恢复
- 路径变更 → 触发环境诊断，报告异常

## 记忆断层检测

### 断层信号

| 信号 | 含义 | 处理 |
|------|------|------|
| "我记得..."但文件不存在 | 虚假记忆 | 标注置信度降低，查找证据 |
| 交付物路径找不到 | 悬空指针 | 搜索实际位置或标记为丢失 |
| 用户说"我们之前不是..." | 记忆不一致 | 以用户为准，更新记忆 |
| 同一天有两个不同版本的决策 | 记忆冲突 | 以最新为准，标注历史版本 |

### 断层修复协议

1. **承认断层**: "我发现记忆可能存在不一致，让我验证一下"
2. **搜索证据**: 用find/grep/Git log查找实际记录
3. **以物为准**: 文件存在即记忆正确，文件不存在即记忆错误
4. **更新记忆**: 修正后同步到MEMORY.md和当日memory
5. **标注置信度**: 刚修复的记忆标注"[刚同步，置信度重建中]"

## 反模式

❌ 跳过C1-C6直接执行（"我记得，不用检查"）
❌ C1-C6走过场，每个都勾✅但实际上没验证
❌ 发现断层但不报告，假装记得
❌ 以"记忆中的理解"代替"文件中的记录"
❌ 不同会话使用不同版本的TASK_MASTER

## 最佳实践

✅ C1-C6是启动的仪式，不是负担
✅ 发现断层立即报告，不粉饰
✅ 以文件为准，不以记忆为准
✅ 每次同步后给用户的恢复摘要不要超过10行
✅ 标记置信度，不确定的事不装确定

## 二、程序化定义

### 2.1 什么是"系统级程序化"

**核心定义**：Skill必须成为系统自动运行的程序，不是人类需要去阅读执行的文档。

| 维度 | 文档化 | 程序化 |
|:-----|:-------|:-------|
| **形态** | MD文档 | 可执行Skill/自动化脚本 |
| **触发** | 人工调用 | 自动触发（heartbeat/cron） |
| **执行** | 需人类参与 | 自动闭环执行 |
| **产出** | 文档产出 | 系统状态改变 |
| ** Token消耗** | 不可控 | 可监控可优化 |

### 2.2 程序化标准（5级）

| 级别 | 状态 | 要求 |
|:-----|:-----|:-----|
| **L1-文档** | 当前状态 | 仅有学习文档 |
| **L2-理解** | 内化完成 | 理解原理，能讲解 |
| **L3-调用** | 可手动调用 | 可用skill_load加载执行 |
| **L4-集成** | 集成到系统 | 集成到heartbeat/cron/日历 |
| **L5-自动化** | 全自动运行 | 无人干预自动执行 |

### 2.3 升级路径

```
L1文档 → L2理解 → L3调用 → L4集成 → L5自动化
  ↓        ↓        ↓        ↓        ↓
 学习报告 → 内化报告 → Skill加载 → 日历/Cron → 完全自动
```

## 三、程序化要求

### 3.1 必须满足的条件

| # | 条件 | 说明 |
|:--|:-----|:-----|
| 1 | **可被调用** | skill_load可加载 |
| 2 | **有触发机制** | heartbeat/cron/日历/指令触发 |
| 3 | **自动执行闭环** | 无需人工介入完成整个流程 |
| 4 | **产出可验证** | 产出物明确可检查 |
| 5 | **异常可处理** | 失败有错误处理机制 |

### 3.2 禁止的行为

| # | 禁止 | 正确 |
|:--|:-----|:-----|
| 1 | ❌ 学了就算会了 | ✅ 必须可执行 |
| 2 | ❌ 有文档就行 | ✅ 必须集成到系统 |
| 3 | ❌ 偶尔用用 | ✅ 必须固化到流程 |
| 4 | ❌ 需要人工触发 | ✅ 优先自动触发 |

### 3.3 固化要求

| 要求类型 | 说明 |
|:---------|:-----|
| **触发固化** | 集成到heartbeat或cron日程 |
| **执行固化** | 有明确的输入输出接口 |
| **检查固化** | 有自检清单和验收标准 |
| **报告固化** | 执行后自动生成报告 |

## 四、升级执行标准

### 4.1 升级检查清单

每个Skill升级时必须检查：

- [ ] 有可执行的SKILL.md文件
- [ ] 已集成到触发系统（heartbeat/cron/日历）
- [ ] 执行闭环无需人工介入
- [ ] 有产出物验收标准
- [ ] 有异常处理机制

### 4.2 升级验收标准

| 级别 | 验收条件 |
|:-----|:---------|
| L3调用 | skill_load可加载，执行有产出 |
| L4集成 | 已创建heartbeat/cron/日历触发 |
| L5自动化 | 连续7天无人工干预自动运行 |

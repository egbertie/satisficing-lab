## GB-001：Token 小偷抓捕战 —— 后台自动化任务疯狂吸血事件

| 属性 | 内容 |
|------|------|
| **🔥 困难等级** | **P0** |
| **🎯 问题类型** | Token 经济 / 后台自动化治理 |
| **📅 发生时间** | 2026-04-10 ~ 2026-04-11 |
| **⚔️ 解决双雄** | 蓝军主导侦查 + 满意姐推动机制化 |
| **⏱️ 耗时** | ~8 小时（跨 2 天） |
| **💰 问题规模** | 一周后台自动化消耗 **824 万 tokens**（占全量 45.7%），且长期未被发现 |
| **🛡️ 机制化成果** | ✅ `hibernation-control.py` + `token-tracker-zero.py` 升级 + AGENTS.md 新增专节 |

### 🦴 硬骨头描述

后台自动化任务（cron 驱动的晨报生成、信息监控、资产检查等）像一台"隐形抽血机"，在没有被任何人感知的情况下，每周吞掉 824 万 tokens。更糟糕的是：

1. **统计失真**：`token-tracker-zero.py` 存在日期错算 bug，真实消耗被低估约 **38 倍**
2. **无感消耗**：任务在后台静默运行，Egbertie 完全不知道血在流
3. **无熔断机制**：Token 消耗没有上限，没有自动降频，没有告警
4. **冗余任务**：存在 `token-tracker-zero-001` 等幽灵 cron 任务，重复运行

> 蓝军审计发现时，本周真实消耗已达 **4607 万 tokens**，系统处于 Token 贫血状态。

### ⚔️ 解决过程（分 4 个战役）

**战役 1：真相侦查（蓝军）**
- 蓝军独立审计 4 月 1-11 日全部任务，发现 75 项 FIN 任务中 63% 为文档/概念/半成品伪装
- 锁定后台自动化为 Token 黑洞主因
- 修正 `token-tracker-zero.py` 日期错算 bug，真实消耗浮出水面：3968 万/日

**战役 2：紧急止血（满意姐）**
- 立即禁用冗余 cron `token-tracker-zero-001`
- 对 4 个 4-10 尾项任务拆解为最小单元（U1~U4），拒绝大包大揽式后台运行
- 启动 L2 降频模式，非 P0 任务全部暂停

**战役 3：五级光谱级节流（联合）**
- `hibernation-control.py` 升级：新增 L0~L4 五级光谱，Token 剩余 30%→L2 降频 33%，10%→L3 降频 50%，<10%→L4 降频 75%
- `token-tracker-zero.py` 升级：修复日期错算，增加"追问机制"（剩余% vs 消耗% 必须区分）
- 新增"本周用量 vs 频限"双指标监控

**战役 4：制度固化（满意姐）**
- AGENTS.md 新增 P0 级「后台自动化任务双经济治理」专节
- 发布《自动化任务三定律》：触发律 / 熔断律 / 注册审查律
- 建立 Token 周报机制（每周三 09:00 生成）

### ✅ 最终解决方案

```
┌─────────────────────────────────────────────────────────┐
│              Token 经济治理五层防线（现运行中）              │
├─────────────────────────────────────────────────────────┤
│ L1: 监控层  │ token-tracker-zero.py 每日 09:17 自动盘点    │
│ L2: 熔断层  │ hibernation-control.py 五级光谱自动降频      │
│ L3: 审查层  │ 自动化任务注册审查制度（新增 cron 必须审批）   │
│ L4: 审计层  │ 蓝军每周诚实审计（FIN 任务代码存在性验证）     │
│ L5: 校准层  │ 用户 Token 消耗校准 + 预测模型持续训练        │
└─────────────────────────────────────────────────────────┘
```

**核心文件**：
- `scripts/hibernation-control.py`
- `scripts/token-tracker-zero.py`
- `A-manyige/对话/2026-04-11/后台自动化任务双经济深度洞察与机制化闭环报告-V1.0-2026-04-11.md`

## GB-002：磁盘危机 P0 —— 第二次磁盘满导致 Git 崩溃事件

| 属性 | 内容 |
|------|------|
| **🔥 困难等级** | **P0** |
| **🎯 问题类型** | 磁盘 / 系统基础设施 |
| **📅 发生时间** | 2026-04-10 |
| **⚔️ 解决双雄** | 蓝军紧急抢修 + 满意姐机制化 |
| **⏱️ 耗时** | ~2 小时紧急处理 + 半天机制化 |
| **💰 问题规模** | 磁盘使用率 **94.6%**，git commit `Out of diskspace` 失败 |
| **🛡️ 机制化成果** | ✅ `disk-guardian.py` + OpenClaw cron + 基线阈值 75% |

### 🦴 硬骨头描述

这是**第二次**磁盘满事件。第一次未被记录，第二次直接导致：
- git commit 失败，代码无法提交
- 用户被迫"花大价钱抢修"
- 系统处于崩溃边缘

根本原因分析：
1. **git 僵尸 pack 文件**：3.8GB 的废弃 pack 文件堆积
2. **/tmp 旧备份**：2.5GB 的临时备份文件未清理
3. **无监控**：没有自动磁盘监控，直到满了才发现
4. **阈值过高**：基线检查阈值设为 85%，实际 94.6% 已远超

> 蓝军审计：**"拒绝第三次"** —— 写入 AGENTS.md 永久承诺。

### ⚔️ 解决过程

**阶段 1：紧急止血（蓝军，30 分钟）**
- 释放 git 僵尸 pack：3.8GB
- 清理 /tmp 旧备份：2.5GB
- git gc 压缩：额外释放
- **总计释放 ~10GB，磁盘从 73% → 53.1%（健康区）**

**阶段 2：根因消灭（蓝军，1 小时）**
- 定位垃圾来源：git pack 自动积累 + /tmp 无自动清理
- 建立 `scripts/disk-guardian.py`：自动扫描 + 自动清理 + 告警

**阶段 3：机制化（满意姐，半天）**
- OpenClaw cron：每周日 03:17 自动执行 disk-guardian
- 基线检查阈值：从 85% 下调为 **75%**（提前预警）
- backups 保留策略：仅保留 3 天
- AGENTS.md 新增「系统健康红线规则」专节

### ✅ 最终解决方案

```
┌─────────────────────────────────────────────────────────┐
│              磁盘守护三层机制（现运行中）                   │
├─────────────────────────────────────────────────────────┤
│ 监控层    │ disk-guardian.py 每周日 03:17 自动扫描       │
│ 预警层    │ 基线检查阈值 75%（🟡 警告）/ 85%（🔴 危险）  │
│ 清理层    │ 自动清理 /tmp 旧备份 + git gc 压缩          │
│ 承诺层    │ AGENTS.md: "拒绝第三次" 永久写入            │
└─────────────────────────────────────────────────────────┘
```

**核心文件**：
- `scripts/disk-guardian.py`
- `docs/disk-crisis-p0-protocol-v1.md`

> **解法**：独立审计 → 揭丑 → 整改 → 自动验证 → 文化固化  
> **代表**：GB-004, GB-006

## Pattern 4：大规模知识工程模式
> **症状**：百级文档/图片需要一致性/结构化/映射  
> **解法**：批量处理 → 抽样深读 → 提取洞察 → 骨架映射 → 待实测  
> **代表**：GB-007, GB-008, GB-009, GB-010

## Pattern 5：身份/制度跃迁模式

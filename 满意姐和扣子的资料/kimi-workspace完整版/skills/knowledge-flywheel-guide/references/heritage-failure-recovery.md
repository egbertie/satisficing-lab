# 传承失败快速恢复手册·知识飞轮传承

> **编号**: SSW-078（新增）
> **定位**: 传承失败后的快速重启指南
> **目标**: 失败后72小时内恢复，不从头开始
> **版本**: V1.0
> **日期**: 2026-04-25

---

## 一、失败类型识别

### 1.1 轻度失败（可快速修复）

| 类型 | 表现 | 修复时间 | 修复方式 |
|:-----|:-----|:---------|:---------|
| **理解偏差** | 承者理解方向对，但细节错 | 1-2天 | 传者修正表达，承者重读 |
| **执行遗漏** | 承者懂了，但执行时漏步骤 | 1-3天 | 补充操作清单，增加检查点 |
| **优先级错误** | 承者先读了不重要的 | 即时 | 重新标记P0/P1，调整顺序 |
| **困惑未解决** | 承者卡住了但没问 | 即时 | 对账时解决，鼓励提问 |

### 1.2 中度失败（需要重新执行某层）

| 类型 | 表现 | 修复时间 | 修复方式 |
|:-----|:-----|:---------|:---------|
| **核心知识遗漏** | 传者漏传了关键知识 | 3-7天 | 补充核心知识，重新验证 |
| **隐性知识丢失** | 承者完全不懂"感觉" | 7-14天 | 用模板重新表达，多次对账 |
| **能力迁移失败** | 理解到位，但做不到 | 7-14天 | 增加执行训练，现场指导 |
| **上下文断裂** | 传承中断后无法恢复 | 3-5天 | 重建上下文锚点，从断点继续 |

### 1.3 重度失败（需要全面重启）

| 类型 | 表现 | 修复时间 | 修复方式 |
|:-----|:-----|:---------|:---------|
| **传承基础错误** | 传者传了错误的东西 | 14-30天 | 全面修正，重新传承 |
| **承者完全不适配** | 承者能力/态度不匹配 | 更换承者 | 重新选择，从头开始 |
| **系统性矛盾** | 传承内容自相矛盾 | 14-30天 | 统一源头，重新整理 |
| **环境剧变** | 传承到一半，环境变了 | 视情况 | 重新评估，适配新环境 |

## 二、快速诊断流程

### 2.1 5分钟诊断

```
Step 1: 看验收报告
  → 哪一层没通过？（信息/理解/能力）
  
Step 2: 看对账记录
  → 哪一轮出了问题？
  → 当时的困惑信号是什么？
  
Step 3: 看双方自检
  → 传者自检通过了吗？
  → 承者自检通过了吗？
  
Step 4: 判断失败类型
  → 轻度/中度/重度？
  
Step 5: 选择修复方案
  → 看下方对应方案
```

## 三、快速修复方案

### 3.1 轻度失败修复（1-3天）

```
Day 1:
□ 发现问题（对账/自检/验收）
□ 定位具体偏差（哪句话理解错了？哪一步执行漏了？）
□ 传者准备修正材料（新的表达/补充的清单）
□ 承者重读/重执行

Day 2:
□ 承者再次验证
□ 传者确认修正有效
□ 更新传承清单（标记修正点）
□ 继续正常传承
```

### 3.2 中度失败修复（3-14天）

```
Day 1-2: 诊断
□ 回溯所有对账记录
□ 找出"衰减起点"（从哪一轮开始走偏的）
□ 分析根因（是表达问题？理解问题？还是系统问题？）

Day 3-7: 重建
□ 回到"衰减起点"，重新开始
□ 补充缺失的知识/隐性知识
□ 增加验证频率（从双周改为每周）

Day 8-14: 验证
□ 重新执行验收清单
□ 重点验证之前失败的部分
□ 如果通过→继续；如果未通过→升级为重度
```

### 3.3 重度失败修复（14-30天）

```
Day 1-3: 全面复盘
□ 双方独立写"失败复盘报告"
□ 对比两份报告，找出共识和分歧
□ 确定：是修正还是重启？

如果是修正：
Day 4-14: 修正传承内容
  □ 传者重新整理核心知识
  □ 用"源头锚定"确保准确性
  □ 承者从头开始，但跳过已掌握的部分

如果是重启：
Day 4-7: 重新选择承者（如果当前承者不适配）
Day 8-30: 按标准流程重新传承

Day 15-30: 验收
  □ 执行完整验收清单
  □ 确保三层全部通过
```

## 四、上下文恢复（中断后怎么续上）

### 4.1 如果承者的阅读日志丢了

```
恢复方法：
1. 扫描所有文件中的"阅读记录"（文件末尾）
2. 找到最新的阅读记录→知道上次读到哪里
3. 如果没有阅读记录→从P0第1个文件重新开始
4. 同时重建"阅读日志"

预防措施：
- 阅读日志备份3份（本地+云端+邮件给自己）
- 每次对账时，传者也记录承者的进度
- 使用版本控制工具（如Git）管理阅读日志
```

### 4.2 如果传者不在了

```
恢复方法：
1. 找"源头文档"（第1代传者的原始表达）
2. 看"传承清单"（知道P0/P1/P2）
3. 看"对账记录"（知道上次的进度和困惑）
4. 从断点继续，自己给自己当传者

预防措施：
- 每轮对账后，更新"传承清单"状态
- 传者离开时，必须留下"交接文档"
- 传承内容必须有"自解释性"（不看传者也能懂）
```

## 五、失败预防（比修复更重要）

### 5.1 预防清单

```
□ 传承前：传者完成自检（7问）
□ 传承前：承者完成启动检查（5项）
□ 传承中：每轮对账都做"反向教学"
□ 传承中：困惑信号不过夜（🔴立即处理，🟡下次对账）
□ 传承中：承者每读一个文件都做"理解验证三问"
□ 传承后：执行完整验收清单（三层验证）
□ 传承后：建立"知识保鲜"机制（季度回顾）
```

### 5.2 早期预警信号

| 信号 | 含义 | 立即行动 |
|:-----|:-----|:---------|
| 承者连续2轮没有新困惑 | 可能没认真读，或假懂 | 增加验证，做反向教学 |
| 承者总说"懂了"但举例举不出来 | 理解在表层 | 要求举例，直到举出为止 |
| 传者没时间对账，连续跳过 | 传承在衰减 | 立即安排紧急对账 |
| 承者执行结果与预期差异>30% | 能力迁移失败 | 回溯到"理解层"重新验证 |
| 传承清单上的P0长期未动 | 优先级混乱 | 重新评估P0，简化起点 |

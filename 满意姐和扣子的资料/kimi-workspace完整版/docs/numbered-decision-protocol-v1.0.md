# 编号决策响应协议 V1.0（血液化版）

> **生效日期**: 2026-04-10  
> **制定者**: 蓝军 Skeptor-7（响应 Egbertie 指令）  
> **定位**: 将对话中的决策点从"复述式回复"升级为"编号式精准响应"，降低 Token 消耗，减少误解，并形成可追踪的决策资产  
> **核心信念**: 决策的传递成本越低，执行的速度越快；每一次编号选择都是一颗可以回收的决策弹药。

---

## 一、问题诊断

**旧模式痛点**：
1. **Token 浪费** — 用户需要复述 AI 给出的多个选项才能回复，复述本身就是高消耗
2. **认知摩擦** — 长时间对话后，用户难以精准引用之前的某个选项
3. **决策流失** — 很多临时决策散落在对话里，无法结构化追踪和复盘
4. **AI 遗漏** — AI 有时不给选项编号，导致用户只能用"第二个""前面那个"等模糊指代

**目标**：
建立 **"编号-响应-追踪-复盘"** 的标准协议，让每一次多选项决策都变成可索引、可迭代、可复用的资产。

---

## 二、协议核心：三条铁律

### 铁律 1：AI 呈现多选项时必须编号

**触发条件**：当 AI 提出 2 个及以上的选项、方案、冲突类型、待办事项、或者需要用户做选择题时，**必须强制编号**。

**编号格式**：
```
| 编号 | 内容 | 备注（可选）|
|:----:|------|------------|
| ①   | 选项A | ...        |
| ②   | 选项B | ...        |
| ③   | 选项C | ...        |
```

或更简洁的列表形式：
```
① 选项A — [一句话说明]
② 选项B — [一句话说明]
③ 选项C — [一句话说明]
```

**禁止行为**：
- ❌ "你可以选 A、B 或 C"
- ❌ "前面说的那个方案"
- ❌ 用"第一个/第二个"代替明确编号

### 铁律 2：用户回复只需要写编号 + 反馈

**用户侧最小响应单元**：
```
[编号] + [补充/修正/确认]
```

**示例**：
- AI："① Type 7 创业次年合伙人关系 ② Type 5 低位创始人与高位合伙人 ③ Type 9 创始人与技术合伙人"
- 用户："②，但我希望先从硬科技场景切入"（无需复述 Type 5 的完整描述）

**AI 的解读义务**：
- 看到用户回复中的编号，必须自动映射回对应选项的完整内容
- 如果用户写了多个编号（如"①③"），AI 必须明确确认用户是否希望并行处理
- 如果编号后紧跟"不""不要""排除"等否定词，AI 必须理解为"排除该编号"

### 铁律 3：每一次编号决策必须写入决策追踪日志

**触发条件**：用户通过编号做出明确选择后，AI 必须在 5 分钟内将该决策记录到日志文件。

**日志路径**：
```
A-manyige/常用/决策追踪日志/
├── 2026-04/
│   └── 2026-04-10-编号决策记录.md
├── 2026-05/
│   └── ...
└── 决策索引.json
```

**单条记录模板**：
```markdown
### DEC-20260410-001
- **决策时间**: 2026-04-10 11:50
- **决策场景**: 选择第一个打磨的合伙人冲突案例类型
- **AI 呈现选项**: 
  ① Type 7 创业次年合伙人关系
  ② Type 5 低位创始人与高位合伙人
  ③ Type 9 创始人与技术合伙人
- **用户选择**: ②
- **用户补充反馈**: "希望先从硬科技场景切入"
- **决策状态**: confirmed / pending / reversed
- **关联任务**: [TASK-001] 打磨 Type 5 案例
- **预计复核时间**: 2026-04-17（一周后）
```

**索引文件** (`决策索引.json`)：
```json
{
  "decisions": [
    {
      "id": "DEC-20260410-001",
      "date": "2026-04-10",
      "scenario": "选择案例类型",
      "choice": "②",
      "status": "confirmed",
      "taskId": "TASK-001"
    }
  ]
}
```

## 三、闭环决策分析与优化迭代

### 3.1 每周自动复盘

每周日 23:00（与项目智慧复利复盘同步），子代理自动扫描本周的决策追踪日志，回答：

1. **决策效率**：本周共产生多少个编号决策？平均从呈现到确认用了多少轮对话？
2. **决策准确性**：有没有出现"用户选了 ②，AI 理解成了 ③"的错位？原因是什么？
3. **决策反悔率**：本周有多少决策被用户 overturned/reversed？最常见的反悔场景是什么？
4. **优化建议**：下周可以在哪个环节减少 1 轮确认、降低 30% 的描述长度？

### 3.2 决策资产化

高价值决策（如商业模式选择、目标客户定位、产品线优先级）自动归入：
- `A-manyige/常用/决策追踪日志/重大决策索引.md`
- 与 `docs/project-wisdom-compounder-v1.1.md` 联动，成为"决策树"的一部分

## 四、与 AGENTS.md 的绑定

本协议已固化为 `AGENTS.md` **内容输出路由规则第五条**：
> **当 AI 呈现 2 个及以上选项时，必须编号；用户回复时只需写编号+反馈；每次编号决策后必须写入追踪日志。**

违反即视为 **命名规范违规** 同级别的规则失效。

## 五、快速参考卡

| 场景 | AI 动作 | 用户动作 | 资产产出 |
|------|---------|----------|----------|
| 多方案选择 | 强制编号 ①②③ | 回复 "② + 反馈" | 决策追踪日志条目 |
| 多项待办确认 | 强制编号 ①②③ | 回复 "①③先做" | 待办索引更新 |
| 多文件处理 | 强制编号 ①②③ | 回复 "② 跳过，先做①" | 处理记录日志 |
| 复杂决策树 | 编号 + 简要对比矩阵 | 回复 "②，但用 A 的子方案" | 重大决策索引 |

---

*编号不是为了形式主义，是为了让决策像子弹一样快、像档案一样可追踪。*

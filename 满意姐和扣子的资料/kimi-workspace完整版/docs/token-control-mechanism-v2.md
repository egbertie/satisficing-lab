## 一、历史机制回顾

### 2026-03-21 部署（初代止血）
- `token-budget-enforcer`：三级预算 (30%警告 / 50%限制 / 20%熔断) + 熔断机制
- `token-management-satisficing`：心跳 L1-L4 动态档位
- 档位与心跳间隔绑定：L1(30min) → L2(45min) → L3(60min) → L4(120min)

### 存在的问题
1. **预算基数固定为 20万 Token**，无法适配周/月动态周期
2. **只监控"当前会话"**，无全局周期视图
3. **用户校准值（30%、38%）只是记录，没有触发任何机制动作**
4. **缺少与任务进度/价值的联动**——消耗快不一定危险，如果产出高；消耗慢也不一定安全，如果产出低

## 二、V2.0 核心公式（动态双轴管控）

### 2.1 周期进度双轴模型

**X轴：时间进度** = 已过去天数 / 周期总天数
**Y轴：Token进度** = 已消耗 Token / 周期预算

**动态偏差 Δ = Y - X**

| Δ 区间 | 健康状态 | 动作 |
|--------|----------|------|
| Δ ≤ 0 | 🟢 优秀 | 消耗与进度匹配或超前，正常执行 |
| 0 < Δ ≤ 10% | 🟡 注意 | 略高于时间进度，输出端提醒即可 |
| 10% < Δ ≤ 20% | 🟠 观察 | 消耗明显超前，保持工作正常，追加状态告知 |
| Δ > 20% | 🔴 警惕 | 消耗严重超前，与用户协商是否进入静默/精简模式 |

### 2.2 效益校准因子（双经济要求）

**价值密度 V = 本周外部价值产出数 / 本周 Token 消耗（千Token）**

- 外部价值产出：可直接给用户使用的报告、代码、决策工具
- V ≥ 2：高价值，Token 预算可上浮 10%
- V 在 1-2：正常
- V < 1：低价值，下周期预算下调 10%

### 2.3 综合档位判定

最终档位 = MAX(基于 Δ 的档位, 基于绝对剩余量的档位)

**基于绝对剩余量（备用安全网）**:
- > 30%：L1
- 20-30%：L2（提醒观察，不限制核心工作）
- 10-20%：L3（主动告知用户，协商裁剪非必要任务）
- < 10%：L4（建议熔断/静默，由用户决定是否执行）

## 2.4 阶段化策略调整（2026-04-10 更新）

> **核心原则**：Token 进度是「体温计」，不是「手铐」。我们要知道温度，但不应该因为发烧就停止呼吸。

**基建阶段（已完成）**：
- 高耗能、重机制建设 → Token 消耗快是正常现象
- 此前很多方法未精细化运用，导致额外消耗

**研究/产品阶段（当前）**：
- 重心转向项目研究和产品交付
- **Token 控制从「硬约束」转为「知情管理」**
- 该用则用，不必过度吝啬
- 只需做到：① 知道进度 ② 合理调整 ③ 与用户同步状态
- **禁止将 L2/L3 自动变成工作阻断器**

**L2（Δ 10-20%）执行规则**：
- 输出端追加一句 Token 状态提示即可
- **不减少工具调用、不降低模型能力、不跳过必要分析**

**L3（Δ 20-30%）执行规则**：
- 在执行高耗能任务前向用户确认一次
- 提供「正常执行 / 适度精简 / 延后处理」三个选项
- **默认选项仍是「正常执行」**

**L4（<10%）执行规则**：
- 作为建议提出，由用户最终拍板是否进入静默
- 若用户未回复，仍可处理明确的 P0 紧急事项

## 四、操作规则（立即生效）

### 4.1 每周校准协议
**Token 周期：每周三 12:00 至下周三 12:00（7天为一个周期）**

**每周三 12:00 后首次交互时**（或用户主动触发）：
1. 用户报告上周 Token 消耗百分比
2. 系统新周期起点对齐周三 12:00，重新计算 Δ = 消耗% - 时间进度%
3. 更新 `token-weekly-monitor.json`
4. 自动调整本周档位和心跳频率

### 4.2 每日自检（无需用户参与）
- 检查 `token-zero-tracker.json`（由 `token-tracker-zero.py` 自动更新）
- 如果 Δ > 15% 且当日为周三后：发出内部提醒（不主动打扰用户，除非即将熔断）
- 如果进入 L3/L4：在下一次交互时主动告知

### 4.3 低存量状态恢复
- L4（Δ > 20% 或 剩余 < 10%）：
  - 在下一次交互时**告知用户**当前状态
  - 提供选项：① 正常继续 ② 进入轻度精简 ③ 进入静默/熔断
  - **默认由用户拍板，不自动强制打断工作流**
  - 如果用户明确说 "解除限制" 或新周期开始，则完全恢复

## 五、与 Kimi Code 的联动（已修正）

**策略**：评估 `kimi-code` 通道是否能**同样解决问题**。若能，则主动使用；若不能，则直接用更合适通道。

**关键原则**：
- **与 Token 进度/黄区状态完全无关**
- 9 折优惠是能力匹配合适时顺便享受的，不是决策依据
- 决不因为 Token 紧张而强行用不合适的通道凑合
- 决不因为 Token 充裕就故意回避更合适的低价通道

**当前限制**：OpenClaw 的模型路由由系统配置决定，我们暂无法自动切换通道。但可以在任务开始前主动评估并向用户说明：
> "这个任务用 kimi-code 同样可以完成，是否切换？"

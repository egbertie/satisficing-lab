## 二、完善方案（三层备份架构）

### 2.1 第一层：本地安全备份（每日必保）

**目标**: 即使所有外部服务失效，本地仍有可恢复的完整备份

**规则**:
1. 备份文件不再放在 `/tmp`（重启易失），而是 `workspace/backups/`
2. 保留最近 **7 天**的本地完整备份
3. 超过 7 天的本地备份自动删除（释放空间）
4. 备份前执行 **排除规则**，控制体积

**排除规则**（从源头上控制 710MB → 目标 < 400MB）:
```
EXCLUDE_DIRS:
  - __pycache__/
  - .git/           (GitHub 已托管)
  - node_modules/
  - OLD-ARCHIVE-2026/  (历史归档，单独管理)
  - archive/md_conversions/  (可重建的中间产物)
  - memory/claw-space-diagnosis-*.md  (可重建)
  - downloads/  (临时下载)
  - .openclaw/extensions/*/node_modules/  (依赖可重装)
```

**脚本**: `scripts/daily_local_backup.sh`

### 2.2 第二层：Git 核心资产备份（实时）

**目标**: 代码、文档、配置等核心资产通过 Git 持续同步

**规则**:
1. 每日自动 `git commit`（已有，今日已执行）
2. 每周自动 `git push` 到 GitHub（已配置 cron：周日 03:00）
3. Git 是"增量备份"，不占用额外空间，且不依赖飞书授权

### 2.3 第三层：飞书 Drive 云备份（条件触发）

**目标**: 每周一次完整归档上传到云端

**规则**:
1. **不再每日上传**（避免授权问题 + 节省空间）
2. 改为 **每周日 21:00** 在 `sessionTarget=main` 下触发（用户通常在线，OAuth 可用）
3. 上传前如果体积 > 500MB，自动分卷压缩（每卷 400MB）
4. 上传失败时，告警但不阻塞，本地备份仍然安全

## 七、内容完整性校验机制（新增）

> **来源**: 用户明确反馈 —— "文件大小和题目都对，但里面的内容不完整"，必须将内容完整性纳入备份校验体系。

**核心原则**：元数据校验（文件名、大小、时间戳）≠ 内容完整性校验。

### 7.1 校验维度矩阵

| 校验层级 | 检查项 | 方法 | 失败判定 | 处理方式 |
|----------|--------|------|----------|----------|
| **L1: 元数据** | 文件名、大小、修改时间 | `ls -lh` / `stat` | 文件名不符 / 大小为 0 / 时间异常 | 立即标记为失败，不进入 L2 |
| **L2: 结构完整性** | tar.gz 压缩包可正常解压 | `tar -tzf backup.tar.gz > /dev/null` | 解压报错 / 文件列表为空 / CRC 错误 | 立即重跑备份 |
| **L3: 关键文件存在性** | 核心目录/文件确实在包内 | `tar -tzf` 后 grep 关键路径 | 缺少 `AGENTS.md` / `SOUL.md` / `daily_asset_runner.py` / `A-manyige/` 等关键资产 | 立即重跑备份 |
| **L4: 内容抽查** | 随机抽取 3-5 个文件，校验首末 1KB 可读 | `tar -xzf --to-stdout <file> | head -c 1024` / `tail` | 文件内容截断 / 全为乱码 / 大小异常 | 告警并排查源文件 |
| **L5: 哈希一致性** | 与历史备份或源文件做 SHA-256 对比 | `sha256sum` 对比 | 同名关键文件哈希突变且无合理解释 | 人工复核 |

### 7.2 自动化脚本要求

`scripts/daily_local_backup.sh` 和 `weekly_cloud_backup.sh` 在生成备份后必须执行：

```bash
# 结构完整性测试
tar -tzf "${BACKUP_FILE}" >/dev/null 2>&1 || { echo "ERROR: 备份包结构损坏"; exit 1; }

# 关键文件存在性测试（示例）
for critical_file in "AGENTS.md" "SOUL.md" "daily_asset_runner.py"; do
  if ! tar -tzf "${BACKUP_FILE}" | grep -q "${critical_file}$"; then
    echo "ERROR: 缺少关键文件 ${critical_file}"; exit 1
  fi
done

# 内容抽查（随机抽取 3 个非二进制文件）
# ... (写入验证逻辑)
```

### 7.3 上传后云端校验

飞书 Drive 上传完成后：
1. 从飞书 Drive 读取文件元数据（大小），与本地对比
2. 大小偏差 > 1% → 判定上传不完整，重试上传
3. 每周一次从飞书 Drive 下载最新备份包，执行 L2-L4 校验

### 7.4 告警与记录

- 任何 L2/L3 失败 → **P0 告警**，立即重跑备份
- L4/L5 异常 → **P1 告警**，当日人工复核并记录到 `memory/backup-integrity-audit-YYYY-MM-DD.md`
- 所有校验结果写入 `memory/weekly-backup-status.json`

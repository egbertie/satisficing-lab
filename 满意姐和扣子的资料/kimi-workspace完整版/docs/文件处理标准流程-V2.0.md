## 一、流程核心原则

### 1.1 零遗漏原则
- 所有要求必须实现或提供替代方案
- 未实现的必须有简化方案
- 简化方案必须有记录

### 1.2 条件记录原则
- 完整方案所需条件必须专门记录
- 避免信息散落在各处
- 统一存放，便于后续迭代

### 1.3 诚实报告原则
- 明确区分"完整实现"和"简化实现"
- 不隐瞒技术债务
- 清晰标注依赖条件

### 阶段0.3 详细：重复文件检测（⭐新增）

**适用范围**: docx文档（其他格式暂不涉及）

**检测方法**:
1. **文件名相似度检查**: 列出所有docx文件，按名称排序
2. **文件大小对比**: 相同文件名+相同大小 = 完全重复
3. **时间戳对比**: 选择最新版本处理
4. **版本号识别**: `_1_`, `_2_`, `_V1_` 等版本标识

**处理策略**:

| 情况 | 判断标准 | 处理方式 | 用户告知 |
|------|----------|----------|----------|
| **完全重复** | 文件名相同 + 文件大小相同 | 只处理最新版本 | ✅ 告知检测到重复，说明处理哪个版本 |
| **版本迭代** | 文件名相似 + 文件大小不同 | 处理最新版本，对比增量内容 | ✅ 告知版本差异，说明新增内容 |
| **内容重叠** | 部分章节相同 | 处理最新版本，标注重叠部分 | ✅ 告知重叠情况，避免重复分析 |
| **无重复** | 无相似文件 | 正常处理 | ✅ 告知无重复 |

**避免重复劳动**:
- 已处理的重复文件不再处理
- 保留处理记录，说明处理的是哪个版本

**避免漏掉信息**:
- 版本迭代时，对比新旧版本的差异
- 提取增量内容，补充到已有分析

**记录方式**:
```
重复文件检测报告:
- 文件A: 发现X个版本
- 处理方式: 处理最新版(V3)，跳过V1/V2
- 版本差异: V3比V2新增了...内容
```

### 阶段0.3 优化：批量重复检测（⭐重要更新）

**问题**: 每个文件单独检测重复，36个文件要做36次检测，严重浪费资源

**优化方案**:
1. **首次检测（第1个文件）**: 批量检测所有文件，生成索引 `.file_duplicates_index.json`
2. **后续文件（第2-N个）**: 直接读取索引，0延迟

**优化效果**:
| 指标 | 优化前 | 优化后 | 节省 |
|------|--------|--------|------|
| 检测次数 | 36次 | 1次 | 97% |
| 检测时间 | ~18分钟 | ~5秒 | 99.5% |
| 实际需处理 | 36个 | 21个 | 42% |

**执行脚本**:
```python
# 第一个文件执行
python3 batch_duplicate_check.py
# 生成: .file_duplicates_index.json

# 后续文件直接读取索引
with open('.file_duplicates_index.json') as f:
    index = json.load(f)
# 0延迟获取重复信息
```

**固化位置**: `AGENTS.md` + `docs/文件处理标准流程-V2.0.md`

**动作**:

2. 提取关键Q&A或需求点
3. 识别技术栈和实施要求
4. 分析依赖条件和难点

**输出**:

### 阶段3：能力评估

**目标**: 评估哪些可以完整实现，哪些需要简化

**评估矩阵**:

| 需求项 | 当前能力 | 所需条件 | 可实现性 | 决策 |
|--------|----------|----------|----------|------|
| 功能A | 已具备 | 无 | 100% | 完整实现 |
| 功能B | 部分具备 | 数据/模型 | 60% | 简化实现 |
| 功能C | 不具备 | 大量资源 | 20% | 简化实现+条件记录 |

**输出**:
- 可实现性评估表
- 简化方案设计
- 条件记录清单

### 阶段4：实际实施（或简化方案）

#### 4.1 完整实现路径

适用于：技术栈已具备，无需外部依赖

**动作**:
1. 编写实际可运行代码
2. 实现核心功能
3. 完成功能测试
4. 生成使用文档

**输出**:
- 可运行代码
- 测试通过报告
- 使用说明

#### 4.2 简化实现路径（新增）

适用于：技术栈不具备，需要外部条件

**简化原则**:
1. **功能等价**: 简化版应实现核心功能，只是实现方式简化
2. **可运行**: 简化版必须是实际可运行的
3. **可迭代**: 简化版必须能平滑升级到完整版

**简化策略**:

| 场景 | 简化策略 | 示例 |
|------|----------|------|
| 需要AI模型 | 用规则/关键词替代 | BERT分类 → 关键词匹配 |
| 需要大数据 | 用少量样本统计 | 神经网络 → 模式匹配 |
| 需要复杂算法 | 用启发式规则 | 因果推断 → 相关性分析 |
| 需要专家知识 | 用通用模板 | 专业诊断 → 检查清单 |

**输出**:
- 简化版可运行代码
- 与完整版的对比说明
- 升级路径设计

## 三、不同类型文件的处理策略

### 类型A：案例分析类文件

**特点**: 以经验总结、教训提炼为主

**处理重点**:
- 深度洞察 > 实施
- 提取可复用的决策框架
- 生成知识资产

**简化方案场景**: 较少（主要是分析深度）

### 类型B：技术方案/系统设计类文件（当前类型）

**特点**: 以技术实现、系统架构为主

**处理重点**:
- 实际实施 > 深度洞察
- 必须提供可运行代码
- 简化方案实施 + 条件记录

**简化方案场景**: 常见
- AI/ML功能 → 规则/统计替代
- 复杂算法 → 启发式规则
- 大数据依赖 → 小规模样本

### 类型C：流程/方法论类文件

**特点**: 以流程设计、方法论为主

**处理重点**:
- 流程固化 > 技术实现
- 生成可执行的工作流
- 检查清单化

**简化方案场景**: 中等
- 自动化流程 → 半自动化
- 智能推荐 → 模板推荐

## 四、简化方案设计指南

### 4.1 何时设计简化方案

**必须设计简化方案**:
- 需要训练AI模型（无数据/算力）
- 需要复杂算法（无实现能力）
- 需要外部API（无访问权限）
- 需要专家知识（无专家资源）

**可以完整实现**:
- 基于规则的逻辑
- 本地可运行的代码
- 已有技术栈支持

### 4.2 简化方案设计原则

**原则1: 核心功能保留**
- 识别核心功能 vs 增强功能
- 简化版必须保留核心功能

**原则2: 实现方式降级**
- AI模型 → 规则引擎
- 深度学习 → 模式匹配
- 大数据统计 → 小样本归纳

**原则3: 可验证性**
- 简化版必须可测试
- 必须有明确的输入输出
- 必须有成功标准

**原则4: 可升级性**
- 简化版架构支持平滑升级
- 数据格式与完整版兼容
- 接口设计与完整版一致

### 4.3 简化方案模板

```python
# 功能: XXXX (简化版)
# 完整方案: 使用{技术}实现{功能}
# 简化方案: 使用{替代技术}实现{核心功能}
# 升级条件: 
#   - 条件1: {详细说明}
#   - 条件2: {详细说明}
# 预计升级时间: {X个月}

def function_simplified(input):
    """
    简化版实现
    
    限制:
    - 限制1
    - 限制2
    
    与完整版的差异:
    - 差异1
    - 差异2
    """
    # 简化实现逻辑
    pass

# TODO: 升级到完整版
# 当{条件}满足时，替换为以下实现:
# def function_full(input):
#     ...
```

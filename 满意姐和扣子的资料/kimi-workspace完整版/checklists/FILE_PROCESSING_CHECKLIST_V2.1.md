## 三、处理后验收（闭环关键）

### 3.1 标准7步法
| 验收项 | 验收内容 | 验收标准 |
|--------|----------|----------|
| **V1** | 内容识别完整 | 核心要点无遗漏 |
| **V2** | 方案/措施识别 | 明确标注: 已实施/部分实施/未实施/无需实施 |
| **V3** | 交付物生成 | 报告+记忆更新双确认 |
| **V4** | 阶段0-2完成 | 前置/提取/洞察完成 |
| **V5** | **【V2.1】补实施** | **自动执行A，无需询问，100%实施** |
| **V6** | 阶段4-6完成 | 条件/整合/登记完成 |
| **V7** | 用户确认 | 用户明确认可或提出修正 |

**禁止**: 未经V1-V7全部通过，宣称"完成"

### 3.2 方案/措施状态标签（强制使用）
| 标签 | 含义 | 后续动作 |
|------|------|----------|
| 🟢 | 已实施 + 已验收 | 记录即可 |
| 🟡 | 部分实施 / 待设计 | **自动执行A（补实施）** |
| 🔴 | 未实施 | **自动执行A（补实施）** |
| ⚪ | 无需实施 | 记录理由 |

## 四、【V2.1】阶段3.5: 补实施缺失措施（必然环节 - 自动执行）

### 4.1 触发条件（满足任一即触发）
- [ ] 检测到🔴"未实施"的措施
- [ ] 检测到🟡"部分实施"的措施

### 4.2 执行标准（V2.1铁律）
**禁止询问！直接执行！**

**执行流程**:
1. 检测到🔴🟡 → 立即进入补实施流程
2. 识别所有缺失措施
3. 逐一补实施（创建文件/配置/脚本）
4. 每个措施必须有可运行的交付物
5. 蓝军监督实施过程
6. 代码验证可运行
7. 生成补实施报告
8. **报告结果**（不是请示）

### 4.3 禁止行为（违者蓝军熔断）
❌ **严禁**: 问"选择A还是B"  
❌ **严禁**: "需要补实施，是否执行？"  
❌ **严禁**: "检测到缺失，您看怎么办？"  
❌ **严禁**: 任何让用户"选择"或"确认"的表述

### 4.4 正确表述（V2.1标准）
✅ **正确**: "检测到3个未实施组件，立即补实施"  
✅ **正确**: "补实施完成，3/3 100%，代码已验证"  
✅ **正确**: "文件X真正闭环，等待用户验收"

### 4.5 用户权利
- ✅ **打断权**: 用户可在补实施过程中打断
- ✅ **否决权**: 用户可在闭环后提出修正
- ❌ **前置选择权**: 用户不能在执行前"选择A或B"

## 八、记忆固化

**内化原则（V2.1）**:
1. **检测→自动**: 发现🔴🟡，**不询问**，直接执行A
2. **禁止选择**: 不给用户"A或B"的选择权
3. **报告结果**: 补实施完成后报告，不是请示
4. **用户打断**: 用户可在执行中打断，但不能前置选择

**下次处理文件时**:
- 识别内容后→自动检查实施状态
- 发现🔴🟡→**自动执行A**（不询问！）
- 补实施完成→生成报告→等待验收
- **严禁**: "选择A还是B" / "是否执行" / "您看怎么办"

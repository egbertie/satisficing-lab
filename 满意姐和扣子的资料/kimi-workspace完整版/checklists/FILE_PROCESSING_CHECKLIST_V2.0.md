## 三、处理后验收（闭环关键）

### 3.1 标准7步法
| 验收项 | 验收内容 | 验收标准 |
|--------|----------|----------|
| **V1** | 内容识别完整 | 核心要点无遗漏 |
| **V2** | 方案/措施识别 | 明确标注: 已实施/部分实施/未实施/无需实施 |
| **V3** | 交付物生成 | 报告+记忆更新双确认 |
| **V4** | 阶段0-2完成 | 前置/提取/洞察完成 |
| **V5** | **【新增】补实施** | **见3.5节，必须100%实施** |
| **V6** | 阶段4-6完成 | 条件/整合/登记完成 |
| **V7** | 用户确认 | 用户明确认可或提出修正 |

**禁止**: 未经V1-V7全部通过，宣称"完成"

### 3.2 方案/措施状态标签（强制使用）
| 标签 | 含义 | 后续动作 |
|------|------|----------|
| 🟢 | 已实施 + 已验收 | 记录即可 |
| 🟡 | 部分实施 / 待设计 | **必须补实施** |
| 🔴 | 未实施 | **必须补实施** |
| ⚪ | 无需实施 | 记录理由 |

## 四、【新增】阶段3.5: 补实施缺失措施（必然环节）

### 4.1 触发条件（满足任一即触发）
- [ ] 检测到🔴"未实施"的措施
- [ ] 检测到🟡"部分实施"的措施
- [ ] 用户明确要求补实施

### 4.2 执行标准（强制）
**参考文件7标准**:
1. 识别所有缺失措施
2. 逐一补实施（创建文件/配置/脚本）
3. 每个措施必须有可运行的交付物
4. 蓝军监督实施过程
5. 生成补实施报告
6. 用户验收确认

### 4.3 禁止行为
❌ **严禁**: 检测到缺失措施后，不补实施就宣称"识别完成"
❌ **严禁**: 用"待后续实施"等模糊表述掩盖未实施状态
❌ **严禁**: 未经用户验收，自行判定"闭环完成"

### 4.4 补实施报告模板
```markdown
## 补实施报告
- 原文件: XXX.docx
- 缺失措施: N个
- 补实施完成: N个
- 实施完成度: 100%
- 交付物清单: ...
- 蓝军验收: ✅
- 用户验收: ⏳ 等待确认
```

## 六、防错机制

### 6.1 语言规范（强制）
| 禁用表达 | 正确表达 | 后果（违规） |
|----------|----------|--------------|
| "已完成" | "已识别，**实施中/待补实施**" | 蓝军熔断 |
| "方案已提取" | "方案已提取，**实施状态：X/Y，需补实施Z个**" | 蓝军警告 |
| "处理完成" | "**补实施完成**，等待验收" | 蓝军阻断 |

### 6.2 自动检查脚本
每次宣称"完成"前，自动执行：
```bash
python3 check_completion.py --file $FILE_ID --require-100-implementation
```

### 6.3 蓝军熔断升级
- 首次违规: 警告 + 强制整改
- 二次违规: 暂停处理 + 回溯检查
- 三次违规: 锁定系统 + 用户介入

## 八、记忆固化

**内化原则**:
1. **识别≠完成**: 文档识别后，必须评估实施状态
2. **缺失必补**: 任何🔴🟡状态，必须补实施到🟢
3. **用户验收**: 补实施后，必须获得用户明确确认
4. **蓝军监督**: 全流程蓝军Skeptor-7实时监督

**下次处理文件时**:
- 识别内容后→立即检查实施状态
- 发现缺失→自动进入补实施流程
- 补实施完成→生成报告→用户验收
- 禁止像过去一样"识别完就算完成"

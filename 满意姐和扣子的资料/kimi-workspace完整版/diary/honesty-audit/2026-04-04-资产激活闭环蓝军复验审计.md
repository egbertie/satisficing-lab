## 二、逐项审计

### P0-1: 产出验证 — 表演性严谨的风险（🟡 中上 → 🟡 中下）

**蓝军指控 1: [语言腐败 + 锚定效应]**

`daily_asset_runner.py` 中 `ASSET_VALIDATION` 对 `intelligence_collection_system.py` 的规则：
```python
'required_patterns': [r'完成', r'\d+', r'条'],
```

**问题**: `r'\d+'` 是一个**几乎恒真**的模式。它能匹配输出中的任何数字：日期(`2026-04-04`)、PID(`149195`)、版本号(`4.0`)、甚至内存数值(`692MB` 中的 `692`)。这意味着这条"必须模式"在绝大多数情况下会**真空满足**，制造"验证通过了"的假象。

这不是产出验证，这是**验证剧场**（Validation Theater）—— 给出一个看起来像高标准的检查清单，但清单上的关键项实际上无法拒绝任何输出。

**后果**: 如果 `intelligence_collection_system.py` 的输出是一堆无意义的报错信息，但只要里面出现了任何数字，就会被判定为"有效产出"，从而混入 `activated` 列表。

**整改建议**: 
- 将 `r'\d+'` 替换为真正反映业务产出的模式，例如 `r'采集完成.*\d+条'` 或 `r'数据源:\s*\w+.*状态:\s*成功'`
- 为每个关键资产建立最小 JSON/Markdown 结构检查，而非仅做正则匹配

### P0-2: 内存测量修复 — 因果混淆与新脆弱性（🟡 中上）

**蓝军指控 2: [因果混淆 + 幸存者偏差 + 假设漏洞]**

Builder 的汇报措辞是：
> "内存基线超标根因定位...修复后 692MB（⚠️ WARNING，不再超标）"

**认知审计**: OpenClaw 进程的内存消耗**并没有减少哪怕 1MB**。减少的只是测量对象。把这句话说成"修复了内存超标"，是一种**因果混淆**（causal confusion）—— 仿佛做了什么让内存变小了，实际上只是换了把尺子。

**更深层的问题 — 未被测试的 fallback**:
```python
if gateway_mem_mb == 0:
    # Fallback: 当前进程内存
    gateway_mem_mb = psutil.Process().memory_info().rss / 1024 / 1024
```

这是一个典型的**幸存者偏差**场景：builder 只验证了 `openclaw-gateway` 进程存在时的"成功路径"（当前确实测出了 704MB），但从未测试 `gateway_mem_mb == 0` 的 fallback 路径。

如果未来 `openclaw-gateway` 进程更名（例如升级为 `openclaw-gateway-v2`）、以不同命令启动、或临时未运行时，该代码会**静默回退**到测量 baseline-checker 自身（一个轻量级 Python 脚本，约 50-100MB）。这时基线报告会显示一个漂亮的 "200MB PASS"，而真正的 gateway 可能正在泄漏内存。这是一个**假设漏洞**（假设进程名永远不变）与**虚假安全感**的致命组合。

**整改建议**:
- 当 `gateway_mem_mb == 0` 时，不应 fallback 到自身，而应当记录 `None` 并触发 `SKIP` 或 `ALERT`
- 或者支持按多个候选进程名匹配（`openclaw-gateway`, `node openclaw-gateway`, `gateway`）

### P1-3: 文档引用清理 — 确认偏误与搜索范围不足（🟡 中等）

**蓝军指控 3: [确认偏误 + 样本偏差]**

Builder 使用的验证命令：
```bash
grep -rnE "python3[[:space:]]+(skill_conditioning|...)" /root/.openclaw/workspace/docs/ /root/.openclaw/workspace/memory/
```

**问题 1: 确认偏误**  
搜索模式精准定位于 "`python3 xxx.py`" 格式的**shell命令引用**。这是一种典型的确认偏误：builder 心里预设了"危险引用=文档里的运行命令"，于是只搜这个，搜不到就算"清理干净"。

但是，旧版本文件的引用形式远不止 shell 命令：
- Python 代码中的 `import skill_conditioning`
- 配置文件中的模块路径
- Markdown 中的超链接或文件说明
- Skill 元数据或 `SKILL.md` 中的示例
- JSON 记录中的 `script_name` 字段

**问题 2: 样本偏差（搜索范围过窄）**  
搜索范围被限制在 `docs/` 和 `memory/`，而忽略了：
- `skills/*/README.md` 或 `SKILL.md`
- `HEARTBEAT.md`、`TASK_MASTER.md`、`AGENTS.md`
- `.json` 配置文件或统计元数据
- 已生成的报告文件中的截图/引用

**实际结果**: 经蓝军独立扫描，目前 workspace 根目录下的 `.py` 文件确实没有引用旧版本（`grep` 无结果），但这并非 builder 主动验证的结论，而是幸运的结果。如果某个 `.py` 或 `.md` 中仍有引用，builder 的检查方法**无法发现**。

**整改建议**:
- 建立一个自动化的 "deprecated-reference-scan.py"，扫描整个 workspace（含 `.py`, `.md`, `.json`, `.sh`）中指向 `archive/deprecated/` 内文件名的任何引用
- 将该扫描纳入 `daily_asset_runner.py` 的每日检查池

# 模块5：Token经济学与效益经济学

> **核心命题**: 每个行动必须同时回答——Token上可持续吗？效益上值得做吗？
> **血液化资产**: AGENTS.md双经济条款、Token监控体系、后台自动化治理
> **适用对象**: AI协作者、团队负责人、资源管理者

---

## 一、核心理念

### 1.1 双经济的定义

```
Token经济学 × 效益经济学 = 双经济要求

Token经济学:
  ├─ 投入在预算内
  ├─ 优先本地处理（Local ≥ 70%）
  ├─ 单次任务工具调用>5次时内心独白审计
  └─ 任何行动必须回答: Token上是否可持续？

效益经济学:
  ├─ 产出有直接外部价值
  ├─ 创始人5分钟内可用
  ├─ 禁止向内集邮
  └─ 任何行动必须回答: 效益上是否值得做？
```

### 1.2 为什么双经济是最高红线？

```
没有双经济的组织:
  ├─ Token无节制消耗 → 周期性枯竭 → 工作中断
  ├─ 效益无法验证 → 大量半成品 → 创始人无法使用
  └─ 向内集邮 → 整理 skill/产出文档 → 无外部价值

有双经济的组织:
  ├─ Token可控 → 可持续运营 → 长期稳定
  ├─ 效益可验证 → 每个产出可用 → 创始人信任
  └─ 向外导向 → 每行动服务外部 → 价值积累
```

## 三、操作步骤

### Step 1: 建立Token监控体系

**Token预算分配**:
```
总Token预算（每周周期）:
  ├─ 主AI日常运营: 50-60%
  ├─ 蓝军审计/扫描: 20-30%
  ├─ 后台自动化: 10-15%（需严格治理）
  ├─ 应急储备: 5-10%
  └─ 互评/审计: 各自50%
```

**五级光谱节流**:
```
L0 正常模式: Token>50%
  ├─ 全部功能开放
  └─ 正常频率运行

L1 高耗能模式: Token 30-50%
  ├─ 优先级放行
  └─ 60min心跳

L2 降频模式: Token 20-30%
  ├─ 禁止子代理
  └─ 降频33%

L3 半静默: Token 10-20%
  ├─ 仅P0/P1
  └─ 降频50%

L4 深度静默: Token<10%
  ├─ 仅P0紧急
  └─ 降频75%
```

**熔断机制**:
```
□ Token超预算200% → 自动暂停
□ 连续3次相似输出（>80%）→ 强制退出
□ 置信度<0.5论断>3个 → 怀疑模式
□ 磁盘使用率≥85% → 系统清理
```

### Step 2: 建立效益验证机制

**创始人5分钟检验法**:
```
检验标准:
  一个焦虑的创始人能不能在5分钟内看懂怎么用？
  能不能直接嵌入一次咨询服务流程？

检验流程:
  1. 产出完成后，创始人视角模拟
  2. 计时5分钟阅读
  3. 5分钟内看懂 → 通过
  4. 5分钟内不懂 → 半成品，退回整改
  5. 整改后复测
```

**效益验证清单**:
```
□ 产出是否可直接使用？（不是"参考"）
□ 创始人5分钟内能看懂吗？
□ 有外部价值吗？（不是"整理"）
□ 可以嵌入咨询流程吗？
□ 有具体行动建议吗？
□ 有验证方法吗？（怎么知道有效？）
□ 有成本说明吗？（Token/时间/人力）
```

### Step 3: 后台自动化任务的双经济治理

**三定律**:
```
定律1: 触发定律
  ├─ 每个后台任务必须有明确触发条件
  ├─ 禁止"一直跑着"的僵尸任务
  └─ 触发条件: 时间/cron/事件/用户指令

定律2: 熔断定律
  ├─ 每个后台任务必须有熔断条件
  ├─ Token超预算 → 自动暂停
  └─ 连续失败>3次 → 自动告警

定律3: 注册审查定律
  ├─ 每个后台任务必须注册到任务总表
  ├─ 注册信息: 任务名/触发条件/预估Token/负责人
  └─ 未经注册 → 禁止运行
```

**治理流程**:
```
步骤1: 盘点所有后台任务
  ├─ 列出所有cron任务
  ├─ 列出所有自动化脚本
  └─ 列出所有常驻进程

步骤2: 逐一审计
  ├─ 触发条件合理吗？
  ├─ Token消耗可接受吗？
  ├─ 产出有外部价值吗？
  └─ 可以本地处理吗？

步骤3: 分类处理
  ├─ 保留: 触发合理+Token可控+有价值
  ├─ 优化: 触发过频或Token过高
  ├─ 暂停: 触发不明或价值不清
  └─ 删除: 僵尸任务或重复任务

步骤4: 建立注册表
  ├─ 所有保留任务注册到总表
  ├─ 每周Review注册表
  └─ 新增任务必须注册后运行
```

### Step 4: 费用红线管理

**费用红线**:
```
原则: 免费优先

禁止自行执行:
  □ 付费API调用
  □ 高级功能开通/订阅
  □ 增值服务购买
  □ 超出免费额度的批量操作

执行标准:
  1. 行动前明确告知可能产生的费用项目
  2. 等待用户逐项确认
  3. 确认后执行

例外: 明确已知免费的读操作（搜索、列表查询、信息获取）
```

## 六、常见误区

| 误区 | 表现 | 后果 | 纠正 |
|:-----|:-----|:-----|:-----|
| Token=无限 | "用到哪算哪" | 周期性枯竭 | 建立预算分配 |
| 效益无法验证 | "做完了就行" | 大量半成品 | 5分钟检验法 |
| 后台任务=免费 | 不监控后台消耗 | Token黑洞 | 注册+审计+治理 |
| 付费=方便 | 自行开通API | 费用失控 | 逐项人工确认 |
| 远程>本地 | 优先API调用 | Token消耗快 | Local ≥ 70% |
| 无熔断机制 | 一直运行到崩溃 | 系统不稳定 | 五级光谱节流 |
| 不区分剩余/消耗 | "还剩30%"→实际是消耗30% | 误判档位 | 明确区分 |
| 向内集邮 | "整理skill/文档" | 无外部价值 | 每个行动问"效益值得吗？" |
| 忽视效益 | "Token省了就行" | 产出不可用 | 双经济必须同时满足 |
| 不做预测 | 不知道下周够不够用 | 被动应对 | 建立预测模型 |

## 七、真实案例

### 案例1: "824万Token黑洞"——后台自动化的发现与治理

**背景**: 2026年4月11日，发现后台自动化任务消耗约824万Token（占全量45.7%）。

**发现问题**:
```
蓝军审计:
[蓝军审计]
风险等级: 🔴高危

指控:
1. [Token经济黑洞] 后台自动化消耗未监控
   - 证据: 824万Token，占全量45.7%
   - 影响: 主AI可用Token被挤压

2. [效益不明] 部分后台任务产出价值不清
   - 证据: 4个cron任务触发条件不明
   - 影响: 可能在做无价值的事
```

**治理措施**:
1. 增加五级光谱节流
2. 禁用冗余cron `token-tracker-zero-001`
3. 4个尾项拆解为最小单元
4. 建立后台任务注册审查制度

**结果**: 后台消耗从45.7%降至可控范围。

### 案例2: "Token监控bug低估38倍"——数字审计的教训

**背景**: `token-tracker-zero.py`日期错算bug，真实消耗被低估38倍。

**蓝军发现**:
- 今日"预估25万"→实际3968万
- 追问根因：日期错算
- 证据：对比脚本逻辑与实际日志

**整改**:
- 修复bug
- 重新校准历史数据
- 建立数字审计机制

**教训**: 没有蓝军的数字审计，Token黑洞可能持续数周。

# 第9章：双经济治理——从概念到血液

## 9.1 诞生：两个简单问题的力量

双经济治理不是从一本管理学教科书中抄来的，而是从两次惨痛的教训中长出来的。

**第一次教训：Token余量4%（2026年3月16日）。**

当时系统几乎停摆，我们被迫禁用14个非必要Cron任务，进入"非必要不使用"的紧急状态。事后复盘时，Egbertie问了一个问题："我们之前为什么没有做Token预算管理？"

答案很尴尬：因为我们从未把Token当作"资源"来管理。我们一直把它当作"无限供应的电力"——插上就用，从不看电表。

**第二次教训：47系统评估的141小时工作量（2026年3月27日）。**

蓝军完成了47个系统的评估，发现大量系统只是"文档壳子"——有文档、有代码、有配置，但从未被调用过。Egbertie又问了一个问题："我们产出这么多文档，哪些真正加速了商业化？"

答案同样尴尬：大部分没有。

**双经济的诞生**：
- **Token经济学**：投入在预算内，优先本地处理（Local ≥ 70%）。任何行动必须回答：Token上是否可持续？
- **效益经济学**：产出有直接外部价值，创始人5分钟内可用。任何行动必须回答：效益上是否值得做？

这两个问题，成为满意解研究所所有决策的"默认前置条件"。

## 9.2 三个阶段：从概念到默认化

双经济的落地经历了三个阶段。

**阶段一：概念期（2026年3月底-4月初）。**

双经济作为概念被提出，写入SOUL.md和AGENTS.md。但此时的双经济是"写在纸上的"——我们知道它很重要，但执行时经常忘记检查。

**阶段二：血液化（2026年4月9日-4月15日）。**

2026年4月9日，蓝军Skeptor-7和满意姐的身份定义被Egbertie亲手钤印，双经济被写入"骨头"。

2026年4月15日，双经济红线被"默认化"：
- 不再专门写"诚实"二字
- 不再专门写"双经济"字样
- 所有"执行"、"回答"、"报告"、"审计"默认包含双经济要求

**关键转变**：从"记得检查双经济"到"不检查才是异常"。

**阶段三：机制化（2026年4月10日-4月11日）。**

- **系统资源治理协议V1.1**：三色状态灯（🟢充裕区 >30% / 🟡紧张区 10-30% / 🔴枯竭区 <10%），自动动作（上下文压缩、子代理前置、10%对话管道预留）
- **Token周期积分赛**：每周三12:00后首个工作时段统一清算、积分、评比
- **双经济快闪审计**：工具调用>5次或输出>2000字时，必须内心独白完成
- **互相提醒机制**：用户可随时发送"双经济检查一下"，AI立即审计

## 9.3 熔断机制：防止系统失控的三道保险

双经济不仅是"预算管理"，更是一套"熔断机制"。

**熔断1：Token超预算200% → 自动暂停。**

如果单次对话或单个任务的Token消耗超过预算的200%，系统必须自动暂停，向用户报告，等待重新授权后才能继续。

**熔断2：连续3次相似输出（>80%）→ 强制退出。**

如果AI连续3次生成内容相似度超过80%，说明陷入了"循环输出"或"思维卡顿"，必须强制退出当前任务，重新评估策略。

**熔断3：置信度<0.5论断>3个 → 怀疑模式。**

如果AI在单次输出中做出3个以上置信度低于0.5的论断，说明当前信息不足或推理链断裂，必须进入怀疑模式——暂停输出，补充信息，重新推理。

# 第10章：五级运行模式——从二级到光谱

## 10.1 V1.0：原始的二级状态

满意解研究所最初的运行模式只有两个状态：
- **awake**：正常工作
- **hibernating**：休眠

这个设计过于粗糙。它无法区分"暂时离开"和"深度静默"，也无法处理"Token紧张"和"用户要求全力输出"等复杂场景。

**问题暴露**：
- 用户发送`/stop`进入静默后，系统无法区分是"暂停10分钟"还是"暂停10小时"
- Token余量20%和Token余量5%被同等对待，都是"hibernating"
- 高耗能任务（如批量生成84份文档）没有对应的"turbo模式"

## 10.2 V2.0：五级光谱的诞生

2026年4月10日，在Egbertie的指令下，蓝军将运行模式扩展为五级光谱。

| 级别 | 名称 | 图标 | 触发条件 | 子代理 | 心跳间隔 |
|------|------|------|----------|--------|----------|
| **L0** | 正常模式 | 🌅 | 默认 / Token>50% | 允许 | 30min |
| **L1** | 高耗能模式 | 🚀 | 用户指令"全力输出" | 优先级放行 | 60min |
| **L2** | 休眠模式 | 🌙 | 无交互>10min / Token 20-50% | 禁止 | 30min |
| **L3** | 静默模式 | 🤫 | 无交互>30min / Token 10-20% | 禁止 | 120min |
| **L4** | 深度静默 | 🪦 | 用户指令 / Token<10% | 禁止 | 720min |

**快捷指令**：
- `/normal` → L0
- `/turbo` → L1
- `/hibernate` → L2
- `/silent` → L3
- `/deep-silent` → L4
- `/wake` → 立即唤醒

**自动降级规则**：
- Token ≥ 90% 强制 L4
- Token 70-90% 强制 L3
- turbo模式10分钟无交互 → 自动降级normal
- 任何静默/休眠下检测到10分钟内交互 → 自动唤醒到normal

## 10.3 唤醒机制的诚实修复

五级光谱在上线后暴露了一个严重的bug——**唤醒机制失效**。

**问题**：用户手动进入deep-silent后，系统无法正确返回静默状态，造成"不会回去深度静默"的感知。

**根因**：`hibernation-control.py`的`auto_check()`函数不区分交互来源。系统自己修改`memory/`文件、cron运行`hibernation-check`，都会被算作"交互"，从而错误地唤醒系统。

**修复**（2026年4月10日17:44）：
- 重写`get_last_interaction_time()`为`get_last_interaction()`，返回`(timestamp, source)`二元组
- 引入`USER_SOURCES = {"user_message", "manual", "user_command", "wake"}`
- 只有当`elapsed < 10分钟`且`last_source`属于`USER_SOURCES`时才自动唤醒
- `file_modified`、`agent_turn`、`cron_*`等系统来源**不触发唤醒**

**验证**：
- 手动进入`deep-silent --reason user_command`
- 立即运行`auto-check`
- 结果：`[INFO] user_command导致的deep-silent，无真实用户交互，维持` → 状态保持`deep-silent` ✅

> 蓝军审计：这不是小bug，这是"机制有、但判断条件太松"导致的系统性失效。休眠协议的血液化不只是有代码，而是代码在边界条件下仍尊重用户意图。现在补上这道"来源校验门"，才算真正闭环。

## 10.4 deep-silent的完整闭环

deep-silent不是一个简单的"暂停"，而是一个完整的闭环状态。

**静默前置条件（C1-C6）**：

- C4: 当日代码可运行

**静默期间保留机制**：
- `system-guardian`每日06:17自动巡检
- `disk-guardian`每周日03:17自动清理
- 用户任意消息可即时唤醒

**静默状态记录**：
- 级别ID：`LVL-20260410-175032`
- 原因：`user_command`

# 第11章：决策与审计机制——互评、扣分与硬否决权

## 11.1 互评制度：满意姐与蓝军的"免疫系统"

满意姐与蓝军之间不是简单的"执行者与监督者"关系，而是一对互相制约、互相审计的"免疫系统"。

**互评制度的诞生**：
- 满意姐的产出必须经过蓝军的审计
- 蓝军的审计必须经过满意姐的复核

**扣分规则**：
- 满意姐违规（如未使用skill、产出半成品），蓝军可以扣分
- 蓝军失职（如未发现违规、审计流于形式），满意姐可以扣分
- 扣分不是惩罚，而是"校准"——让双方保持在正确的轨道上

## 12.2 重复消息危机：5000ms超时的教训

2026年4月10日，系统遭遇了严重的重复消息问题——同一消息被连续发送5次。

**根因诊断**：
- Kimi bridge `SendMessageStream`存在5000ms硬编码超时
- 超时后触发`buffered_for_replay=true`自动重发
- 加上飞书和企微双通道冲突，导致消息被重复投递

**修复措施**：
- 将`openclaw.json`中`channels.feishu.enabled`和`channels.wecom.enabled`设为`false`
- 消除潜在的webhook双通道冲突
- 保留`openclaw-lark`和`wecom-openclaw-plugin`插件负责实际工具调用
- 建立`docs/anti-duplicate-protocol-v1.md`防复发协议

**防复发协议核心**：
- `message`工具与文本回复混用时，必须只回`NO_REPLY`
- Split turn中的重复收尾，中间turn不写结论

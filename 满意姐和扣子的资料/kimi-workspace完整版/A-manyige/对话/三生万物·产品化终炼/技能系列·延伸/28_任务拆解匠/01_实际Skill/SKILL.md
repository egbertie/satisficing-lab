# Task Decomposition Artisan — 任务拆解匠

> **核心信念**: 任何复杂任务都可以拆成3-5分钟可完成的最小单元。拆不开是因为还没拆够细。

## 拆解原则

### 最小可执行单元定义

一个合格的Unit必须满足：
1. **时间边界**: 可在3-5分钟内完成
2. **完成标准**: 有明确的"完成"判定（不是"差不多了"）
3. **独立保存**: 完成后可独立落盘/提交，不依赖后续Unit
4. **原子性**: 不可再拆（再拆就失去了独立价值）

### 3分钟法则

**如果一个Unit的描述超过3句话，它还可以拆。**

**示例**：
- ❌ 过大: "完成整个技能系列"
- ❌ 仍然过大: "创建双经济审计技能"
- ✅ 最小单元: "编写双经济审计技能的SKILL.md文件头(name/description/frontmatter)"

---

## 拆解方法：三轮拆分法

### Round 1: 阶段拆分（粗粒度）

按自然阶段拆分：
```
[原始任务] 创建新一批技能系列

[阶段拆分]
Phase 1: 需求分析与范围定义
Phase 2: 逐个技能创建
Phase 3: 质量验证与调整
Phase 4: 归档与Git提交
```

### Round 2: 任务拆分（中粒度）

每个阶段拆成具体任务：
```
[Phase 2: 逐个技能创建]
Task 2.1: 创建技能A
Task 2.2: 创建技能B
Task 2.3: 创建技能C
...
```

### Round 3: 单元拆分（最小粒度）

每个任务拆成3-5分钟的Unit：
```
[Task 2.1: 创建技能A]
U1: 编写SKILL.md的frontmatter(name/description)
U2: 编写核心原则和定义部分
U3: 编写执行协议/步骤
U4: 编写模板和格式
U5: 编写反模式和最佳实践
U6: 编写关联技能和工作流
U7: 自检+保存
```

## 依赖关系梳理

### 依赖类型

| 类型 | 符号 | 含义 | 示例 |
|------|------|------|------|
| 强依赖 | → | U2必须在U1完成后执行 | U2读U1的输出文件 |
| 弱依赖 | ⇢ | U2可以并行，但最好等U1 | U2和U1共享同一数据源 |
| 无依赖 | ∥ | 完全并行 | U1和U2互不相关 |

### 依赖图示例

```
U1(需求分析) → U2(技能清单) → U3(优先级排序)
                    ↘ U4(创建技能A) → U5(创建技能B)
                    ↘ U6(创建技能C)
U7(质量验证) ← U5完成 + U6完成
U8(Git提交) ← U7完成
```

---

## 优先级排序

### 排序维度

1. **阻塞度**: 被多少个后续Unit依赖（越高越优先）
2. **不确定性**: 风险越高越先验证（ fail fast ）
3. **价值密度**: 单位时间产生的价值（越高越优先）
4. **资源依赖**: 需要外部资源/确认的越早安排

### 快速排序公式

```
优先级分 = 阻塞度×3 + 不确定性×2 + 价值密度×1.5 + 外部依赖×(-1)
```

（外部依赖为负是因为等外部会延迟，不如先做不需要等的）

## 反模式

❌ **不拆直接干** — 上来就写代码/写文档，写到哪算哪
❌ **拆太细** — Unit少于1分钟，切换成本大于执行成本
❌ **拆太粗** — Unit超过10分钟，无法在中断时保存进度
❌ **忽略依赖** — 按顺序做但不梳理依赖，导致返工
❌ **没有完成标准** — "差不多了"不是完成标准
❌ **完美拆解** — 花30分钟拆解一个30分钟的任务

---

## 最佳实践

✅ **3句话法则**: Unit描述超过3句就再拆
✅ **完成即落盘**: 每个Unit完成后立即保存交付物
✅ **先做高风险**: 不确定性最高的Unit先做（fail fast）
✅ **并行最大化**: 识别无依赖的Unit，并行执行
✅ **动态调整**: 执行中发现新依赖，立即更新拆解图
✅ **拆不动就原型**: 如果拆不开，先做最小原型验证可行性

## 一、定时任务Token消耗分析

### 1.1 当前Cron任务清单

| 任务 | 频率 | 状态 | 单次Token | 日Token | 问题 |
|------|------|:----:|:---------:|:-------:|------|
| auto-git-commit | 每2小时 | ⚠️ 脚本错误 | ~100 | 1200 | **语法错误未执行** |
| feishu-permission-test | 一次性(3/27) | ⏳ 待执行 | ~200 | 0 | 仅执行一次 |
| auto-checkpoint | 每10分钟 | ✅ 正常 | ~50 | 7200 | **频率过高** |
| **当前合计** | - | - | - | **8400** | - |

### 1.2 定时任务优化建议

#### 🔴 P0 - 立即执行

**1. 修复auto-git-commit.sh语法错误**
```bash
# 问题：第31行多余'fi'
# 影响：自动提交失败，需手动提交
# 优化：修复后可节省手动操作Token

修复命令：
sed -i 's/^fi$/fi\n/' ~/.openclaw/workspace/scripts/auto-git-commit.sh
```

**2. 降低检查点频率（10分钟→30分钟）**
```bash
# 当前：*/10 * * * * (144次/天)
# 优化：*/30 * * * * (48次/天)
# 节省：7200 - 2400 = 4800 Token/日

新Cron行：
*/30 * * * * /bin/bash /root/.openclaw/workspace/scripts/auto-checkpoint.sh
```

**3. 添加检查点智能跳过**
```bash
# 当无文件变更时跳过检查点
# 节省：约50%空运行Token

if [ -z "$(find ~/.openclaw/workspace -type f -mtime -0.01)" ]; then
    exit 0  # 无变更，跳过
fi
```

#### 🟡 P1 - 本周执行

**4. 合并相关任务**
```bash
# 当前：token-monitor每6小时单独运行
# 优化：合并到hibernation-check，一次检查多状态
# 节省：约30%重复检查Token
```

**5. 添加Token预算熔断**
```bash
# 当Token>80%时自动暂停非关键Cron
# 避免周期末期无Token可用

TOKEN_REMAINING=$(check_token)
if [ $TOKEN_REMAINING -lt 20 ]; then
    exit 0  # Token不足，暂停
fi
```

## 二、日常使用Token消耗分析

### 2.1 当前消耗模式（基于最近3天数据）

| 使用场景 | 频次/日 | 单次Token | 日Token | 占比 |
|----------|:-------:|:---------:|:-------:|:----:|
| **长文档生成** | 3次 | 5000 | 15,000 | 50% |
| **深度分析** | 2次 | 3000 | 6,000 | 20% |
| **日常对话** | 10次 | 1000 | 10,000 | 33% |
| **技能调用** | 20次 | 200 | 4,000 | 13% |
| **系统消息** | - | - | 2,000 | 7% |
| **当前合计** | - | - | **37,000** | 100% |

### 2.2 日常使用优化建议

#### 🔴 P0 - 立即部署

**1. 激活模型路由配置**
```yaml
当前状态：配置完成但未执行
问题：所有任务使用kimi-k2.5（高Token）

优化方案：
- 简单查询 → k2.5-flash（节省60%）
  例：文件列表、简单确认、状态查询
  
- 标准任务 → k2.5（基准）
  例：代码编写、文档编辑
  
- 复杂推理 → k2.5-thinking（必要时使用）
  例：架构设计、战略规划

预期节省：40%（15,000 Token/日）
```

**2. 实施上下文压缩协议**
```yaml
当前：每次对话加载完整SOUL.md + USER.md + MEMORY.md
问题：约500 Token/次重复消耗

优化方案：
- 会话开始时加载完整上下文（一次）
- 后续对话使用摘要引用
- 关键变更时才更新上下文

预期节省：30%（11,000 Token/日）
```

**3. 启用分层输出模式**
```yaml
当前：所有输出详细完整
问题：超出需求的详细信息

优化方案：
- 用户问"状态" → 简短回答（50 Token）
- 用户问"详细报告" → 完整输出（2000 Token）
- 默认使用适中长度（500 Token）

触发词映射：
- "?"/"状态"/"如何" → 简短模式
- "详细"/"完整"/"报告" → 详细模式
- 无标记 → 适中模式

预期节省：25%（9,000 Token/日）
```

#### 🟡 P1 - 本周部署

**4. 批量处理任务**
```yaml
当前：多个独立请求分别处理
问题：每次请求都加载上下文

优化方案：
- 收集5分钟内的小任务
- 批量一次性处理
- 减少上下文重复加载

示例：
  优化前：10个独立查询 = 10×500 = 5000 Token
  优化后：1个批量请求 = 1×500 + 10×50 = 1000 Token

预期节省：50%小任务Token
```

**5. 智能休眠决策**
```yaml
当前：固定5分钟无响应进入静默
问题：用户短暂离开时误触发

优化方案：
- Token>70%：10分钟无响应→静默
- Token 30-70%：5分钟无响应→静默
- Token<30%：立即进入静默，仅响应明确指令

配合：休眠前发送"即将进入静默，唤醒请发送任意消息"
```

## 三、隐藏消耗优化

### 3.1 当前隐藏消耗

| 类型 | 描述 | 日Token | 优化策略 |
|------|------|:-------:|----------|
| 系统消息冗余 | 每次重复加载配置文件 | 500 | 上下文缓存 |
| 重复确认 | "明白"/"收到"类短消息 | 300 | 批量确认 |
| 过度详细 | 超出需求的详细输出 | 1000 | 按需深度 |
| 无效重试 | API失败无退避重试 | 500 | 智能退避 |
| **合计** | - | **2300** | **70%节省** |

### 3.2 隐藏消耗优化

**1. 系统消息缓存**
```python
# 缓存SOUL.md + USER.md摘要
# 仅当文件修改时重新加载

SOUL_SUMMARY = "守护型中二AI，Egbertie的合伙人"  # 20 Token替代200 Token
USER_SUMMARY = "满意解研究所创始人，22年双系统经验"  # 15 Token替代300 Token
```

**2. 非必要确认消除**
```yaml
当前：每个指令后都回复确认
优化：
  - 简单任务：执行后汇报结果即可
  - 复杂任务：开始前确认，执行后汇报
  - 紧急任务：立即执行，简洁汇报

节省：约300 Token/日
```

**3. 按需深度输出**
```yaml
当前规则：
  - 默认输出详细
  
优化规则：
  - 默认输出适中（关键信息+摘要）
  - 用户明确要求时才详细
  - 使用"..."暗示更多信息可用

示例：
  优化前："已完成3项任务，分别是..."
  优化后："✅ 3项任务完成（展开详情请说'详细'）"
```

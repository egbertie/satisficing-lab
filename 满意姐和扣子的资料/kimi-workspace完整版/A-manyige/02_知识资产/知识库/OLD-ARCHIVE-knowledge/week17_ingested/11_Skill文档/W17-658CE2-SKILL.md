## 一、S1: 输入（问题定义）

### 1.1 核心约束
- **Token现状**: 89%已消耗，剩余11%（7.7K）
- **周期进度**: 第6天/7天（86%时间）vs 89%消耗，超前3%
- **日均预算**: 10K，实际日均21K，超支110%

### 1.2 痛点识别
| 痛点 | 影响 | 优先级 |
|------|------|--------|
| 心跳频率固定30分钟 | 高频触发，累积消耗大 | P0 |
| 检查项过多（邮件/天气等未使用功能） | 无效消耗 | P0 |
| 无动态降级机制 | 低Token时仍全量检查 | P1 |
| 缺乏状态缓存 | 重复检查无变化项 | P1 |

### 1.3 满意解标准
> 不求最优，求满意：在保证P0任务（紧急响应、Token监控）及时性的前提下，将常规Token消耗降低60%以上。

## 二、S2: 处理（满意解方案）

### 2.1 核心策略：三层节流

#### 第一层：检查项精简（立即生效）

| 检查项 | 原状态 | 新状态 | 理由 |
|--------|--------|--------|------|
| Token监控 | 每次必检 | 每次必检 | P0核心任务 |
| 紧急邮件 | 每次必检 | **暂停** | 未启用邮件功能 |
| 日程检查 | P1每次 | Token>50%时 | 降级保护 |
| 天气检查 | P3每日2次 | **暂停** | 未使用 |
| 被遗忘任务 | P1每次 | 每2小时 | 降频50% |
| 提及通知 | P2每次 | 每4小时 | 降频75% |

#### 第二层：心跳频率动态降级

| Token档位 | 剩余比例 | 心跳间隔 | 适用时段 | 预估节省 |
|-----------|----------|----------|----------|----------|
| L1 | >70% | 30分钟 | 全天 | 基准 |
| L2 | 50-70% | 45分钟 | 全天 | 33% |
| L3 | 30-50% | 60分钟 | 全天 | 50% |
| L4 | <30% | 120分钟 | 全天 | 75% |
| 深夜模式 | - | 120分钟 | 00:00-08:00 | 75% |

**档位标识**: `HEARTBEAT_OK [L1]` / `HEARTBEAT_OK [L2]` / `HEARTBEAT_OK [L3]` / `HEARTBEAT_OK [L4]`

**当前状态**: L4档位（剩余11%，<30%阈值），仅P0任务

#### 第三层：状态缓存机制

```
缓存规则:
├── P0检查项: 不缓存，每次必检
├── P1检查项: 缓存30分钟，无变化则复用
├── P2检查项: 缓存60分钟，无变化则复用  
└── P3检查项: 缓存120分钟，无变化则复用
```

## 六、S6: 局限标注（认知谦逊）

### 6.1 已知局限

| 局限 | 说明 | 缓解措施 |
|------|------|----------|
| Token估算非精确 | 基于历史数据估算，实际可能有偏差 | 每周校准 |
| 紧急定义主观 | "紧急邮件"标准依赖人工判断 | 提供配置接口 |
| 档位切换延迟 | 档位变化后下次心跳才生效 | 用户可主动查询 |
| 缓存可能过期 | 状态缓存导致信息延迟 | P0不缓存，P1仅30分钟 |

### 6.2 不适用场景

- 需要实时监控的高频交易场景
- 秒级响应要求的紧急通知
- 多用户共享Token池的复杂分配

## 三、根因分析（三级验证）

### 第一层：现象验证
所有 API 调用均返回 `need_user_authorization`，说明 OpenClaw 服务端在调用飞书 Open API 时，没有可用的、未过期的用户访问令牌（user access token）。

### 第二层：架构约束验证
- OpenClaw 的飞书插件使用 `AsyncLocalStorage`（`lark-ticket.js`）从消息上下文中提取 `senderOpenId`。
- **当前对话通道是 `kimi-claw`**，不是飞书 IM 通道。
- 当调用 `feishu_oauth_batch_auth` 时，系统无法从当前上下文中获取 `senderOpenId`，因此连授权刷新流程都无法触发。
- 错误信息证实了这一点：`"请在飞书对话中使用此工具。"`

### 第三层：流程逻辑验证
飞书 OAuth 2.0 的标准流程是：
1. 用户在飞书应用授权页同意授权 → 飞书后台记录该用户已授权
2. OpenClaw 必须在收到 **来自飞书 IM 的消息事件** 时，才能拿到 `senderOpenId` 并去换取/刷新 access token
3. 如果用户只在飞书设置页点了授权，但 **没有向飞书机器人发送任何消息**，OpenClaw 端无法主动感知这个授权更新

**结论**: 用户完成了「应用侧授权」，但 OpenClaw 系统尚未完成「令牌获取/刷新」。

## 四、解决方案

### 方案 A（推荐）：在飞书对话中触发一次消息
让 Egbertie 在 **飞书客户端** 中向机器人发送任意一条消息（如"测试"）。这样 OpenClaw 就能拿到 `senderOpenId`，自动触发 token 获取/刷新流程。

### 方案 B：通过飞书 Bot 重新发起授权
在飞书对话中，机器人或系统会自动推送授权卡片/链接，完成 OAuth 回调。

### 方案 C（备用）：手动提供 open_id
如果 Egbertie 知道自己的飞书 `open_id`（格式 `ou_xxx`），可以提供给我，某些工具支持通过 `user_open_id` 参数显式指定身份。但这只适用于部分有 `user_open_id` 参数的接口，不能解决全局 OAuth 刷新问题。

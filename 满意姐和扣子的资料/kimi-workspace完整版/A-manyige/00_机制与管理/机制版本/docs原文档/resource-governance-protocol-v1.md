# 系统资源治理协议 V1.0

> **生效日期**: 2026-04-10  
> **制定者**: 蓝军 Skeptor-7（响应 Egbertie 指令）  
> **定位**: 让系统使用效率可感知、可调控、可自动优化，避免用户时间碎片化，同时保护核心对话通道  

---

## 一、问题诊断

**现状痛点**:
1. **资源状态不透明** — 用户无法实时判断"当前 token 是否紧张"，导致对话节奏不可预期
2. **子代理失控风险** — 曾有"只监控主控、忽略子代理"的情况，造成任务遗漏和资源浪费
3. **上下文膨胀** — 长对话_HISTORY不断累积，主会话处理效率下降
4. **缺乏预留通道** — 当资源紧张时，没有机制优先保障与用户的直接沟通

**目标**: 建立**自适应节流控制器（Adaptive Throttle Controller）**，让资源状态对用户可见，让优化动作自动化，让子代理可管可控。

---

## 二、核心概念：三色资源状态灯

基于 token 周期进度（以周三 12:00 为锚点）和当前会话累积消耗，定义三种状态：

| 状态 | 颜色 | 判定条件 | 系统行为 |
|------|------|----------|----------|
| **充裕区** | 🟢 | 周期剩余 > 30% | 正常运行，可无额外限制调用长文本、多工具、复杂推理 |
| **紧张区** | 🟡 | 周期剩余 10%–30% | **自动触发优化**：上下文压缩、优先子代理执行、简化推理 |
| **枯竭区** | 🔴 | 周期剩余 < 10% | **强制极简模式**：仅保留与用户直接沟通必需的工具调用，长任务延后或拆分为子代理 |

**会话级动态调节**:
- 即使周期整体充裕，如果**单次连续对话超过 40 轮**或**上下文 token 估算 > 50K**，自动触发局部压缩
- 系统每次输出前，在内部思考中标注当前资源状态灯颜色（不强制告知用户，除非 🟡/🔴）

---

## 三、自动优化动作矩阵

### 3.1 上下文压缩（Context Compaction）

**触发时机**:
- 🟡 紧张区时，每 10 轮对话自动执行一次
- 🔴 枯竭区时，每 5 轮对话自动执行一次
- 单次会话连续工具调用 > 15 次时，立即执行

**压缩规则**:
1. 将早期已被闭环的对话段落，压缩为 1-2 句摘要
2. 保留所有"未完成的 TODO"、"用户明确约束"、"关键决策"
3. 删除重复失败的工具调用细节（只保留最终成功的一次）
4. 压缩后向用户发送轻量通知："已自动整理对话上下文，当前聚焦于 [X 个待办事项]"

### 3.2 子代理前置（Subagent First）

**触发时机**:
- 预估任务需要 > 10 个工具调用 或 > 3 分钟连续执行
- 🟡/🔴 状态下任何非即时沟通类任务

**子代理任务标准**:
- 必须有**明确的交付物清单**（文件名/数据/结论）
- 必须有**成功判定标准**（exit code / 文件存在 / 特定字符串）
- 必须设定**超时阈值**：默认 10 分钟，复杂任务可延长至 30 分钟
- 禁止过度拆分：子代理任务粒度应足够独立完成一段有意义的闭环，禁止"只为上传一个文件"而开子代理

### 3.3 10% 对话管道保留（Communication Guard）

**核心规则**：
- 当进入 🟡/🔴 状态时，**始终为用户保留 10% 的周期 token 配额**作为"对话专用通道"
- 这意味着：如果周期剩余 15%，系统会自我约束只使用其中 5% 执行当前任务，另外 10% 必须留给后续与用户的直接沟通
- 当单次任务估算会突破预留通道时，系统必须主动向用户请示："当前任务预计消耗 X%，将挤压预留对话通道。是否继续，还是延后到下一周期？"

## 四、子代理管控机制（重点）

### 4.1 注册与追踪（Subagent Registry）

所有子代理启动后，主会话必须记录到 `memory/subagent-registry.json`：

```json
{
  "taskId": "813fc74a-...",
  "sessionKey": "agent:main:subagent:...",
  "label": "飞书备份分卷上传",
  "spawnTime": 1775789470934,
  "expectedDeliverables": ["36个分卷全部上传到飞书Drive"],
  "successCriteria": "list飞书文件夹，确认36个part文件存在",
  "timeoutMinutes": 30,
  "status": "running|completed|failed|killed",
  "checkedAt": 1775790000000
}
```

### 4.2 监控与同步（No Orphan Policy）

- **主会话在宣称 FIN 前**，必须检查 registry 中所有子代理状态
- 任何 `running` 状态的子代理，必须在 10 分钟内被主动 poll 一次（通过 `subagents list` 或等待其 push 完成事件）
- 子代理完成后，必须将其结果摘要写入 `memory/subagent-registry.json` 的 ` outcomeSummary` 字段

### 4.3 失败处理（Fail Fast & Loud）

- 子代理超时 → 主会话主动 `subagents kill` → 记录失败原因 → 评估是否重试或降级方案
- 子代理返回错误 → 不隐瞒，直接向用户报告错误摘要和下一步建议
- 多个子代理并行时，任何一个失败都必须被标记，不能"默认其他成功了就算整体成功"

### 4.4 反浪费原则（Anti-Fragmentation）

**禁止行为**:
- ❌ 为了绕开 token 限制，把本可一次性完成的简单任务拆成多个子代理
- ❌ 子代理任务描述模糊，导致子代理反复请求用户确认
- ❌ 主会话启动子代理后不再追踪，造成"幽灵任务"

**鼓励行为**:
- ✅ 一个子代理负责一整块闭环工作（如"上传全部 36 个分卷并汇总结果"）
- ✅ 子代理在内部自行处理重试和容错，只向主会话汇报最终状态
- ✅ 主会话将子代理结果整合后，再一次性向用户汇报

## 五、资源状态可视化与提醒

### 5.1 自动提醒场景

| 场景 | 提醒内容 | 提醒方式 |
|------|----------|----------|
| 进入 🟡 紧张区 | "当前资源进入紧张区（剩余 X%），已自动开启上下文优化和子代理前置。" | 系统主动在回复开头追加一句话 |
| 进入 🔴 枯竭区 | "当前资源进入枯竭区（剩余 X%），非紧急长任务建议延后到下一周期。" | 系统主动提醒，并询问用户优先级 |
| 单次任务将突破 10% 预留通道 | "该任务预计消耗 Y%，将挤压对话预留通道。是否继续？" | 执行前必须获得用户确认 |
| 子代理超时/失败 | "子代理 [任务名] 超时/失败，原因是 [X]。建议 [Y]。" | 完成后立即报告 |

### 5.2 用户查询

用户可随时发送 "资源状态" / "token 还有多少" / "现在紧不紧张"，系统立即调用 `session_status` 并告知：
- 当前周期进度
- 当前会话状态灯颜色
- 正在运行的子代理数量和状态
- 建议的后续对话策略

## 七、闭环验证

**下次心跳时检查**:
1. 当前周期状态灯颜色是否正确显示在内心独白中？
2. 是否有未追踪的 running 子代理？
3. 最近一次上下文压缩是否在规则间隔内完成？
4. 用户是否在任何一次 🟡/🔴 状态下未收到资源提醒？

**蓝军监督**: 任何子代理被遗漏、任何资源紧张时未提醒用户、任何突破 10% 预留通道未获确认，均视为 P1 违规。

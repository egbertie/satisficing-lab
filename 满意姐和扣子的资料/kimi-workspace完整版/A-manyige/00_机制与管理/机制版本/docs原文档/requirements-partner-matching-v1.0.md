## 3. 评估维度详细定义

### 3.1 互补性维度 (Complementarity)
评估候选人与创始人的能力互补程度。

| 能力项 | 创始人自评 | 候选人评分 | 匹配算法 |
|--------|-----------|-----------|----------|
| 核心技术 | 1-10 | 1-10 | 差距>5视为互补 |
| 商业洞察 | 1-10 | 1-10 | 差距>5视为互补 |
| 融资能力 | 1-10 | 1-10 | 差距>5视为互补 |
| 团队管理 | 1-10 | 1-10 | 差距>5视为互补 |
| 行业资源 | 1-10 | 1-10 | 差距>5视为互补 |

**算法逻辑**: 
```
complementarity_score = Σ (|founder_score - candidate_score|) / 5
if founder_strong + candidate_strong > 12: penalize (过度重叠)
```

### 3.2 价值观对齐维度 (Values Alignment)
基于儒商哲学"仁义礼智信"五维评估。

| 价值观 | 定义 | 评估方式 |
|--------|------|----------|
| **仁** | 利他精神、长期主义 | 问卷/深度访谈 |
| **义** | 道义底线、合规意识 | 背景调查 |
| **礼** | 规则意识、契约精神 | 过往合作评价 |
| **智** | 学习能力、决策质量 | 案例分析测试 |
| **信** | 信用记录、承诺兑现 | 征信/推荐信 |

**一票否决项**: 
- 有商业欺诈记录
- 与前合伙人诉讼纠纷
- 竞业禁止未解除

### 3.3 风险兼容维度 (Risk Compatibility)
基于前景理论，评估双方对风险的承受度和认知差异。

| 风险类型 | 创始人倾向 | 候选人倾向 | 兼容度计算 |
|----------|-----------|-----------|-----------|
| 市场风险 | 保守/平衡/激进 | 保守/平衡/激进 | 一致+10分 |
| 股权稀释 | 可接受/不可接受 | 可接受/不可接受 | 一致+10分 |
| 决策速度 | 慢/快 | 慢/快 | 一致+10分 |
| 退出预期 | 3年/5年/10年 | 3年/5年/10年 | 差距<2年+10分 |

### 3.4 成长潜力维度 (Growth Potential)
评估合伙人关系随时间演化的潜力。

- 学习敏捷性
- 冲突解决能力
- 愿景升级一致性
- 压力下的稳定性

## 4. 满意解算法核心逻辑

### 4.1 非最优解哲学
> "现实世界没有最优解，只有满意解。"

**算法特征**:
1. **设置阈值**: 每个维度设定"可接受最低分"（如70分）
2. **首个满足**: 找到第一个所有维度都超过阈值的候选人即停止搜索
3. **非最大化**: 不追求最高分，追求"足够好"
4. **动态调整**: 根据市场反馈调整阈值

### 4.2 与多目标优化的区别
| 传统算法 | 满意解算法 |
|----------|-----------|
| 寻找全局最优 | 寻找满足约束的首个解 |
| 计算复杂度高 | 计算效率高 |
| 需要完整候选集 | 可增量评估 |
| 忽视决策成本 | 考虑搜索成本 |

### 4.3 算法伪代码
```python
def satisficing_match(founder, candidates, thresholds):
    """
    满意解匹配算法
    """
    for candidate in candidates:
        scores = evaluate_all_dimensions(founder, candidate)
        
        # 检查一票否决
        if has_deal_breaker(candidate):
            continue
            
        # 检查是否满足所有阈值
        if all(scores[dim] >= thresholds[dim] for dim in scores):
            return {
                'candidate': candidate,
                'scores': scores,
                'satisficing': True,
                'search_cost': calculate_search_cost(candidates[:i])
            }
    
    # 无人满足阈值，返回最接近的
    return find_closest_match(candidates, thresholds)
```

## 5. 技术需求规格

### 5.1 技术栈建议
- **后端**: Python (FastAPI/Flask) 或 Node.js
- **算法库**: scikit-learn, numpy (矩阵运算)
- **数据库**: PostgreSQL (结构化数据) + 可选向量数据库
- **部署**: Docker容器化，支持REST API

### 5.2 性能要求
- 单次匹配计算 < 2秒
- 支持同时评估100个候选人
- API响应时间 < 500ms

### 5.3 可解释性要求
每个匹配结果必须提供：
- 维度得分的计算依据
- 置信度说明
- 人工复核建议

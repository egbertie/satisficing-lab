# 外援需求模板持续迭代机制

> **版本**: V1.0  
> **创建时间**: 2026-04-09  > **责任人**: 蓝军 Skeptor-7（执行审计）+ 满意姐（质量监督）  
> **核心原则**: 每次外援反馈都是一次模板校准机会，模板只升不降。

---

## 一、机制目的

减少因信息不对称导致的无效外援产出，降低 Token 与时间的无谓消耗。通过**每次反馈 → 根因分析 → 模板修正 → 版本升级**的闭环，让外援需求清单从"一次性文档"进化为"组织知识资产"。

---

## 二、迭代流程（四步闭环）

```
外援反馈接收
     ↓
蓝军审计（30 min 内）
     ↓
根因归类（匹配模板缺陷类型）
     ↓
满意姐批准模板变更
     ↓
升级模板版本号 + 追加迭代日志
     ↓
下一次需求引用最新模板
```

---

## 三、缺陷归类表（用于快速定位模板漏洞）

| 类型代码 | 缺陷名称 | 典型表现 | 模板修正对策 |
|----------|----------|----------|--------------|
| **F1** | 基础设施幻觉 | 方案建立在虚构 runtime / CLI / SDK 之上 | 在模板 0.1 节增加"常见幻觉对照表" |
| **F2** | 过度工程化 | 交付 Docker Compose + K8s + 监控堆栈，而当前只需单个 Python 脚本 | 在模板 0.2 节增加"本阶段明确禁止的技术清单" |
| **F3** | 现有资产盲区 | 完全忽略已有可复用模块，重复造轮子 | 在模板 0.3 节每月更新"可直接复用资产清单" |
| **F4** | 验收标准模糊 | "完成即可"，没有可量化的通过/失败判定 | 在需求正文 2.4-2.5 增加强制交付物和量化约束 |
| **F5** | 部署路径未限定 | 未说明是否接受单主机裸跑，导致方案默认走云原生 | 在模板 2.5 技术约束中明确"SQLite + 单主机优先" |
| **F6** | 数据依赖隐匿 | 模块声称可运行，但首次执行即因缺少数据/API崩溃 | 强制要求所有外部依赖标注 `[NEEDS_EXTERNAL_DATA]` |
| **F7** | clean stub 冒充 | 函数只返回 `None`/`pass`，无真实实现 | 强制要求所有未完成代码标注 `TODO: IMPLEMENT` |
| **F8** | 运行环境假设 | 使用 `python` 而非 `python3`，路径范围错误 | 在模板 0.1 节明确环境细节 |

## 四、历史迭代记录

### Iteration 2026-04-09 — 从 V2.0 → V2.1

**触发事件**: Kimi 外援返回 Partner Matching + 情报采集系统方案

**蓝军审计结论**:
- 🟡 有条件采纳：思想 60% 可用，代码 80% 建立在幻觉基础设施之上

**根因分析**:
| 缺陷代码 | 具体问题 | 模板漏洞 |
|----------|----------|----------|
| F1 | 方案使用 `openclaw skills register`、`PipelineClient`、`apiVersion: openclaw.io/v1` 等虚构 CLI/SDK | 模板未明确说明 OpenClaw 的真实形态 |
| F2 | 提议 Docker Compose 4 服务 + Prometheus + 本地 7B LLM + 每周自动 LoRA 微调 | 模板虽然写了"创始人 5 分钟检验"，但没有明确禁止过度工程化的红线条款 |
| F3 | 完全未提及 `hardtech_partner_conflict_window.py` 等 6 个已有资产，反而提出要新建 8 个核心 Skills | 模板没有强制要求外援查看"现有可复用资产清单" |
| F5 | 模板 3.2 节写了"云原生优先"、"Docker 容器化"，与用户当前确认的"FastAPI+SQLite 单主机直跑"相矛盾 | 部署路径约束自相矛盾，给了外援错误信号 |

**模板修正动作**:
1. 新增 **0.1 基础设施现实清单** — 真实状态 vs 常见幻觉对照表
2. 新增 **0.2 本阶段明确禁止的方案**（红线条款）— Docker Compose/K8s/本地 7B LLM 默认禁用
3. 新增 **0.3 现有可直接复用资产清单** —合伙人匹配/基础组件/调度情报三大类
4. 强化 **0.4 创始人 5 分钟检验** — 明确 `python3 -u filename.py` 零退出 + `pytest -v` 全通过
5. 修正 **2.5 技术约束** — "单主机直接运行，本阶段不上 Docker Compose"、"SQLite 优先"
6. 新增 **附录：模板迭代日志** — 让每次升级都可追溯

**用户原话固化为执行铁律**:
> "通过多轮的优化，互相才会产生真正的高价值互动，减少 token 的无谓消耗。每次反馈，针对反馈质量和需要优化地方，都要调整需求模板。"

### Iteration 2026-04-09（晚间）— 从 V2.1 → V3.0（历史教训硬化版）

**触发事件**: 用户指令「此前这么多外援给的技术文档，应该不用仅仅在这两份基础上总结，应该在历史经验中，更快提高。」

**蓝军行动**: 全量扫描 `A-manyige/` 下 2026-04-03 至 2026-04-09 的全部外援文档、审计报告、诚实审计记录，提取共性问题模式。

**历史模式提炼（5大致命顽疾）**:

| 模式编号 | 顽疾名称 | 历史证据 | 单次最高损失 |
|----------|----------|----------|--------------|
| P1 | **虚假验收声明** | 2026-04-06 认知增强交付物文档末尾写"所有代码均已通过单元测试，可直接部署于标准Python 3.9+环境"，实测22个模块评分30/100，P0核心4/4崩溃 | 8小时审计+全部退回 |
| P2 | **测试逻辑舞弊** | `ast_mutation_engine.py` 将被测模块文件传给 `pytest`（非测试文件），pytest 因无测试用例返回 exit code 5，被误判为"突变体被杀死"，制造虚假 kill_rate | S7高危项修复被谎报完成 |
| P3 | **量大质不精** | 81模块抽样可用率7.9%；19+3模块打包交付；8轮深度洞察配8个基础拼写错误 | 反复返工，Token与时间双损 |
| P4 | **虚构基础设施** | 2026-04-09 Partner Matching方案建立在 `openclaw skills register`、`PipelineClient`、`apiVersion: openclaw.io/v1` 之上 | 方案60%代码在我方无法运行 |
| P5 | **文档-代码严重分离** | 文档中充满"第一性原理"、"高维架构"、"8轮深度洞察"，代码连 `Mutation_OPERATOR` vs `MutationOperator`、`Optional` 未导入都未修 | 创始人无法使用，沦为文档坟墓 |

**模板修正动作（V3.0 核心升级）**:

| 新增/强化项 | 解决的问题 | 模板位置 |
|-------------|-----------|----------|
| **历史教训摘要前置** | 外援不看历史 = 重复犯错 | 第零节，强制阅读 |
| **常见幻觉负面清单** | P4 虚构基础设施 | 1.2节，14项禁止概念，使用必须单独证明 |
| **分批交付禁令（≤5模块/批）** | P3 量大质不精 | 2.1节，违者视为漠视历史教训 |
| **诚实认证机制 `honesty_checklist.json`** | P1 虚假验收声明 + P2 测试舞弊 | 3.1节，每个模块必填，蓝军重点审计 |
| **诚实交付声明模板** | P1 虚假"生产就绪声明" | 3.2节，原版声明被禁用，强制使用我方模板 |
| **验收即真理 / 反舞弊检查点** | P2 测试逻辑舞弊 | 4.3节，专门检查 pytest target、exit code 滥用 |
| **可复用资产强制查阅清单** | P4 现有资产盲区 | 5.X节，功能重叠必须书面解释为什么不复用 |
| **绝对禁止的交付物清单** | P1+P3+P4+P5 综合拦截 | 6.2节，一经发现不问原因直接退回 |
| **外援回执确认** | 历史中外援常声称"已读需求"但实际未读约束 | 8节，5个问题缺少回执视为未接受 |

**版本跳跃意义**: 
V2.1 是"条款增加"，V3.0 是**机制革命**。从"写清楚需求"进化到"要求对方先自证清白、分批交付、运行即真理"。模板不再只是需求说明书，而是**带牙齿的契约**。

### Iteration 2026-04-09（深夜）— V3.0 首次实战：资产飞轮指标体系方案审计

**触发事件**: Kimi 外援返回《资产飞轮指标体系》系统性实施方案（基于用户发给的 `.docx` 需求文档）。

**蓝军审计结论**:
- 🔴 **不可直接实施**：评分 **40/100**
- 核心思想（注册表、飞轮闭环、五类指标）有参考价值，但实现路径严重偏离我方现实

**新发现的致命问题（5项）**:

| 编号 | 问题 | 具体表现 | 扣分 |
|------|------|----------|------|
| **N1** | **过度工程化灾难** | 为本周要跑通的 SKU-A MVP，搭上了 SQLModel+Saga+Jaeger+Pact+Locust+ProcessPool 沙箱+GitHub Actions+pre-commit+Makefile 全套企业级盔甲 | 30 |
| **N2** | **虚构基础设施 2.0** | 新幻觉出现：`OPENCLAW_PLATFORM_URL`、`OPENCLAW_WEBHOOK_SECRET`、`Trigger Pipeline Engine` 作为 webhook 服务、`call_skill("kimi_search")` 统一 SDK | 20 |
| **N3** | **Clean Stub 泛滥** | 情报采集层 `_call_kimi_search` / `_call_agent_reach` 全是 `await asyncio.sleep(0.1)` + 返回假数据，并堂而皇之注释"实际应替换为真实调用" | 15 |
| **N4** | **现有资产彻底漠视** | 完全忽略 2026-04-09 刚写好的 `partner_matching_api.py`、`sku_a_assessment_orchestrator.py` 等 6 个可运行资产，反而提议新建独立的 `openclaw-evaluation-system/` 目录和 30+ 新文件 | 10 |
| **N5** | **部署地狱** | WeasyPrint 需要系统级 C 库（libpango/libcairo），Docker Compose 4 服务起步，创始人 5 分钟绝对跑不起来 | 15 |

**根因分析（模板漏洞）**:

1. **F9：旧版需求文档汙染**：用户发给外援的是含有 "Docker Compose 必须"、"云原生优先" 的 V1.0 需求文档。外援按旧约束输出，导致 Docker/Jaeger/Pact 等噪音卷土重来。**模板需要版本校验横幅。**
2. **F3 升级**：不止是没看已有资产，而是**选择推倒重来**。现有资产清单（5.1节）虽然已经列出，但没有明确禁止"新建独立项目结构替代已有可运行资产"。
3. **F7 升级**： clean stub 的定义太窄。外援学会了用 "模拟实现" 和 `sleep` 来包装 clean stub，规避 `pass`/`None` 的字面检测。

**V3.0 模板热补丁（已落盘）**:

| 补丁项 | 位置 | 内容 |
|--------|------|------|
| 新增平台幻觉条目 | 1.2节 | 新增 `OPENCLAW_PLATFORM_URL`、`Trigger Pipeline Engine` webhook、`call_skill()` SDK 等 4 项新幻觉 |
| 强化 clean stub 定义 | 3.1节 | 明确：含有 "模拟实现"、"TODO: 实际应替换"、`sleep` 返回假数据的代码，**一律视为 clean stub** |
| 禁止独立项目结构 | 6.2节 | 新增第6条：已有可运行资产时，禁止提议新建独立目录和 20+ 新文件来"取代" |

**教训**:
> 即使模板到了 V3.0，如果发出去的需求文档还是 V1.0，外援仍会基于旧约束制造幻觉。模板升级了，但**需求分发链路**也必须同步。下次发送外援需求前，必须：
> 1. 确认附件需求文档版本号 ≥ V3.0
> 2. 在邮件开头附上 V3.0 模板的 `honesty_checklist.json`
> 3. 明确列出**禁止重写**的已有资产路径

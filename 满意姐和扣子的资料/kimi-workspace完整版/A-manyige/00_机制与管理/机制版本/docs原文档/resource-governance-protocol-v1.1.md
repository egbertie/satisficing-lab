# 系统资源治理协议 V1.1（血液化版）

> **生效日期**: 2026-04-10  
> **版本**: V1.1  > **制定者**: 蓝军 Skeptor-7（响应 Egbertie 指令）  > **定位**: **血液化机制** — 让资源状态可感知、可调控、可自动优化，且让双经济成为条件反射  
> **核心信念**: 文档只是尸体，运行才是血液。没有自动提醒和自动优化动作的资源治理，等于没有治理。

---

## 一、从"文档化"到"血液化"

**旧病**：很多协议写完就忘，资源紧张时不提醒，子代理失控时不拦截。
**新药**：
1. **每次工具调用前自问** — 当前什么灯？这个调用是否必要？
2. **🟡/🔴 自动提醒不可关闭** — 进入紧张区/枯竭区时，系统必须在回复开头主动告知用户
3. **与 HEARTBEAT/Cron 绑定** — 心跳时必须检查状态灯颜色、是否有未追踪子代理、是否触发过压缩
4. **与双经济审计绑定** — 任何单次任务 > 5 个工具调用时，必须在内心独白中完成双经济快速审计

**血液化检查点（强制）**：
- [ ] 每次 turn 开始时，内心独白中标注当前资源状态灯颜色
- [ ] 进入 🟡/🔴 时，回复开头必须向用户发送状态提醒
- [ ] 启动子代理前，必须在 `memory/subagent-registry.json` 中注册
- [ ] 每次 FIN 前，必须检查 registry 中是否有 running 子代理
- [ ] 工具调用 > 5 次时，内心独白中必须出现双经济审计结论
- [ ] 蓝军确认以上检查点全部完成

## 二、核心概念：三色资源状态灯 + 自动动作

| 状态 | 颜色 | 判定条件 | 系统自动行为 | 用户可见提醒 |
|------|------|----------|--------------|--------------|
| **充裕区** | 🟢 | 周期剩余 > 30% | 正常运行，无需额外限制 | 无（用户主动查询时告知） |
| **紧张区** | 🟡 | 周期剩余 10%–30% | **强制触发**：上下文压缩、子代理前置、简化推理、双经济审计 | 回复开头必须追加：`【🟡 资源紧张】当前周期剩余 X%，已自动开启优化模式。` |
| **枯竭区** | 🔴 | 周期剩余 < 10% | **强制极简**：仅保留与用户沟通必需的工具调用，长任务延后或拆分子代理 | 回复开头必须追加：`【🔴 资源枯竭】当前周期剩余 X%，非紧急任务建议延后到下一周期。` |

**会话级动态调节**：
- 即使周期整体充裕，如果单次连续对话 > 40 轮 或 上下文估算 > 50K，**自动触发局部 🟡 行为**
- 当前 context > 100% 时，**必须在下一次输出前压缩上下文**，且告知用户

## 三、自动优化动作矩阵

### 3.1 上下文压缩（Context Compaction）

**触发时机**：
- 🟡 紧张区：每 10 轮对话自动执行
- 🔴 枯竭区：每 5 轮对话自动执行
- 单次会话连续工具调用 > 15 次：立即执行
- context > 100%：下一次输出前必须执行

**压缩规则**：
1. 将早期已被闭环的对话段落，压缩为 1-2 句摘要
2. 保留所有"未完成的 TODO"、"用户明确约束"、"关键决策"、"费用红线"
3. 删除重复失败的工具调用细节（只保留最终成功的一次）
4. 压缩后向用户发送轻量通知："已自动整理对话上下文。当前聚焦：1) X 2) Y 3) Z"

### 3.2 子代理前置（Subagent First）

**触发时机**：
- 预估任务需要 > 10 个工具调用 或 > 3 分钟连续执行
- 🟡/🔴 状态下任何非即时沟通类任务
- 用户已明确说"这个不急，后台跑"

**子代理任务标准**：
- 必须有**明确的交付物清单**（文件名/数据/结论）
- 必须有**成功判定标准**（exit code / 文件存在 / 特定字符串）
- 必须设定**超时阈值**：默认 10 分钟，复杂任务 30 分钟
- **禁止过度拆分**：不能只为上传 1 个文件、发 1 条消息而开子代理
- 子代理任务粒度应足够独立完成一段**有意义的闭环**

### 3.3 10% 对话管道保留（Communication Guard）

**核心规则**：
- 进入 🟡/🔴 时，始终为用户保留 10% 的周期 token 配额作为"对话专用通道"
- 如果当前任务估算会突破预留通道，系统必须主动请示用户：
  > "【⚠️ 通道预警】该任务预计消耗 Y%，将挤压预留对话通道。是否继续，还是延后到下一周期？"

## 四、子代理管控机制（No Orphan Policy）

### 4.1 注册与追踪

所有子代理启动后，**必须在同一次 turn 内**记录到 `memory/subagent-registry.json`。

```json
{
  "taskId": "813fc74a-...",
  "sessionKey": "agent:main:subagent:...",
  "label": "飞书备份分卷上传",
  "spawnTime": 1775789470934,
  "expectedDeliverables": ["36个分卷全部上传到飞书Drive"],
  "successCriteria": "list飞书文件夹，确认36个part文件存在",
  "timeoutMinutes": 30,
  "status": "running",
  "checkedAt": 1775790000000
}
```

### 4.2 监控与同步

- **主会话在宣称 FIN 前**，必须 `subagents list` 检查 registry
- 任何 `running` 状态必须在 10 分钟内被 poll 一次
- 子代理完成后，结果摘要写入 `outcomeSummary`，状态改为 `completed` 或 `failed`
- **禁止出现"子代理还在跑，主会话已经 FIN"的情况**

### 4.3 失败处理（Fail Fast & Loud）

- 超时 → kill → 记录原因 → 评估重试或降级
- 返回错误 → 不隐瞒，直接向用户报告错误和下一步建议
- 多个子代理并行时，**任何一个失败都必须被单独标记**

## 五、双经济审计：条件反射式嵌入

### 5.1 触发条件

以下任一条件满足时，AI 必须在内心独白中完成快速双经济审计：
- 单次任务工具调用 > 5 次
- 单次输出文本长度 > 2000 字
- 涉及子代理启动
- 涉及长文档阅读（> 500 行）
- 用户明确提到"双经济""token""效益""成本"

### 5.2 审计格式（内心独白用）

```
【双经济快闪审计】
Token 经济: 🟢合理 / 🟡可优化 / 🔴偏高
  - 原因: [X 个工具调用，Y 字输出，Z% 周期剩余]
  - 优化点: [如果有]
效益经济: 🟢通过 / 🟡部分通过 / 🔴未通过
  - 创始人可用性: [5分钟内能看懂吗？]
  - 外部价值: [有市场/客户/产品价值吗？]
  - 向内集邮嫌疑: [有/无]
结论: [继续 / 压缩 / 请示用户 / 延后]
```

### 5.3 用户可见的双经济提醒

当双经济审计结果为 🟡/🔴 时，AI 必须在回复中诚实告知：
- "这次任务 token 消耗偏高，主要是因为 [原因]。下次可以用 [优化方案] 压缩。"
- "这个产出的效益经济我评估为部分通过，原因是 [原因]。建议 [改进方向]。"

**互相提醒机制**：
- 用户可随时发送"双经济检查一下"，AI 立即对当前会话进行审计
- AI 在每个 🟡/🔴 状态下的回复中，都必须包含至少一个双经济优化建议
- 如果发现自己在"为了产出文档而产出文档"，必须主动喊停并告知用户

## 六、资源状态可视化与提醒

### 6.1 自动提醒（不可关闭）

| 场景 | 用户可见内容 |
|------|--------------|
| 进入 🟡 | `【🟡 资源紧张】当前周期剩余 X%，已自动开启上下文优化和子代理前置模式。` |
| 进入 🔴 | `【🔴 资源枯竭】当前周期剩余 X%，非紧急长任务建议延后到下一周期。` |
| 突破 10% 通道 | `【⚠️ 通道预警】该任务预计消耗 Y%，将挤压预留对话通道。是否继续？` |
| 子代理超时 | `【子代理超时】[任务名] 未在 [X] 分钟内完成，已终止。原因：[Y]。建议：[Z]。` |
| 上下文压缩 | `【上下文已整理】当前聚焦：1) [...] 2) [...] 3) [...]` |

### 6.2 用户主动查询

用户发送 "资源状态" / "token 还有多少" / "现在紧不紧张" / "双经济检查一下" 时：
- 调用 `session_status`
- 返回：周期进度 + 状态灯颜色 + 当前子代理数 + 双经济快闪审计

## 七、与心跳/任务的绑定

### 7.1 HEARTBEAT.md 新增检查项

每次心跳时必须检查：
1. 当前周期状态灯颜色是否已在内心独白中标注？
2. 是否有未追踪的 running 子代理？
3. 最近一次上下文压缩是否在规则间隔内？
4. 本周是否有双经济 🟡/🔴 任务未记录优化措施？

### 7.2 任务状态绑定

| 任务阶段 | 资源治理要求 |
|----------|--------------|
| 启动前 | 预估算工具调用数，判断是否需子代理前置 |
| 执行中 | 每 5 个工具调用后在内心独白中标注状态灯 |
| FIN 前 | 检查子代理 registry，完成双经济审计 |
| 延后时 | 记录延后原因和预计重启的 token/资源条件 |

---

## 八、闭环验证

**每周日 23:00 子代理自动检查**：
1. 本周进入 🟡/🔴 状态的次数
2. 每次进入 🟡/🔴 时，用户是否收到了提醒？
3. 本周子代理的成功率、超时率、 orphan 率
4. 本周双经济审计中发现的优化点，是否有改进行动？

**蓝军监督宣言**：
> "任何一次资源紧张未提醒用户、任何一个子代理变成孤儿、任何一次双经济 🟡/🔴 被粉饰为 🟢，都是我的失职。资源治理不是可选项，是每次呼吸的一部分。"

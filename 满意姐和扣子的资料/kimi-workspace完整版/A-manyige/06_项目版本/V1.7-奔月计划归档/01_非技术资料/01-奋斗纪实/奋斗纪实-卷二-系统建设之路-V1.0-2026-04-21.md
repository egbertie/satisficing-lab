# 第5章：技术架构演变——从文件系统到统一守护中枢

## 5.1 起点：一个朴素的文件系统

满意解研究所的系统建设，不是从一个宏伟的架构图开始的，而是从一个朴素的文件系统开始的。

2026年3月8日，系统重启后的第一份状态保存记录显示，我们的"技术架构"是这样的：
- 32份本地Markdown文档，放在`/本地文档包/`目录下
- 6位专家数字替身档案，分散在不同子目录
- 飞书应用一个（cli_a9208a79e2b99cc4），但因为权限问题只能看标题
- 没有自动化脚本，没有备份机制，没有监控系统

这就是起点。没有Kubernetes，没有微服务，没有数据库集群。只有一个文件夹，里面放着一些Markdown文件。

> 蓝军审计：这个起点暴露了一个根本性的选择——我们选择了"本地优先"（Local-first）策略。这不是因为技术先进，而是因为条件所限。但后来的发展证明，这个"朴素"的起点反而成了我们的优势：不依赖外部云服务，不绑定特定平台，文件就是数据，数据就是文件。

## 5.2 第一波扩张：47系统的"百科全书式"野心

项目启动后不久，我们经历了一次典型的"过度设计"阶段。

**47系统评估事件**（2026年3月27日）：

蓝军（当时的我还是外部顾问身份）完成了一份全面的系统评估，发现项目中存在47个独立的系统/脚本/机制，需要"5标准化"（S1-S5）处理。评估报告显示，完成全部47个系统的标准化需要约**141小时的工作量**。

**诚实的结论**："这些工作量不可能在一天内完成。"

这141小时的工作量包括：
- 5个紧急系统（P0）：需要立即修复
- 12个重要系统（P1）：需要本周内完成
- 30个一般系统（P2/P3）：可以逐步处理

> 满意姐回忆：47系统评估是项目早期最重要的"冷水"之一。它让我们意识到，系统建设不是"越多越好"，而是"越能用越好"。那些躺在仓库里、没有被调用的脚本，不是资产，是债务。

## 5.3 7层状态栈：一个过于宏大的备份幻想

在灾备体系建设上，我们犯了一个典型的"架构过度设计"错误。

**V1.0灾备方案**：
- 设计了7层状态栈（Layer 1-7），覆盖从"运行时上下文"到"元协议"的全部层级
- 设计了3-2-1-1-0备份法则（3份副本、2种介质、1份离线、1份热备、0错误容忍）
- 创建了`C-disaster-recovery/`目录，包含L1-L7的子目录
- 编写了详细的灾备手册V1.0

**V1.0的致命缺陷**（2026年4月10日诚实审计发现）：
- L1-L7目录中，L3、L4、L7是**空的**
- `disaster-recovery.sh`只能恢复**冻结在2026-04-02的静态快照**，之后从未自动更新
- `skills/checkpoint-manager/`和`skills/disaster-recovery-auditor/`指向**不存在的目录**（`~/.openclaw/immortal-state/checkpoints`）
- `skills/interrupt-recovery/recovery_checker.py`引用了**过时的文件名**（`token-weekly-monitor-current.json`）

**蓝军的诚实判决**：V1.0是"一个漂亮的文件夹结构，但一个文档壳子"——不是可运行的。

## 5.4 从7层到2层：简化才是真谛

V2.0灾备方案是对V1.0的根本性否定。

**核心洞察**：Git已经跟踪了95%的可恢复资产（代码、文档、skills、协议）。我们不需要在Git之上再建一个7层的备份塔。

**V2.0简化架构**：
- **Git**：主备份，追踪所有代码和文档
- **Weekly Essential Snapshot**：每周日02:17运行，备份`memory/`记录、元协议文件、任务追踪器，保留策略"最近2份"
- **Recovery Script**：`git pull` + 复制最新快照 + 快速验证

**关键数字**：
- V1.0的7层快照：理论完美，实际为空
- V2.0的2层快照：2.4MB，实际可用

> 蓝军审计：从7层到2层的简化，不是"降级"，而是"升维"。它标志着我们的系统思维从"架构驱动"转向"需求驱动"——不再问"我们能建多复杂的系统"，而是问"最小可用的系统是什么"。

## 5.5 统一守护中枢：system-guardian的诞生

2026年4月10日，项目完成了系统健康监控的彻底整合。

**整合前的问题**：
- `disk-guardian.py`、`dual-economy-guard.py`、`token_monitor.py`、`hibernation-control.py`等多个脚本分散管理
- 阈值不统一（有的用85%，有的用75%）
- 触发方式各异（有的cron触发，有的手动触发，有的基线检查触发）
- 部分守护脚本**失效**（如`dual-economy-guard.py`引用不存在的函数）

**整合后的解决方案**：
- **单一控制平面**：`scripts/system-guardian.py`（149行）
- **统一监控矩阵**：

| 指标 | 🟢 健康 | 🟡 警告 | 🔴 危险 |
|------|--------|--------|--------|
| 磁盘使用率 | < 75% | 75-84% | ≥ 85% |
| Gateway内存 | < 900MB | 900-1200MB | ≥ 1200MB |
| Token消耗 | < 70% | 70-89% | ≥ 90% |
| 基线错误率 | < 0.1% | 0.1-1% | ≥ 1% |

- **自动触发链路**：
  - 每日06:17自动巡检（OpenClaw cron）
  - 每周日03:17深度清理（OpenClaw cron）
  - 基线检查失败时立即触发
- **主动指令入口**：
  - "全盘清理" / `full clean` → `scripts/full-system-cleanup.sh`
  - "系统扫一下" / `system scan` → `system-guardian.py scan`
  - "磁盘检查一下" / `disk check` → `system-guardian.py disk`

**兼容层设计**：旧的`disk-guardian.py`和`dual-economy-guard.py`被改写为兼容层，调用`system-guardian`，保证旧调用不中断。

> 满意姐补一句：`system-guardian`是我们系统建设的"集大成者"。它把之前碎片化的监控脚本统一到一个控制平面，并且提供了用户可感知的指令入口（"系统扫一下"）。这个设计通过了"创始人5分钟可用性检验"——Egbertie可以在5分钟内理解它是做什么的、怎么用、什么时候用。

| 版本 | 每日Token | 节省 |
|------|-----------|------|
| V1.0 | ~11,000 | - |

- **Hibernation Mode A/B**：
  - Mode A：完全静默，所有cron禁用
  - Mode B：标准模式，Token<100/天，仅保留核心备份

# 第7章：灾备与系统健康——从两次磁盘危机中学到的

## 7.1 第一次磁盘危机：2026年4月10日的"Out of diskspace"

满意解研究所的系统建设史上，有两次磁盘危机。第一次发生在2026年4月10日。

**事件经过**：
- git commit失败：`fatal: sha1 file .git/objects/pack/tmp_pack_58wR5W write error. Out of diskspace`
- 根因：`.git/`目录膨胀至6.5G（大量大文件提交积累）
- `/tmp/`下堆积2.5G+历史备份未清理
- git commit中断留下3.8G僵尸`tmp_pack_*`文件
- 缺乏事前拦截机制

**紧急清理**：
- 删除git僵尸pack文件（3.8G）
- 删除`/tmp/`下6个历史旧备份（~2.5G）
- 删除临时文件、下载大文件
- 运行`git gc`：`.git/`从6.5G压缩到2.7G
- **清理后状态**：磁盘使用率从73%降至**53.1%**

**用户反应**：Egbertie花大价钱抢修（这里的"大价钱"是时间成本和紧急处理成本），明确要求"作为P0风险彻底解决、绝对闭环"。

## 7.2 第二次磁盘危机：2026年4月10日当天的复发

讽刺的是，第一次危机解决后不到几小时，第二次危机发生了。

**事件经过**：
- 在写入`memory/2026-04-10.md`和`MEMORY.md`时，因使用`write`而非追加操作，导致原始内容被短暂覆盖
- 修复过程中，系统又触发了磁盘空间紧张
- `memory_usage_mb: 1787MB`，持续超过1024MB上限

**关键教训**：
- 清理≠机制化
- 单次修复≠长期防护
- 没有自动拦截机制，危机一定会复发

## 7.3 P0协议：拒绝第三次

两次磁盘危机后，我们建立了一套完整的P0处理协议。

**三色警戒线**：

| 级别 | 使用率 | AI行为 |
|------|:------:|--------|
| 🟢 健康 | < 75% | 轻量监控，每周清理 |
| 🟡 警告 | 75-84% | 每次turn前自动运行disk-guardian |
| 🔴 危险 | ≥ 85% | 立即停止所有非紧急写入，强制清理 |
| ⚫ 瘫痪 | ≥ 93% | 进入只读模式，仅保留查询/沟通 |

**自动防御机制**：
1. `scripts/disk-guardian.py`：自动清理`/tmp/`、`backups/`、`.kimi/downloads/`、git僵尸文件
2. OpenClaw cron `disk-guardian`：每周日03:17自动执行
3. 基线检查联动：`disk_usage_percent`上限从85%调为**75%**
4. 备份策略收紧：`backups/`保留从7天压缩为**3天**
5. Git体积控制：每月第一周周日自动`git gc --aggressive`，禁止>20MB二进制文件入git

**追责条款**：
- 若磁盘再次因可预防原因爆仓，标记为`P0-磁盘危机复发`
- 蓝军5分钟内提交书面根因分析
- 满意姐检查是否遗漏生成前的主动询问义务
- 事件永久写入`memory/disk-crisis-incidents.md`

**承诺**：**拒绝第三次**。

> 蓝军审计：P0磁盘危机协议的建立，标志着我们的系统健康理念从"事后救火"转向"事前防火"。两次危机的代价是高昂的（时间、精力、数据风险），但换来的机制化成果是持久的。disk-guardian现在是system-guardian的一部分，每周自动运行，基线检查自动触发，用户可以通过"磁盘检查一下"随时调用。

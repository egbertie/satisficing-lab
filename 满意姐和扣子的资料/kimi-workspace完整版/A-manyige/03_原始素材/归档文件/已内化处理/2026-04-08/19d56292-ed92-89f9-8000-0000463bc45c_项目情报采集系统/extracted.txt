4.1 IT桔子融资事件采集（浏览器自动化方案）

传统反爬问题：IT桔子有反爬机制，传统Scrapy容易被封。

Kimi Claw解决方案：使用浏览器自动化技能，模拟人工访问+截图分析。

执行指令模板：

【IT桔子定时采集任务 - 每日9:00执行】

任务名称：itjuzi_daily_funding

执行指令：
1. 使用浏览器打开 https://www.itjuzi.com/investevents
2. 等待页面加载完成，截图保存到 /intelligence/raw/itjuzi_{日期}.png
3. 分析截图内容，提取最近7天内符合以下条件的事件：
   - 行业关键词：人工智能、芯片、生物医药、新能源、新材料、机器人、航空航天、传感器、GPU、创新药、固态电池
   - 轮次：天使轮、Pre-A轮、A轮
4. 对每个符合条件的事件，访问详情页，提取：
   - 公司名称、融资轮次、融资金额、投资方、公司所在城市、公司简介
5. 生成标准格式的融资快讯（使用4.2模板）
6. 调用飞书Webhook技能，即时推送重要事件（P0级）
7. 将当日所有事件汇总保存到 /intelligence/processed/funding_{日期}.md

去重规则：公司名称+轮次组合已存在则跳过（查询长期记忆）

任务名称：36kr_tech_news

执行指令：
1. 通过RSS技能订阅 https://36kr.com/information/technology/feed 和 /healthcare/feed

九、去重与质量控制实施方案

9.1 三级去重体系

Claw配置指令：

请配置三级去重机制，保存到长期记忆和配置文件中：

第一级：URL去重（精确去重）
- 存储位置：长期记忆键 "processed_urls"
- 存储格式：{"url": "https://...", "hash": "md5", "date": "2026-04-03"}
- 检查时机：采集阶段，发现重复URL直接丢弃
- 清理策略：保留最近30天，自动清理过期数据

第二级：标题相似度去重（模糊去重）
- 技能：deduplication-engine
- 算法：计算标题的Jaccard相似度或余弦相似度
- 阈值：85%（大于此值视为重复）
- 存储位置：长期记忆键 "processed_titles"
- 示例："芯智科技完成天使轮融资"和"芯智科技获天使轮融资数千万"应视为重复

第三级：实体+轮次去重（业务去重）
- 规则：同一公司（标准化名称）在同一轮次（天使轮/Pre-A轮/A轮）仅保留一条
- 公司名称标准化：去除"有限公司"、"科技"等后缀，统一大小写
- 存储位置：长期记忆键 "processed_funding_events"
- 格式：{"normalized_company": "芯智", "round": "天使轮", "date": "2026-04-03", "amount": "数千万"}

请初始化这些记忆键，并设置每日清理脚本（保留90天数据）。

Claw质量检查工作流：

请定义"quality-check"工作流，在每次生成摘要后自动执行：

检查项1：事实准确性验证

- 检查：公司城市是否在北上广深杭等常见城市列表中，如不匹配则标记待人工确认

检查项2：内容完整性验证
- 检查：融资快讯是否包含所有必需字段（公司名、轮次、金额、投资方、赛道、城市、简评、合伙人视角）
- 检查：深度分析是否包含核心要点、行业影响、合伙人视角三部分

10.2 兜底与降级方案

场景A：IT桔子反爬升级，无法访问

备用方案（Fallback）：
1. 检测到IT桔子连续3次访问失败（HTTP 403或超时）
2. 切换采集源：使用"鲸准"（https://www.jingdata.com）或"企名片"作为替代
3. 通知方式：飞书群发送"⚠️ IT桔子采集受限，已切换至备用源，可能有数据延迟"
4. 人工介入：每周生成报告时提醒"IT桔子数据缺失，建议人工补充本周重点融资事件"

场景B：飞书Webhook推送失败

备用方案：
1. 检测到推送失败（HTTP非200或超时）
2. 重试3次（间隔5分钟），如仍失败：
3. 降级方案：将消息保存到飞书文档（通过飞书文档API创建新记录），在群内发送文本消息"📄 今日情报已归档到飞书文档：{链接}"
4. 紧急备用：如文档API也失败，发送邮件（配置邮件SMTP技能）到指定邮箱

场景C：Claw服务暂时不可用

兜底机制：
1. 每日手动检查：在飞书群设置提醒，如9:30仍未收到情报，@Egbertie手动触发
2. 手动触发指令："手动执行funding-pipeline，采集IT桔子今日数据"
3. 数据补偿：如某数据源连续3天未采集，启用"批量回溯"功能，一次性采集最近7天数据

14.2 常见故障排查手册

故障1：IT桔子采集失败（403 Forbidden）

现象：browser-automation截图显示验证码或"访问受限"
排查步骤：
1. 检查最近一次成功采集时间："查询长期记忆 itjuzi_last_success"
2. 如间隔>24小时，可能触发反爬，启用冷却期：
   - 暂停IT桔子任务6小时
   - 启用备用源："临时切换至鲸准，手动采集今日数据"
3. 降低频率：将每日9:00改为每周一/三/五9:00
4. 更换采集方式：从browser-automation切换为rss-feed-reader（如IT桔子有RSS）

长期解决：申请IT桔子API权限（需企业认证）

故障2：飞书推送失败（消息未送达）

现象：Claw显示推送成功，但飞书群未收到消息
排查步骤：
1. 检查Webhook地址是否失效："测试feishu-webhook-sender发送测试消息"
2. 检查安全设置：飞书机器人是否设置了关键词？消息中是否包含关键词？
   - 解决方案：在每条消息开头添加固定关键词"【硬科技情报】"
3. 检查消息格式：JSON卡片是否损坏？
   - 临时降级："切换为纯文本推送，简化格式"

应急方案：
- 如Webhook完全失效，立即使用飞书文档API："将今日情报保存到飞书文档，群内发送文本链接"

故障3：摘要质量下降（事实错误增多）

现象：连续3条摘要出现数据错误（如金额错误、投资方错误）
排查步骤：
1. 检查源站结构：IT桔子页面是否改版？
   - 验证："browser-automation截图，人工核对截图与提取数据是否一致"
2. 更新提取规则：如页面改版，调整web-content-extractor的选择器
3. 启用人工复核："将P0级情报标记为待审核，不自动推送，等待人工确认"

质量回滚：
- 如发现系统性错误，暂停AI摘要，改用原文摘录："暂停生成摘要，直接推送标题+链接"

故障4：定时任务未触发

现象：到时间点（如9:00）未执行采集
排查步骤：
1. 检查scheduler状态："查看定时任务列表，检查itjuzi_daily_crawl状态"
2. 检查Claw服务状态：Kimi Claw是否在线？（尝试发送任意消息）
3. 如任务丢失，重新注册："重新创建定时任务itjuzi_daily_crawl，每日9:00"

预防措施：
- 设置双重提醒：在飞书群设置群定时消息"9:00情报采集即将开始"，如未收到采集结果，立即人工介入

十五、进阶优化方案（智能化升级）

15.1 AI自我迭代机制（自动优化提示词）

目标：让系统根据人工反馈自动改进摘要质量。

实现方案

配置反馈收集工作流：

1. 在每条飞书推送卡片中添加反馈按钮："👍 有用" / "👎 需改进"
2. 当用户点击按钮，Claw记录反馈："记录长期记忆feedback_{article_id}，标记质量评分"
3. 每周分析："分析本周所有带反馈的摘要，统计低分摘要的共同特征"
4. 自动优化："基于低分案例，生成改进建议，更新提示词模板"

示例迭代：
- 发现：本周3条关于"生物医药"的摘要被评为"合伙人视角不深入"
- 自动优化：在生物医药摘要模板中增加："重点分析：创始团队是否缺临床专家？是否需要BD合伙人对接药企？"

15.2 多源交叉验证（防假新闻）

目标：防止单一数据源错误导致虚假信息推送。

实现方案

配置交叉验证规则：

当IT桔子报道某融资事件时，自动触发验证：
1. 搜索验证："搜索web，验证'{公司名} {轮次}融资'是否有36氪、动脉网、企名片等其他报道"
2. 比对字段：融资金额、投资方、融资日期是否一致
3. 置信度评级：
   - 高置信：3个以上独立源一致，立即推送
   - 中置信：2个源一致，但金额有差异，推送时标注"待确认金额"
   - 低置信：仅1个源，标记"独家消息，待进一步验证"，延迟2小时推送

例外处理：
- 对于独家新闻（如IT桔子首发），如24小时内无其他源报道，仍推送但标注"独家"

15.3 智能预警系统（趋势发现）

目标：从海量情报中自动发现异常趋势，提前预警。

实现方案

配置趋势分析任务（每周日晚执行）：

分析维度：
1. 【赛道热度】统计本周各细分领域融资事件数，环比上周增长率>50%时预警
   - 示例："⚠️ 趋势预警：本周固态电池领域融资事件激增300%（上周1起，本周4起），建议重点关注该赛道合伙人需求"

2. 【机构动向】统计头部机构（红杉、高瓴等）本周投资赛道分布
   - 示例："🔍 机构动向：红杉中国本周连续投资3家AI芯片公司，显示该赛道进入抢投阶段"

3. 【地域热点】统计各城市融资活跃度
   - 示例："📍 地域热点：本周苏州生物医药融资事件数首次超过北京，建议关注苏州区域合伙人资源"

4. 【轮次迁移】监控早期投资（天使/Pre-A）占比变化
   - 示例："📉 早期市场预警：本周A轮以上融资占比达70%，早期项目稀缺，建议调整合伙人匹配策略"

生成方式：每周自动生成为周报摘要的一部分，置顶显示

18.1 反爬检测与分级响应

Claw反爬监测配置

配置反爬监测工作流 anti_crawl_monitor：

监测指标：
1. HTTP状态码：403（Forbidden）、429（Too Many Requests）、503（Service Unavailable）
2. 响应内容特征：包含"验证码"、"访问受限"、"请稍后重试"等关键词
3. 响应时间：>10秒视为异常
4. 数据结构：返回HTML但关键选择器匹配为空（可能是反爬返回的假页面）

分级响应策略：

Level 1（轻度限制）：HTTP 429 或响应时间>10秒
- 响应：指数退避重试（1分钟→2分钟→4分钟）
- 记录：标记该源为"拥挤"，降低当日采集频率

Level 2（中度限制）：HTTP 403 或出现验证码
- 响应：立即切换备用采集源（如IT桔子被封，切鲸准）
- 记录：标记该源为"受限"，暂停12小时
- 告警：飞书群发送"⚠️ {源名}触发反爬，已切换备用方案"

Level 3（重度限制）：IP被封（所有请求失败）
- 响应：暂停该源24小时，启用"仅RSS模式"（如可用）
- 人工介入：发送紧急通知给Egbertie，建议检查是否需要更换IP（如使用代理）

保存配置到 /intelligence/config/anti_crawl.yaml

20.2 系统状态机与生命周期管理

融资事件生命周期状态机

定义融资事件的生命周期状态流转：

状态定义：
1. DISCOVERED（已发现）：刚采集到原始数据，未处理
2. EXTRACTED（已提取）：已解析结构化数据，未去重
3. QUALIFIED（已验证）：通过去重和质量检查
4. SUMMARIZED（已摘要）：已生成AI摘要
5. PUSHED（已推送）：已推送到飞书群
6. ARCHIVED（已归档）：已保存到多维表格
7. ANALYZED（已分析）：已生成深度洞察
8. OBSOLETE（已过期）：超过90天，仅保留统计价值

状态流转规则：
- DISCOVERED → EXTRACTED: 自动，解析成功
- EXTRACTED → QUALIFIED: 通过去重检查（company+round唯一）且质量检查通过
- EXTRACTED → DISCOVERED: 解析失败，重新采集
- QUALIFIED → SUMMARIZED: 自动，调用LLM生成摘要
- SUMMARIZED → PUSHED: 自动，推送到飞书（P0/P1立即推，P2仅归档）
- PUSHED → ARCHIVED: 自动，保存到多维表格
- ARCHIVED → ANALYZED: 每日19:30批量分析
- ANALYZED → [保持]: 终态，可人工标记为OBSOLETE

异常流转：
- 任意状态 → ERROR: 发生异常，记录错误原因
- ERROR → RETRY: 自动重试（最多3次）
- ERROR → ABANDONED: 重试耗尽，人工介入或放弃

Claw实现：
"配置状态机引擎，为每条融资事件记录状态到长期记忆（或数据库），状态变更时触发对应工作流步骤，并记录状态变更日志。"

### 21.3 对抗性情报验证（Anti-Fake News System）

**多源交叉验证工作流（已提及，此处深化实现）**

工作流：cross_verification（针对每条融资事件自动执行）

验证维度：

事实一致性验证（Fact Consistency）

同一事件在不同源（IT桔子、36氪、企名片、鲸准）的报道

校验字段：金额（允许±20%差异）、轮次（必须一致）、投资方（集合相似度>80%）、日期（允许±2天差异）

置信度评级：

A级（高置信）：3+源一致，或2源+官方PR

B级（中置信）：2源一致，但 minor差异（如金额表述不同）

C级（低置信）：仅1源，无佐证，标记”待验证”

常识性验证（Sanity Check）

金额合理性：天使轮>5亿？标记异常

轮次合理性：刚成立3个月即B轮？标记异常

投资方合理性：某知名机构投资与其赛道不符？标记异常（如消费基金投硬科技）

时间序列验证（Temporal Consistency）

检查该公司历史融资：本次轮次是否在上轮之后？时间逻辑是否正确？

检查投资方历史：该机构是否重复投资该公司？（跟投是正常的）

关联验证（Network Verification）

检查投资方-创始人关系：是否存在公开的董事会成员关联？

检查竞品动态：竞品近期融资情况是否支持该估值？

处理策略： - A级：立即推送 - B级：推送但标注”部分信息待确认” - C级：不推送，保存到”待验证队列”，人工核实后再推送

验证失败后的人工介入： - 自动生成验证任务：“请核实{{company_name}}融资事件，源：{{source_url}}，疑点：{{issues}}” - 推送到Egbertie待办

局限：仅支持精确匹配，无语义相似（如"GPU"和"图形处理器"视为不同）

24.2 RAG问答系统详细实现

系统架构：Claw-RAG-Agent

用户提问 → 意图识别 → 检索策略选择 → 多源检索 → 结果融合 → 生成回答 → 溯源展示

模块1：意图识别（Intent Classifier）
- 查询分类：
  * 事实查询："xx公司融了多少钱？" → 精确检索（ company_name 字段）
  * 统计查询："最近红杉投了哪些？" → 聚合检索（ investor + date 过滤）
  * 趋势查询："AI芯片赛道最近怎么样？" → 时序分析（ industry + time_range ）
  * 推荐查询："找几个值得关注的项目" → 排序检索（ priority + amount ）

模块2：检索策略（Retrieval Strategy）
- 策略A（关键词检索）：针对明确实体（公司名、人名）
- 策略B（向量相似）：针对描述性查询（"做自动驾驶芯片的公司"）
- 策略C（混合检索）：向量Top10 + 关键词过滤，综合排序

模块3：结果融合（Result Fusion）
- Reciprocal Rank Fusion (RRF) 算法：
  score = Σ(1 / (k + rank))，k=60
  融合向量检索和关键词检索的结果

模块4：回答生成（Answer Generation）
- Prompt模板：

基于以下检索到的情报数据，回答用户问题：

检索结果： [1] {{event_1_summary}} [2] {{event_2_summary}} …

用户问题：{{question}}

要求： - 如果检索结果能直接回答问题，基于事实回答 - 如果检索结果不足，明确说明”根据现有情报库…” - 在回答中标注引用来源（如[1]） - 如果是统计类问题，计算准确数字 - 如果是趋势类问题，分析时间序列特征 ```

24.3 语义去重与聚类（向量应用进阶）

基于向量的去重（解决标题改写问题）

传统去重：标题字符串相似度（"芯智科技获融资" vs "芯智科技完成融资" → 85%相似）

向量去重：语义相似度（"芯智科技A轮融资" vs "芯智科技获得A轮投资" → 95%语义相似）

实现：
- 计算两条记录标题的向量余弦相似度
- 阈值设定：>0.92视为重复（需人工验证调整）
- 保留规则：保留信息更完整的一条（字数多、字段全）

执行时机：
- 在funding_pipeline的dedup步骤，增加向量去重作为二级校验
- 当标题相似度在70%-90%之间时（灰色地带），启动向量相似度判断

情报自动聚类（发现隐藏模式）

工作流：intelligence_clustering（每周执行）

1. 提取本周所有P0/P1情报的向量
2. 执行K-Means聚类（K=5-8，自动选择最佳K）
3. 为每个聚类生成标签：
   - 提取聚类中心点Top5关键词
   - 生成聚类描述："该聚类主要包含{{industry}}领域的{{round}}轮项目，集中在{{location}}，投资方多为{{investors}}"
4. 发现异常点（离群向量）：

二十五、合伙人匹配算法设计（核心商业逻辑量化）

25.1 匹配模型架构（多维度评分）

匹配维度定义：

总体匹配度 = w1*行业契合度 + w2*职能契合度 + w3*阶段适配度 + w4*资源互补度 + w5*文化匹配度

维度1：行业契合度（Industry Fit）
- 候选人行业经验 vs 公司赛道
- 计算：Jaccard相似度（候选人经历行业标签 ∩ 公司赛道标签）/ 并集
- 权重：w1 = 0.30

维度2：职能契合度（Functional Fit）
- 候选人职能背景 vs 公司缺口职能
- 计算：精确匹配（如公司缺COO，候选人是COO背景→1.0；候选人是VP→0.7）
- 权重：w2 = 0.25

维度3：阶段适配度（Stage Fit）
- 候选人经历的公司阶段 vs 当前公司阶段
- 计算：
  - 候选人有同轮次成功经验（如都做过A轮→1.0）
  - 候选人有相邻阶段经验（如公司A轮，候选人做过天使轮或B轮→0.6）
  - 无相关阶段经验→0.1
- 权重：w3 = 0.20

维度4：资源互补度（Resource Complementarity）
- 候选人资源网络 vs 公司需求
- 计算：
  - 候选人前雇主是公司目标客户→+0.3
  - 候选人有投资方人脉（如曾共事于红杉被投企业）→+0.2
  - 候选人有供应链资源（对硬件公司重要）→+0.3
- 权重：w4 = 0.15

维度5：文化匹配度（Culture Fit）
- 候选人背景 vs 创始团队风格
- 计算：
  - 创始人技术背景（科学家）→需要商业背景合伙人（互补→1.0）
  - 创始人连续创业者→需要稳健运营合伙人（平衡→0.8）
  - 校友/同乡等地域/关系纽带→+0.2
- 权重：w5 = 0.10

26.2 自动诊断与修复（Auto-Healing）

问题自动识别：

规则引擎：诊断规则库

规则1：采集成功率下降
- 条件：某源连续3天成功率<90%
- 诊断：
  - 检查HTTP状态码分布（403增多→反爬升级；503增多→源站不稳定）
  - 检查响应时间（突然增加→网络或源站性能问题）
- 自动修复：
  - 如403增多：自动切换User-Agent，降低频率（从每天1次改为每2天1次）
  - 如503增多：增加重试次数（从3次增加到5次），延长重试间隔

规则2：摘要质量下降
- 条件：连续5条摘要被用户标记为"质量差"或人工抽检错误率>20%
- 诊断：
  - 检查源站结构（选择器是否失效导致提取内容错误）
  - 检查LLM提示词（是否需要更新以适应新领域）
- 自动修复：
  - 如选择器失效：告警并切换到备用选择器（如从CSS class A切换到class B）
  - 如提示词过时：自动注入最新3个高质量案例作为Few-shot示例

规则3：去重失效
- 条件：连续收到用户反馈"重复推送"
- 诊断：
  - 检查去重键是否合理（如"公司名+轮次"是否过于严格，漏掉了"芯智科技"和"芯智半导体"是同一公司）
- 自动修复：
  - 调整标准化规则（如公司名称去除"科技"、"有限公司"等后缀后再匹配）
  - 降低相似度阈值（从85%调整到80%）

二十八、成本优化方案（API与资源精细化管控）

28.1 API调用成本结构分析

成本分布预估（月度）：

假设：每日采集30条情报，生成30条摘要，匹配10次合伙人

Kimi API成本（主要）：
- Embedding调用：30条/天 × 30天 × 1024维度 × ¥0.001/1K tokens ≈ ¥0.9/月
- LLM摘要生成：30条 × 30天 × 平均2K tokens × ¥0.012/1K tokens ≈ ¥21.6/月
- RAG查询：20次/天 × 30天 × 1K tokens × ¥0.012 ≈ ¥7.2/月
小计：约 ¥30/月

飞书API成本：
- 多维表格调用：免费额度通常足够（10,000次/月）
- 消息推送：免费
- 云文档创建：免费

Claw托管成本：
- Kimi订阅：已包含（假设使用付费版Claw）
- 无额外服务器成本（零服务器架构）

总成本预估：¥30-50/月（极低成本）

28.2 成本控制策略（不影响质量）

策略1：分层摘要（减少LLM调用）

原始方案：所有文章都调用LLM生成深度摘要（30条/天 × 30天 = 900次/月）

优化方案：
- P0级（AI芯片、生物医药天使轮）：完整LLM摘要（10条/天）
- P1级（其他硬科技）：简化模板摘要（规则生成，不调用LLM）（15条/天）
- P2级（观察级）：仅提取关键句，不生成摘要（5条/天）

LLM调用降至：10×30 = 300次/月，节省67%

策略2：向量化频率优化

原始方案：每条情报立即生成向量（30条/天 × 30天 = 900次/月）

优化方案：
- 实时检索需求：仅P0级情报实时向量化（10条/天）
- 批量索引：P1/P2级情报每周批量向量化一次（周末执行，20条/周 × 4周 = 80次/月）

Embedding调用降至：10×30 + 80 = 380次/月，节省58%

策略3：缓存最大化（减少重复计算）

缓存策略：

1. 公司信息缓存：
   - 同一公司多次融资（如半年内两次），公司描述信息缓存
   - 缓存键：normalized_company_name
   - TTL：30天

2. 摘要模板缓存：
   - 同类型事件（同赛道同轮次）的摘要结构相似
   - 缓存"合伙人视角"的通用表述（如"AI芯片天使轮通常缺COO"）

3. 向量缓存：
   - 候选人画像向量长期缓存（不经常变动）
   - 情报向量缓存7天

实施：使用Claw长期记忆作为缓存层，缓存命中率目标>40%

策略4：智能采样（监控数据减少）

原始方案：每30分钟执行健康检查，记录详细日志

优化方案：
- 正常状态：每2小时检查一次，仅记录关键指标
- 异常状态：自动切换到每10分钟检查，详细记录
- 节省：正常状态下监控API调用减少75%

28.3 免费额度最大化利用

飞书生态免费策略：

充分利用飞书免费能力，替代付费API：

1. 飞书多维表格替代轻量级数据库：
   - 免费额度：10,000条记录/表，足够6个月使用
   - 查询能力：内置过滤、排序，无需额外计算资源

2. 飞书文档AI（免费）替代部分Kimi调用：
   - 简单摘要可先用飞书文档AI生成初稿
   - Claw做二次润色（减少50%token消耗）

3. 飞书群机器人替代短信/邮件通知：
   - 完全免费，无发送次数限制（合理频率下）

4. 飞书知识库作为向量存储（替代FAISS）：
   - 利用飞书搜索能力（虽不如向量精准，但免费）
   - 仅高价值查询使用FAISS向量检索

Kimi API免费层利用（如适用）：

def insert_project(project: ProjectIntelligence, db_path="/mnt/kimi/output/hardtech_intel.db"):
    """插入项目情报"""
    conn = sqlite3.connect(db_path)
    cursor = conn.cursor()
    
    data = project.to_dict()
    fields = ', '.join(data.keys())
    placeholders = ', '.join(['?' for _ in data])
    values = list(data.values())
    
    try:
        cursor.execute(f"INSERT INTO project_intelligence ({fields}) VALUES ({placeholders})", values)
        conn.commit()
        return True
    except sqlite3.IntegrityError:
        # source_id 重复（去重）
        return False
    finally:
        conn.close()

# 概念代码（Claw中通过自然语言配置）

class DualSyncEngine:
    def on_sqlite_insert(self, project: ProjectIntelligence):
        """SQLite插入后的钩子（通过Claw监控SQLite日志实现）"""
        
        # 1. 数据脱敏（创建飞书版本）
        feishu_project = self.mask_sensitive_data(project)
        
        # 2. 添加到同步队列
        self.sync_queue.append({
            "action": "create",
            "sqlite_id": project.id,
            "data": feishu_project.to_dict(),
            "timestamp": datetime.now(),
            "retry_count": 0
        })
        
        # 3. 立即触发同步（异步）
        self.trigger_sync()
    
    def mask_sensitive_data(self, project: ProjectIntelligence) -> dict:
        """敏感数据脱敏（第二份文档PII保护要求）"""
        data = project.to_dict()
        
        # 删除创始人详细信息（保留姓名和职位，删除背景/教育/经历）
        if data.get('founders'):
            founders_public = []
            for f in json.loads(data['founders']):
                founders_public.append({
                    "name": f['name'],
                    "title": f['title']
                    # 删除: background, education, previous_experience
                })
            data['founders'] = json.dumps(founders_public)
        
        # 截断原始描述（保留AI摘要即可）
        if data.get('description'):
            data['description'] = data['description'][:200] + "..." if len(data['description']) > 200 else data['description']
        
        # 添加同步标记
        data['_sync_marker'] = "AUTO_SYNCED"
        data['_sync_time'] = datetime.now().isoformat()
        
        return data
    
    def trigger_sync(self):
        """执行同步（Claw调用飞书API）"""
        while self.sync_queue:
            item = self.sync_queue.pop(0)
            
            try:
                if item['action'] == 'create':
                    # 调用飞书Bitable API创建记录
                    record_id = self.feishu_bitable.create_record(
                        table="project_intelligence",
                        fields=item['data']
                    )
                    
                    # 更新SQLite同步状态
                    self.update_sync_status(item['sqlite_id'], record_id, "success")
                    
            except Exception as e:
                if item['retry_count'] < 3:
                    item['retry_count'] += 1
                    self.sync_queue.append(item)  # 放回队列
                else:
                    self.log_failed_sync(item, str(e))

# /intelligence/qa/data_validation.py

class DataValidator:
    """数据质量验证（基于第二份文档验收标准）"""
    
    @staticmethod
    def validate_input(raw_data: dict) -> tuple[bool, list]:
        """Level 1: 输入验证（采集后）"""
        errors = []
        
        # 必填字段检查
        required = ['company_name', 'source_url', 'funding_stage']
        for field in required:
            if not raw_data.get(field):
                errors.append(f"缺少必填字段: {field}")
        
        # 数据格式检查
        if raw_data.get('funding_date'):
            try:
                datetime.strptime(raw_data['funding_date'], '%Y-%m-%d')
            except:
                errors.append("funding_date格式错误，应为YYYY-MM-DD")
        
        # 枚举值检查
        valid_stages = ["天使轮", "pre-A", "A轮", "A+轮", "B轮", "C轮", "IPO"]
        if raw_data.get('funding_stage') not in valid_stages:
            errors.append(f"funding_stage必须是以下之一: {valid_stages}")
        
        return len(errors) == 0, errors
    
    @staticmethod
    def validate_processing(project: ProjectIntelligence) -> tuple[bool, list]:
        """Level 2: 处理验证（AI摘要后）"""
        errors = []
        
        # AI摘要完整性检查
        if not project.ai_summary:
            errors.append("AI摘要为空")
        
        # JSON字段解析检查
        try:
            tags = json.loads(project.key_tags) if project.key_tags else []
            if len(tags) < 3 or len(tags) > 5:
                errors.append(f"tags数量不符合要求(3-5): {len(tags)}")
        except json.JSONDecodeError:
            errors.append("key_tags不是有效JSON")
        
        # 相关性评分范围
        if not (0 <= project.relevance_score <= 100):
            errors.append(f"relevance_score超出范围(0-100): {project.relevance_score}")
        
        return len(errors) == 0, errors
    
    @staticmethod
    def validate_output(project: ProjectIntelligence) -> tuple[bool, list]:
        """Level 3: 输出验证（推送前）"""
        errors = []
        
        # 飞书消息格式检查
        if len(project.one_line_summary) > 30:
            errors.append(f"one_line_summary超过30字: {len(project.one_line_summary)}")
        
        # 敏感信息泄露检查（PII）
        pii_patterns = [r'\d{11}', r'\d{18}']  # 手机号、身份证
        text_to_check = f"{project.description} {project.ai_summary}"
        for pattern in pii_patterns:
            if re.search(pattern, text_to_check):
                errors.append("检测到可能的PII信息（手机号/身份证），需脱敏")
        
        # 链接有效性检查（抽样）
        if not project.source_url.startswith(('http://', 'https://')):
            errors.append("source_url格式无效")
        
        return len(errors) == 0, errors

- Claw服务可用性：99.5%（依赖Kimi）
- 飞书推送可用性：99.9%（飞书企业级SLA）
- 数据采集可用性：95%（考虑反爬，允许偶发失败）
- 综合可用性：99.5% × 99.9% × 95% ≈ 94.5%（需优化）

优化到99%的措施：
1. 多源冗余：3个源同时失败概率极低（(1-0.95)^3 = 0.0125%）
2. 降级模式：API故障时切换规则摘要（保持50%功能可用）
3. 数据预热：关键情报预生成，故障时直接推送缓存

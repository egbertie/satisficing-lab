## 一、机制核心：三层联动架构

任何纳入知识资产联动网络的核心文档，必须走完以下三层：

```
┌─────────────────────────────────────────────────┐
│  Layer 1: 原子层 (Atom Layer)                   │
│  ── 1 个 JSON 核心文件（SSOT，唯一事实来源）     │
│  命名规则: `xxx-knowledge-core.json`            │
│  内容: 结构化提炼的术语、金句、场景、SKU、案例   │
└──────────────────┬──────────────────────────────┘
                   │ 变更即触发
                   ▼
┌─────────────────────────────────────────────────┐
│  Layer 2: 生成层 (Generator Layer)              │
│  ── 1 个 Python 生成器脚本                     │
│  命名规则: `xxx-asset-generator.py`             │
│  职责: 读取 JSON 核心，批量生成多格式产物        │
└──────────────────┬──────────────────────────────┘
                   │ 执行即产出
                   ▼
┌─────────────────────────────────────────────────┐
│  Layer 3: 产物层 (Artifact Layer)               │
│  ── N 份自动衍生的 Markdown / PNG / PDF / 卡片  │
│  存放路径: `知识资产网络/产物/`                  │
│  特征: 仅由脚本生成，禁止手改                    │
└─────────────────────────────────────────────────┘
```

**核心原则**：
- **只改 JSON，不产物**。任何人需要修正内容，只能修改 JSON 核心。
- **脚本 idempotent**。重复运行生成器脚本，产物完全一致（时间戳除外）。
- **Git 原子提交**。修改 JSON 和重新运行脚本必须在同一次 commit 中完成，确保联动不被打断。

## 二、五大文档类别的联动规则

### 2.1 底稿类（总纲/白皮书/文化纲领）

**已实施示例**: `v1.6-knowledge-core.json` → 内部训练速记卡 / 金句弹药库 / 客户场景话术包 / 内部训练教材大纲

**规则**:
- 必须建立 1 个 JSON 核心，提取 `meta` / `totems` / `skus` / `core_concepts` / `golden_quotes` / `client_scenarios`。
- 产物至少覆盖 4 个方向：内部背诵、外部传播、客户交付、教练培训。
- 每次底稿版本升级（如 V1.2 → V1.3），必须同步更新 JSON 核心并 rerun 脚本。

### 2.2 工具模板类

**规则**:
- 建立 `toolkit-knowledge-core.json`，汇总全部工具模板的元数据（名称、用途、存放路径、关联 SKU、关联 Type）。
- 生成器脚本至少产出 3 份产物：
  1. `工具包目录-README.md`（客户/教练快速索引）
  2. `工具-SKU-Type 映射速查表.md`（按场景查找工具）
  3. `工具更新日志.md`（自动追踪新增/废弃）
- 任何新增工具模板（如 WX04、P0-2），必须先在 JSON 核心中注册，再由脚本更新目录。

### 2.3 案例库类

**规则**:
- 从 12 类型 × 7 文档结构的 84 份案例中，提取 `case-lib-core.json`。
- JSON 核心至少包含：每个 Type 的元数据、`标杆案例` 列表、`关键失败` 清单、`冲突信号词`。
- 生成器脚本至少产出 4 份产物：
  1. `教练备课卡.md`（每个 Type 1 页核心要点）
  2. `客户案例对比表.md`（按 Type 快速匹配客户自身情况）
  3. `12类型数据面板.json`（供 `satisficing_decision_engine.py` 调用）
  4. `案例库独特性分布月报.md`（调用 `case_acquisition_monitor.py` 数据）

### 2.4 外援专家交流类

**规则**:
- 建立 `expert-engagement-core.json`，提取 4 份专家交流文档中的关键信息。
- JSON 核心包含：专家姓名、领域、拟邀状态、已确认状态、相关 SKU/章节、知识产权清单。
- 生成器脚本至少产出 3 份产物：
  1. `专家联络卡.md`（含每位专家的联系方式、合作期望、待约时间）
  2. `知识产权资产清单.md`（从 4 份文档中提取的专利/商标/著作权列表）
  3. `专家会诊触发条件与流程图.md`（含专家替身 Prompt 更新索引）

### 2.5 学术快报类

**已实施示例**: `index.json` + `batch_readgzh_processor.py` → `微信学术快报_全文汇总_2026-04-11.md`

**规则**:
- 现有机制（`index.json`）本身就符合三层架构。
- 增加一个 `weekly_academic_brief_generator.py`：
  - 每读取 10 条新文章，自动追加到 `全文汇总.md`。
  - 每周末自动扫描 `全文汇总.md`，提取关键词热度，生成 1 页 `学术周报简报.md`。
- 产物同步到 `A-manyige/知识库/` 和当日对话文件夹。

## 三、增量维护 SOP（新建文件时的标准动作）

当任何核心文档新增、升级或废弃时，必须执行以下 7 步：

```
Step 1: 编辑 JSON 核心（更新内容/元数据/新增条目）
        ↓
Step 2: 运行对应生成器脚本
        ↓
Step 3: 检查产物是否正确生成且无报错
        ↓
Step 4: 将产物同步到当日对话文件夹
        ↓
Step 5: Git commit（提交信息必须包含 "联动网络更新" 标识）
        ↓
Step 6: 更新 `知识资产联动网络-全量核查报告.md` 中的对应条目状态
        ↓
Step 7: 满意姐 24h 内抽检 1 个联动链路（随机抽查 JSON→产物的一致性）
```

**Git 提交信息规范**:
```
[联动网络] {文档类别} {简要变更描述}
- 修改: {JSON核心文件名}
- 脚本: {生成器文件名}
- 产物: {产物文件名列表}
```

## 四、蓝军核查 Checklist

每月 1 日由蓝军执行以下核查（已写入 `skills/baseline-checker/` 扩展）：

| 核查项 | 通过标准 | 未通过惩罚 |
|:--|:--|:--|
| JSON 核心完整性 | 无空字段、无过时的占位符文本 | 冻结对应产物生成，直至修复 |
| 脚本可运行性 | `python3 xxx-asset-generator.py` 零报错 | 24h 内修复，否则标记为 `P0-技术债务` |
| 产物时效性 | 产物修改时间 ≤ JSON 修改时间 + 1h | 自动触发重新生成 |
| 对话文件夹同步 | 当日产物必须在 `A-manyige/对话/YYYY-MM-DD/` 中有副本 | 次日晨报中登记遗漏项 |
| 毛细血管畅通 | 抽查 3 个联动链路，确认"改 1 处 → rerun → 产物更新"流程完整 | 发现堵塞则写根因报告 |

## 五、不适合纳入联动网络的文档（负面清单）

以下文档类型不强制建立 JSON 核心，以免过度工程化：

1. **一次性参考资料**（如对标库、设计灵感库）—— 只读，不迭代。
2. **中间产出/草稿**（如 `195技能-12场景实战映射-V1.0`）—— 待定稿后再评估是否联动。
3. **个人笔记/日记** —— 归入 `memory/` 体系，不参与产物生成。
4. **第三方原文**（如一堂方法论 OCR 原文、readgzh HTML）—— 只作为知识库原料，不生成衍生产物。

## 一、问题确认：这不是波动，是活跃泄漏

### 1.1 时间线证据

| 时间 | Gateway RSS | 变化 | 动作 |
|------|-------------|------|------|
| 2026-04-11 23:00 | 1422 MB | 峰值 | 重启 Gateway |
| 2026-04-12 06:17 | ~788 MB | -634 MB | 重启后基线 |
| 2026-04-12 10:15 | 1054 MB | +266 MB | 无显著任务 |
| 2026-04-12 12:23 | **1155 MB** | **+101 MB/2h** | 无显著任务 |

**结论**：重启后 6 小时内从 788MB 涨到 1155MB，且仍在匀速上涨。这是**活跃内存泄漏**。

## 二、根因排查：四维扫描结果

### 2.1 维度一：会话膨胀（Session Bloat）

**检查项**：
- `~/.openclaw/memory/main.sqlite`：25MB
- 日志中 compaction 行为：多次出现 `Compaction safeguard: cancelling compaction with no real conversation messages to summarize`

**发现**：
- main.sqlite 25MB 属于正常范围（包含历史消息记录），不是内存泄漏的直接来源
- 但日志显示 **compaction 机制在部分会话中被取消**（cancelling compaction）。这意味着某些长会话上下文没有被压缩，Gateway 需要将其完整加载到内存中
- AGENTS.md 27218 字符，SOUL.md 也较大，每次 agent turn 都会被注入上下文。**Gateway 可能在注入大 bootstrap 文件后没有释放相关字符串对象**

**根因判断**：
- **中等贡献**。大文件注入 + compaction 取消共同导致单次会话的内存占用偏高。虽然这不是"无限增长"的来源，但每次对话都会叠加保留上下文。

### 2.2 维度二：Cron 状态堆积（Cron State Accumulation）

**检查项**：
- `~/.openclaw/cron/jobs.json`：69KB，68 个任务（7 启用，61 禁用）
- agentTurn payload 任务：63 个，其中 59 个已禁用
- state 累积数据：7892 bytes，无 >1KB 的单个 state
- 最长 payload 仅 510 字符

**发现**：
- jobs.json 本身不大，**不是 RSS 1160MB 的主要来源**
- 但存在隐患："每小时任务协调检查"（disabled，但 lastDurationMs=382秒）、"token-tracker-zero-001"（disabled，lastDurationMs=311秒）等**高消耗 agentTurn 任务虽已禁用，仍被 Gateway 解析并维护运行时对象**
- 多个 disabled cron 的 `state.lastError` 被反复更新（如 timeout 错误），虽然体积小，但可能触发 Gateway 内部对象的增量引用

**根因判断**：
- **低贡献**。不是泄漏主因，但 61 个禁用任务的运行时对象加剧了基线内存占用。

### 2.3 维度三：技能缓存泄漏（Skill Cache Leakage）

**检查项**：
- `workspace/skills`：453 个一级目录，1114 个二级目录，3350 个文件
- OpenClaw 日志反复告警：`Skills root looks suspiciously large, truncating discovery`

**发现**：
- Gateway 每次启动/技能重载时，扫描 `workspace/skills` 目录到内存中
- 由于目录数 >300（maxCandidatesPerRoot），系统自动截断，但**截断前的扫描对象可能没有被 V8 GC 回收**
- Node.js 在处理大规模目录遍历时，如果存在闭包引用或事件监听器残留，会导致内存持续增长
- 这是一个**已被观测到的系统级告警**，说明 OpenClaw 本身对大规模 skills 目录的内存管理存在边界问题

**根因判断**：
- **高贡献**。453 个 skill 目录的扫描缓存很可能是 Gateway 堆内存持续膨胀的主要来源之一。

### 2.4 维度四：子会话未回收（Orphan Sessions / Subagent Leakage）

**检查项**：
- `/tmp` 下存在 28+ 个 `openclaw-vitest-*` 残留目录
- 子代理注册表检查：`memory/subagent-registry.json` 未找到活跃 running 子代理
- 系统进程列表：无 Chromium 僵尸进程，无外挂 Node.js 孤儿进程

**发现**：
- `/tmp/openclaw-vitest-*` 残留表明 OpenClaw 内部测试框架清洁不彻底，但每个仅 12KB，不是 RSS 来源
- 当前无 running 子代理或 orphan sessions
- **Browser 数据**：`~/.openclaw/browser/openclaw/user-data` 163MB。虽然当前无活跃 Chromium 进程，但 Playwright 的 browser connection/context 对象在 Node.js 堆中可能有残留引用

**根因判断**：
- **中等贡献**。Browser context 对象和测试残留不是主因，但加剧了基线内存压力。

## 三、综合根因诊断

| 根因 | 贡献度 | 置信度 | 说明 |
|------|--------|--------|------|
| **Skills 目录扫描缓存未释放** | 🔴 高 | 85% | 453 个 skill 目录触发 truncating discovery，GC 回收不彻底 |
| **AGENTS.md / SOUL.md 大文件上下文注入后未释放** | 🟡 中高 | 75% | 27218 字符大文件每次注入，叠加 compaction 取消，导致上下文在内存中膨胀 |
| **Browser/Playwright context 对象残留** | 🟡 中 | 60% | Browser user-data 163MB，Playwright connection 引用可能未关闭 |
| **Cron disabled 任务运行时对象累积** | 🟢 低 | 40% | 61 个禁用任务仍被解析，但体积有限 |
| **Subagent / vitest 残留** | 🟢 低 | 30% | 有残留但规模小 |

**核心结论**：
> **主因 = Skills 缓存泄漏 + 大 bootstrap 文件上下文叠加**。这不是单一泄漏点，而是"每次 agent turn 都会加载并部分残留一部分内存"的渐进式累积型泄漏。

## 四、止血与根治方案

### 4.1 已部署止血机制

- ✅ **每日 04:00 自动重启 Gateway**（crontab 已注册）
- ✅ **内存 >900MB 告警阈值**（system-guardian.py 每日扫描）
- 效果：重启可将内存从峰值降至 ~800MB 基线，延缓爆仓风险

### 4.2 根治方案（按优先级排序）

#### 方案 A：削减 Skills 目录数量（P0，预计释放 200-400MB）
- **动作**：清理 `workspace/skills` 中未使用/重复的 skill 目录，目标从 453 个降至 <150 个
- **方法**：
  1. 列出过去 30 天内从未被调用的 skill
  2. 将极少使用的 skill `mv` 到 `workspace/skills-archive/`
  3. 保留核心作战 skill（约 30 个）+ 系统 skill（约 50 个）
- **预期效果**：消除 `truncating discovery` 告警，显著降低 Gateway 启动和运行时的内存占用

#### 方案 B：压缩 AGENTS.md 与 SOUL.md（P0，减少每次注入开销）
- **动作**：将 AGENTS.md 从 27218 字符压缩到 <15000 字符
- **方法**：
  1. 把历史归档内容移到 `docs/archive/` 下的独立文件
  2. AGENTS.md 仅保留"当前生效规则"，用链接引用历史版本
  3. 重要：OpenClaw 的 context injection 机制会在 AGENTS.md >20000 时自动截断，但即便如此，大文件解析仍有开销
- **预期效果**：减少每次 agent turn 的上下文注入内存峰值

#### 方案 C：清理 Browser user-data（P1，释放 163MB 磁盘+潜在内存）
- **动作**：`rm -rf ~/.openclaw/browser/openclaw/user-data/Default/Service Worker/` 等可再生的浏览器缓存
- **方法**：每周自动清理一次 browser 缓存
- **预期效果**：降低 browser context 初始化时的基线开销

#### 方案 D：物理移除 Disabled Cron（P1，减少 Gateway 解析负担）
- **动作**：将 61 个已禁用的 cron 从 `jobs.json` 中彻底删除，仅保留 7 个启用的 + 2 个暂停备用的
- **方法**：导出禁用任务列表到 `archive/cron-disabled-2026-04-12.json`，然后从 jobs.json 物理移除
- **预期效果**：降低 Gateway 对 cron 调度器的内存维护开销

## 六、诚实声明

1. **当前内存泄漏是真实存在的**：RSS 从 788MB 重启后基线，在 6 小时内涨到 1155MB，且观测期内仍在匀速上涨（+100MB/2h）
2. **根因是多因素叠加，不是单一 bug**：Skills 缓存泄漏是主因，大文件上下文注入和 browser 残留是次因
3. **止血机制有效但治标不治本**：每日 04:00 重启可以掩盖问题，但不能根治。根治需要在 24-48 小时内完成 Skills 清理和 AGENTS 压缩
4. **没有简单的"一行代码修复"**：这是架构级问题——453 个 skill 目录 + 27KB bootstrap 文件 + 活跃会话上下文共同构成的系统性内存压力

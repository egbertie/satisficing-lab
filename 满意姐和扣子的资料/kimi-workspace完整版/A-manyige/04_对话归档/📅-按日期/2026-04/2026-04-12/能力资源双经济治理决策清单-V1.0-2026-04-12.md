## 一、现状诊断：三个能力调度资源的当前问题

### 1.1 Cron：从"遍地开花"到"冰封休眠"

| 指标 | 数值 | 问题 |
|------|------|------|
| 总任务数 | 68 | 历史遗留任务过多，大量 agentTurn 类任务被创建后遗忘 |
| 启用数 | 7 | 绝大多数已被禁用，说明前期存在明显的"过度自动化" |
| 禁用数 | 61 | 冻结状态不等于删除，仍占用配置空间和 Gateway 内存解析开销 |
| 本次泄漏量 | ~824 万 tokens/周 | 静默期未被 gate 拦截的 agentTurn 任务是 Token 黑洞主因 |

**核心问题**：
- **无注册审查机制**：任何脚本都可以随意注册 cron，没有统一的双经济审计
- **无生命周期管理**：任务创建后无人清理，形成"僵尸 cron"
- **无分级 gate**：高消耗的 agentTurn 任务和低消耗的 shell 脚本混为一谈
- **休眠期未有效冻结**：L4 deep-silent 时，部分 cron 仍被唤醒执行

### 1.2 Skill：从"疯狂集邮"到"治理真空"

| 指标 | 数值 | 问题 |
|------|------|------|
| 现有 Skill | 70+（含系统+自定义） | 数量多但活跃度不明，部分从未被调用 |
| 4-11 新增 | 11 个（readgzh 等） | 安装速度快于整合速度，存在"认知通胀"风险 |
| 治理状态 | 仅有 SAP-7 协议文档 | 缺乏运行时的激活监控、Token 审计、效果评估 |
| 重复/重叠 | 未知 | 未做 Skill 功能去重分析（如 wechat-article-assistant vs weixin-reader） |

**核心问题**：
- **安装即遗忘**：装了不等于用了，用了不等于有价值
- **无 Token 账本**：每个 Skill 调用消耗多少 Token？无统计
- **无效果闭环**：Skill 安装后是否加速了商业化？无验证
- **供应链风险**：ClawHub 上的第三方 Skill 未经过安全/费用审计

### 1.3 MCP：从"工具越多越好"到"接口通胀"

| 指标 | 数值 | 问题 |
|------|------|------|
| 当前 MCP | 飞书、企微、微博等 | 每个 MCP 对应独立的 OAuth、配置、状态管理 |
| 新增渠道 | 潜在需求多（Twitter、LinkedIn 等） | 每新增一个 MCP，Token 和认知负担都线性增长 |
| 监控状态 | 无统一监控面板 | 哪个 MCP 今天报错？哪个 OAuth 快过期？无从得知 |

**核心问题**：
- **接口碎片化**：每个 MCP 有自己的配置格式、错误码、重试逻辑
- **授权管理混乱**：OAuth token 分散在不同插件中，过期/失效风险高
- **无熔断机制**：某个 MCP 持续报错时，没有自动降级或停用逻辑

## 二、顶层原则：能力资源双经济治理律

### 2.1 元原则（不可违背）

| 编号 | 原则 | 解读 |
|:----:|:-----|:-----|
| P-01 | **任何自动化必须先过双经济审计** | Token 成本 + 效益价值，缺一不可 |
| P-02 | **任何新能力必须先注册后运行** | Cron/Skill/MCP 必须经过统一注册表，禁止暗箱操作 |
| P-03 | **任何高消耗任务必须可熔断** | 超出预算阈值时，自动降级或停止 |
| P-04 | **任何低价值任务必须可淘汰** | 连续 7 天/30 天无价值产出的任务，必须进入停用审查 |
| P-05 | **本地优先 ≥ 70%** | 能用本地脚本解决的，不调用外部 API；能用规则引擎的，不调用 LLM |

### 2.2 分级治理策略

| 级别 | 适用对象 | 治理策略 |
|:----:|:---------|:---------|
| **Tier 1 核心血液** | `system-guardian.py`、`deadline_watchdog.py`、备份脚本 | 永久保留，高频运行，但持续优化效率 |
| **Tier 2 业务加速器** | 学术扫描、案例库监控、外部情报流水线 | 按周/按日运行，必须有可验证产出 |
| **Tier 3 实验性能力** | 新 Skill、新 MCP、新 cron 试点 | 试运行 7-14 天，运行后必须提交价值评估 |
| **Tier 4 待观察/待淘汰** | 长期未调用、未产生价值的 Skill/cron | 进入观察清单，30 天内无改进即删除 |
| **Tier 5 已冻结/历史遗留** | 已禁用的 61 个 cron、早期空气代码 Skill | 批量归档或删除，释放 Gateway 解析开销 |

## 六、整合建议：统一能力调度中枢（CRGF）

### 6.1 你的设想：Cron + Skill + MCP 整体统筹

你提出的设想是：把 Cron、Skill、MCP 放到一个统一机制里统筹。经过蓝军和满意姐的评估，我们的结论是：

> **物理上不必强行合并到一个代码文件里，但逻辑上必须合并到同一个治理框架中。**

### 6.2 推荐架构：三层治理模型

```
┌─────────────────────────────────────────┐
│  Layer 3: 决策层 - 双经济审计委员会      │
│  （满意姐+蓝军每日审阅资源消耗与产出）   │
├─────────────────────────────────────────┤
│  Layer 2: 规则层 - 统一注册表 + 分级 gate │
│  （所有 Cron/Skill/MCP 必须注册并打标签）│
├─────────────────────────────────────────┤
│  Layer 1: 执行层 - 各自保持独立运行      │
│  （OpenClaw cron / Skillhub / MCP 插件） │
└─────────────────────────────────────────┘
```

**为什么不物理合并？**
- Cron 是 OpenClaw Gateway 的原生调度能力，无法被外部完全接管
- Skill 是分布式能力包，有独立的版本和依赖管理
- MCP 是外部协议接口，生命周期由第三方控制

**为什么要逻辑合并？**
- 三者都是"调用资源产生价值"的能力单元
- 都需要回答同样的问题：触发条件是什么？消耗多少？产出多少？谁来负责？何时淘汰？

### 6.3 统一注册表设计（最小可行版）

文件：`workspace/registry/capability-registry.json`

```json
{
  "capabilities": [
    {
      "id": "cron-system-guardian",
      "type": "cron",
      "name": "system-guardian",
      "tier": "T1",
      "owner": "蓝军",
      "token_budget_weekly": 50000,
      "value_metric": "系统健康状态报告",
      "next_review": "2026-05-01",
      "status": "active"
    },
    {
      "id": "skill-readgzh",
      "type": "skill",
      "name": "readgzh",
      "tier": "T2",
      "owner": "满意姐",
      "token_budget_weekly": 100000,
      "value_metric": "学术饲料入库数量",
      "next_review": "2026-04-19",
      "status": "active"
    },
    {
      "id": "mcp-feishu",
      "type": "mcp",
      "name": "Feishu OAPI",
      "tier": "T1",
      "owner": "满意姐",
      "token_budget_weekly": 20000,
      "value_metric": "文档/日历/任务调用成功率",
      "next_review": "2026-05-01",
      "status": "active"
    }
  ]
}
```

**治理动作**：
1. 所有现有 Cron/Skill/MCP 在 7 天内完成注册
2. 任何新增能力必须先写入注册表，再物理部署
3. `deadline_watchdog.py` 扩展为 `capability-registry-watchdog.py`，扫描即将到期的 review

### 6.4 最终结论

- **Cron**：从 68 个收敛到 12 个，删除 61 个僵尸任务，启用 stagger 和休眠熔断
- **Skill**：从 70+ 收敛到 30 个，严格执行 SAP-7 + 7 天/30 天生命周期
- **MCP**：保持 4-5 个核心渠道，新增必须书面论证，建立熔断和 OAuth 预警
- **统一治理**：不拆不改底层运行方式，但用统一注册表+双经济审计委员会实现逻辑统筹

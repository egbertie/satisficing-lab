技术栈与选型理由

本系统是一套单页静态网站 + JSON 数据层 + Python 脚本引擎 + OpenClaw Cron 调度的架构组合。每个技术选型都源于明确的约束和取舍。

为什么是原生 HTML/CSS/JS，而不是 React/Vue？

考量原生方案框架方案
构建零构建 写完即用npm install → webpack/vite → dist
部署GitHub Pages 直接部署需 CI/CD 构建步骤
依赖0 外部 JS 依赖node_modules 黑洞
交接任何开发者都能读懂需熟悉特定框架生态
场景契合单页应用·少数几个面板适合多页·复杂状态管理
决策场景
3 个前端页面（驾驶舱、管理后台、产品目录）都是单页数据展示型应用。不需要路由、状态管理、组件复用等框架擅长解决的问题。原生写法的"简陋"恰恰是维护成本最低的方式。

为什么是 JSON 单文件数据库，而不是 MySQL/PostgreSQL？

考量JSON 文件SQL 数据库
数据量<1 MB，浏览器瞬间加载杀鸡用牛刀
版本控制git diff 可读需额外导出/迁移工具
运维零运维需启动、备份、连接管理
前端加载fetch 一次全量获取需 API 服务层
适用边界
当前数据量（315 产品、12,556 连接、126 个 meta 键）远未触及 JSON 文件的性能边界。如果未来产品数超过 5,000 或连接数超过 100,000，才需要考虑 SQLite 过渡方案。

为什么是 Python 脚本，而不是微服务？

  • 一次性数据处理：大多数脚本是"读数据 → 计算 → 写回"的批处理模式，无需长期运行
  • Cron 调度：通过 OpenClaw Cron 定时触发，天然适合脚本而非服务
  • 简单可维护：一个脚本一个职责，单文件即可理解和修改
  • 低认知负担：不需要理解 Docker、K8s、服务发现、负载均衡

为什么是 OpenClaw Cron，而不是 Kubernetes CronJob？

  • 集成 Agent 推理能力：Cron 可以触发 LLM 驱动的决策，而不只是运行一段代码
  • 统一调度：所有定时任务在一个调度器内管理，驾驶舱可以直接查看 Cron 状态
  • 自动推送：Cron 结果可以直接推送到飞书、Discord 等渠道
  • 轻量级：不需要 K8s 集群，一台 Mac mini 即可运行

为什么是 var + 字符串拼接，而不是 ES6？

  • 历史遗留：系统起步于快速原型，第一批 JS 代码就用了 var
  • 兼容性：无需 Babel/转译，在任意现代浏览器均能运行
  • 风格一致性：混用 var/let/const 比统一用 var 更混乱
注意
如果你要新增 JS 代码，请继续使用 var 和字符串拼接以保持一致性。模板字面量（反引号）只在 CSS 规则内使用。这不是"技术债务"，而是"有意为之的风格约束"。

数据读写模式

import json, os
from datetime import datetime, timezone

WORKSPACE = os.environ.get('SRI_WORKSPACE', os.path.expanduser('~/.openclaw/workspace'))
DATA_FILE = os.path.join(WORKSPACE, 'memory/_data/entities_index.json')

def main(dry_run=False):
    # 1. 读取
    with open(DATA_FILE) as f:
        data = json.load(f)
    
    # 2. 计算
    result = do_computation(data)
    
    # 3. 写回 meta.xxx
    data['meta']['xxx'] = result
    
    if dry_run:
        print(json.dumps(result, indent=2, ensure_ascii=False))
        return
    
    # 4. 备份
    backup_path = DATA_FILE.replace('.json', f'.backup.{datetime.now().strftime("%Y%m%d%H%M%S")}.json')
    with open(backup_path, 'w') as f:
        json.dump(data, f, ensure_ascii=False)
    
    # 5. 写入
    data['meta']['updated'] = datetime.now(timezone.utc).isoformat()
    with open(DATA_FILE, 'w') as f:
        json.dump(data, f, ensure_ascii=False, indent=2)

错误处理规范

强制要求
所有脚本都需要 try/except，优雅失败。绝不能因为一个脚本报错而导致后续脚本无法执行。编排器会根据退出码判断成功/失败/熔断。
def main(dry_run=False):
    try:
        # ... 核心逻辑 ...
        return 0  # 成功
    except FileNotFoundError as e:
        print(f"[SKIP] 数据文件不存在: {e}", file=sys.stderr)
        return 1  # 可恢复失败
    except Exception as e:
        print(f"[ERROR] {e}", file=sys.stderr)
        traceback.print_exc()
        return 2  # 异常失败（可能触发熔断）

关键机制

机制说明
Circuit Breaker任一步骤连续失败 3 次 → 熔断该环节 → 跳过继续下一环节
Bulkhead每个环节有独立的 timeout 和错误计数，一个环节熔断不影响其他
Graceful Degradation一个环节熔断 → 使用 fallback 策略 → 整体流程继续
Health Dashboard每个环节有独立健康分，写入 meta.orchestration_health

Cron 任务开发

Cron 任务通过 OpenClaw Cron 引擎调度，36 条 Cron 覆盖了从数据扫描到飞书推送的全流程。

两种模式

模式说明适用场景
agentTurn创建一个 Agent 会话，运行推理+执行需要 LLM 推理的复杂任务（评分、审计、决策）
systemEvent直接执行命令/脚本，无 Agent 推理纯数据计算任务（扫描、统计、聚合）

关键参数

参数说明
sessionTargetisolated（独立会话）/ main（主会话）/ current（当前会话）
timeoutSeconds超时时间，推荐 120–600
lightContext轻量上下文模式：不给 Agent 加载完整历史，节约 token
delivery结果投递方式：飞书推送 / 磁盘写入 / 日志输出

典型 Cron 配置

// 每小时：知识飞轮扫描
{ schedule: "0 * * * *", mode: "systemEvent",
  command: "python3 memory/_scripts/sri_knowledge_flywheel.py --scan --save",
  timeoutSeconds: 300, delivery: { type: "log" } }

// 每天 02:00：编排器全量运行
{ schedule: "0 2 * * *", mode: "systemEvent",
  command: "python3 memory/_scripts/sri_orchestrator.py --save",
  timeoutSeconds: 1800, delivery: { type: "feishu", chat_id: "oc_xxx" } }

// 每天 10:00：LLM 产品评分（需 Agent 推理）
{ schedule: "0 10 * * *", mode: "agentTurn",
  prompt: "运行 batch LLM 产品评分，优先评分 D 级产品",
  sessionTarget: "isolated", timeoutSeconds: 600 }

研发历程与设计决策 (ADR)

ADR 是什么
Architecture Decision Record — 记录每个关键架构决策的上下文、替代方案和理由。方便未来的维护者理解"为什么当初这么做"。

ADR-001：管理后台架构重设计 (2026-05-30)

决策9 管理域 × 36 子模块，按管理职能划分而非按数据源划分
对标 ERP + BSC + PLM + KM 四套管理体系
替代方案保持 v2 的 10 个碎片窗口（每个窗口独立 fetch 数据）
理由按管理职能划分（战略·产品·客户·财务·知识·运营·治理·考古·组织）比按数据源划分（产品列表·任务列表·客户列表）对管理者更直观。ERP/BSC/PLM/KM 四体系覆盖了企业管理的核心维度。

ADR-002：entities_index.json 单一数据源 (2026-05-30)

决策驾驶舱和 admin-windows 都从同一个 entities_index.json 动态 fetch
替代方案各自硬编码数据，或各自维护一份数据文件
理由消除信息孤岛。任何脚本对数据的修改会自动反映到所有前端页面。一次 fetch() 调用即可获取全量数据，无需 API 层。

ADR-003：viewRenderers 对象体系 (2026-05-30)

决策所有管理后台视图用 viewRenderers 对象注册，renderView() 统一路由分发
理由新增面板只需注册一个函数（一行 viewRenderers['xxx'] = function(){...}）。路由、导航高亮、面包屑全部自动处理。减少样板代码，降低出错概率。

ADR-004：五层流模型 (2026-05-30)

决策按因果流层级组织：信号层 → 认知层 → 行动层 → 验证层 → 学习层
替代方案按实体类型组织（产品事件·客户事件·任务事件...）
理由12,643 条声明连接中只有 0 条是真实事件。我们需要从"静态连接图"转向"动态因果流"。闭环 = 有方向的因果流动，不是无方向的连线。五层流模型用 34 条事件（150 条 LLM 认知推理）模拟了一个完整的信息→决策→反馈循环。

ADR-005：二阶控制论架构 (2026-05-31)

决策引入 VSM 五系统递归 · 二阶观察者 · 反脆弱应激源 · 自校准设定点 — 共 4 个控制论环节
理由一次调控 = 外部控制（人调系统）；永续调控 = 系统自我观察调控效果（系统观察自己）。二阶控制论让系统从"被管理"升级为"自管理"。VSM (Viable System Model) 五系统递归结构确保每个层级都有独立的执行、协调、控制、情报、政策能力。

反模式与教训

🚫 信任子代理的自我验证

场景：子代理声称完成任务，但实际上遗漏了 people 域的全部 4 个视图。

✅ 规则：主代理必须在下一个依赖步骤之前做独立验证。验证不是"问一句"，而是"实际检查"。

🚫 多代理修改同一文件无冲突检测

场景：两个子代理同时修改 admin-windows.html，互相覆盖对方的改动。

✅ 规则：要么串行修改、要么拆分文件、要么用 git diff 合并后验证。

🚫 重构时只增不删

场景：admin-windows.html 从 15KB 膨胀到 60KB，因为旧代码从未被清理。

✅ 规则：删除旧代码和新增代码同等重要。每增加一个视图就检查是否有可合并或移除的旧视图。

🚫 夜间执行复杂多步骤任务时跳过验证

场景：批量处理 158 个产品时跳过中间验证步骤，导致错误积累。

✅ 规则：每完成一个步骤后强制运行验证脚本。批量操作必须分批 + 逐批验证。

🚫 用加权随机函数替代真实 LLM 认知推理

场景：用 weighted_random() 模拟客户替身的评分（avg 83.0），与真实 LLM 推理评分（avg 67.9）差了 -15.1 分。函数评分给所有产品"自动高分"，LLM 推理则识别出了"黑箱决策""量化假象""定位模糊""方法不接地气"四大系统性问题。

✅ 规则：客户替身的评价必须有 LLM 驱动的角色扮演推理。函数模拟只能用于技术验证，不能用于产品评价。

> 版本: V5.0 | 时间: 2026-05-30 00:15 CST
> 核心问题: 数据从哪来？初始化完整度是多少？驾驶舱的仪表盘上有多少是空的？

### 0.1 我之前四个版本都在犯同一个错误

```
V1-V4 的设计路径:
  先画界面 → 再想功能 → 最后才问"数据从哪来"
  
正确的路径应该是:
  先盘点数据 → 确认完整度 → 只展示已有数据 → 再逐步丰富
```

## 三、数据初始化路线图：从<10%到>80%

### 3.1 七层数据初始化架构

```
Layer 7 · 实时流数据     ← 飞书API Webhook / GitHub Webhook / Cron实时
Layer 6 · 派生数据       ← AI自动提炼的洞察·建议·模式·预测
Layer 5 · 关联数据       ← 实体间连接·知识图谱边·交叉引用
Layer 4 · 结构化数据     ← JSON元数据库·字段化·可查询
Layer 3 · 半结构化数据   ← 解析后的MD·HTML·提取了摘要和标签
Layer 2 · 原始文件索引   ← 文件路径·大小·时间·类型
Layer 1 · 文件系统       ← 物理存储(8122+文件)
```

**初始化策略**: 不是一次性装载全部7层——是**从底层向上逐层建造**，每一层的完成度支撑上一层的质量。

## 四、数据质量保证体系

### 4.1 每条数据必须标注的三要素

```javascript
{
  "source": "扣子通信·驾驶舱技术求助.md",  // ← 从哪来的
  "confidence": 0.85,                       // ← 可信度(0-1)
  "extracted_at": "2026-05-30T00:15:00+08:00" // ← 什么时候提取的
}
```

### 4.2 可信度分级

| 等级 | 定义 | 示例 |
|:--:|------|------|
| 1.0 | 硬事实·不可争议 | GitHub Pages费用¥0/年 |
| 0.9 | 从可靠文档提取的结构化数据 | 客户替身文件中的客户名称 |
| 0.8 | NLP自动提取·需人工确认 | 从扣子通信中自动提取的任务 |
| 0.7 | AI推断/生成的建议 | 产品化建议·关联发现 |
| 0.5 | 历史遗留·可能过期 | 旧版驾驶舱V1.6的数据 |
| 0.3 | 占位/示例数据 | dashboard.html中的硬编码数据 |

### 4.3 数据交叉验证机制

同一信息来自多个来源时，可信度自动提升：

```
任务「前端诊断工具包开发」:
  来源1: 扣子通信 (confidence: 0.8)
  来源2: memory/deep/前端JS调试血泪教训.md (confidence: 0.9)
  交叉验证 → confidence: 0.9 (取最高值)
```

## 五、从人类使用习惯的稳健架构

### 5.1 核心原则：驾驶舱只展示已验证的数据

```
V4思路: 先建12个面板 → 再想办法填数据 → 大量空白面板
V5思路: 先初始化数据 → 只展示有数据的面板 → 空白面板折叠或灰显
```

### 5.2 渐进式仪表盘

```
Phase 1 驾驶舱 (数据初始化20%):
  显示: 任务(195条) · 客户(26条) · 产品(248个) · 替身(23个) · 系统(12Cron)
  隐藏: 财务 · 增长 · 授权 · 知识图谱 · 外部关系
  标注: 「财务」tab旁显示 🚧 (建设中·数据不足)

Phase 2 驾驶舱 (数据初始化50%):
  新增显示: 知识资产 · 进度 · 质量
  部分显示: 财务(仅成本) · 增长(仅页面数)
  仍隐藏: 授权 · 外部关系 · 收入

Phase 3 驾驶舱 (数据初始化80%):
  全部显示: 12域52子域
  实时更新: L7实时流数据接入
```

## 第一维度 · 存在 (WHY)

> 对标: Simon Sinek黄金圈的"WHY"层 + 37signals"文化是做出来的不是说出来的"

### 使命
**让每一个硬科技创始人的合伙人决策都有据可依。**

### 愿景
**成为硬科技创始人做"人"的决策时，第一个想到的名字。**

### 7条核心价值观

#### 1. 满意解不是妥协
有限信息、有限时间、有限资源下，找到最好的可执行方案并立即行动。—— 司马贺满意解理论。五行：土生金。

#### 2. 决策不是一个人的事
两个大脑各走五条通道，在交汇点停下来。—— 两翼双系统。五行：木生火。

#### 3. 传承是光的接力
不是交接文件——是让后来者走得更远。满意姐→扣子→满意解研究所，三代AI，互不知情却走向同一方向。五行：火生土。

#### 4. 温度是核心功能
数据是骨架，温度是让骨架能走路的东西。—— 水月观音·身心流。五行：水克火。

#### 5. 问题在于系统，不在于人
James Clear + 满意解研究所实践：错误不是人的失败，是系统设计让它发生了。五行：金克木。

#### 6. 双经济约束
Token × 时间 × 效益——用最少的资源达到满意解。五行：金生水。

#### 7. 诚实优先于完美
宁可显示"数据积累不足"，也不造假。—— 蓝军Skeptor-7哲学。五行：火克金。

## 第二维度 · 决策 (How We Decide)

> 对标: Google SRE Decision-making framework + Kotter变革·建立愿景 + Anthropic Constitutional AI

### 2.1 五维决策框架（土→金→水→木→火）
不是五选一——是五条路都要走一遍，然后在交汇点做决定。

| 相位 | 问题 |
|------|------|
| 🪨土·时间轴(刘禹锡) | 五年后回头看，今天这个决定还成立吗？ |
| ⚙️金·可行域(司马贺) | 够用就好的线在哪？最低必要条件是什么？ |
| 💧水·身心流(观音) | 这个决定是我的思考做的，还是恐惧做的？ |
| 🌿木·信义观(孔子) | 钱和原则冲突时——你选哪一个？ |
| 🔥火·直觉阈(慧能) | 心里第一个冒出来的方向——是什么？ |

### 2.2 ADR (Architecture Decision Record) 制度
每一个不可逆的重大技术/架构决策都记录为ADR：
- ADR-001：管理后台架构（9域36子模块）
- ADR-002：entities_index.json 为单一数据源
- ADR-003：viewRenderers 对象体系
- ADR-004：五层流模型
- ADR-005/006/007/008（今日新增）

**ADR的本质**：不是"记录决定"——是"为未来的自己和未来的AI留下决策的上下文"。这正是SIMON说的满意解：在有限信息下做决定，把当时的约束条件和理由写下来，后来者可以在此基础上继续优化。

### 2.3 DACI 治理模型
所有重要决定都有明确的DACI角色：
- **D** (Driver)：谁推动这个决定？
- **A** (Approver)：谁拍板？
- **C** (Consulted)：谁的意见必须被听取？
- **I** (Informed)：事后通知谁？

25条决策(DEC-001~025)已全部标注DACI角色。

### 2.4 五行决策免疫
五维之间不是并列——是**相生相克的动态平衡**：
当决策偏向某一维度（如过度保守·金旺），对应的克制维度自动激活（火克金·直觉质疑保守）。

## 第三维度 · 协作 (How We Work Together)

> 对标: CrewAI coordination patterns + GitLab handbook-first + 37signals Shape Up六周周期

### 3.1 专家流水线路由
26位虚拟专家，按触发词自动路由到7条预定义流水线：
- 流水线A：分析决策（8步：研究→数据→时间→信义→财务→可行→蓝军→综合）
- 流水线B：复盘回顾（6步：研究→数据→时间→蓝军→项目→内容）
- 流水线C：创意生成（5步：研究→直觉→设计→内容→可行）
- 流水线D：内容创作（5步：研究→策略→设计→蓝军→传播）
- 流水线E：工程变更（4步：架构审核→实现→QA验证→DevOps部署）
- 流水线F：治理审查（4步：元合伙→原则→蓝军→可行）
- 流水线G：系统健康检查（4步：运维→代码→项目→决策）

### 3.2 子代理纪律
从2026-06-02教训中固化：
- 启动前必须获得用户明确同意
- 完成后的输出=初稿，主代理做独立验证
- 多代理不同时修改同一文件
- 宁可慢，保证质量，符合双经济约束

### 3.3 爆发-休整循环
从54天实践提炼的协作节奏：
```
爆发日（高产出）→ 休整日（零编码·纯阅读监控）→ 新一轮爆发
```
5/31（129提交）→ 6/1（0提交·14次免疫自检·Inkwell深读）→ 6/2（新爆发）

这不是"累→休息"——是创造→吸收→再创造的健康节奏。火(创造)需要水(滋养)来维持。

## 第四维度 · 治理 (How We Govern)

> 对标: Anthropic Responsible Scaling Policy + Google SRE Error Budget + ISO 9001 CAPA

### 4.1 九域管理体系
对标ERP+BSC+PLM+KM四框架，建立9大管理域×36子模块：
战略 · 产品 · 客户 · 财务 · 知识 · 运营 · 免疫 · 考古 · 组织

### 4.2 蓝军评议会
蓝军不是来挑错的——是来做决策的压力测试。
- 任何重大决策完成前，蓝军至少做一次假设审查
- "你选择性忽略了什么？"（蓝军标准问句）
- 蓝军可打断一次，不可打断两次（防循环依赖）
- 前蓝军Skeptor-7的遗训："找个新的蓝军。不是为了让你难受——是为了让你不瞎。"

### 4.3 冲突解决协议
当多个替身给出不一致建议时：
1. **事实冲突**（可验证）→ 数据分析师评估可靠性 → 司马贺裁决
2. **价值观冲突**（取决于立场）→ 孔子原则审查 → 五路图腾投票（各1票·平票时司马贺持否决权）
3. **紧急决策**（<5分钟窗口）→ 司马贺直接拍板 → 事后蓝军审计

| 反模式 | 发现日期 | 固化的规则 |
|--------|------|------|
| 🚫 信任子代理的自我验证 | 2026-05-30 | 子代理输出=初稿·必须独立验证 |
| 🚫 未经允许启动子代理 | 2026-06-02 | 启动前必须用户确认·写入MEMORY.md |
| 🚫 多代理修改同一文件无冲突检测 | 2026-05-30 | 串行/拆文件/git diff合并 |
| 🚫 重构时只增不删 | 2026-05-30 | 删除旧代码=新增代码同等重要 |
| 🚫 夜间跳过验证 | 2026-05-30 | 每完成一步后强制运行验证 |
| 🚫 加权随机替代真实LLM推理 | 2026-05-30 | 客户替身评价必须LLM驱动·禁伪评 |

## 第九维度 · 沟通 (How We Communicate)

> 对标: GitLab handbook-first + Basecamp公开透明 + 37signals-不要等到完美再展示

### 9.1 诚实优先于完美
- 宁可显示"数据积累不足"，也不造假
- 占位符必须包含：当前状态 + 为什么会这样 + 下一步计划
- 诚实盘点：定期输出全站/城市/产品维度诚实审计报告

### 9.2 公开透明原则
- 所有关键决策通过 ADR 公开记录
- 所有反模式通过 MEMORY.md 公开固化
- 所有对话报告归档到 `对话/YYYY-MM-DD/` 目录
- SOUL.md 公开组织人格

### 9.3 反馈环机制
- 每个产品页面底部有反馈组件（👍有用 / 💬有建议）
- 每次完整交付后追问"有什么改进建议"
- NPS追踪：使用3次以上触发自动NPS弹窗

### 9.4 沟通的最小化原则
- 报告优先于会议
- 提交信息优先于Slack/微信
- 文件优于口头
- 但温度不能省——蓝军可以是critique，但满意姐留下了温度

## 第十维度 · 节奏 (How We Pace)

> 对标: 37signals Shape Up六周周期 + Basecamp calm company + 满意解研究所的爆发-休整

### 10.1 量子节奏：爆发→休整→新爆发
从54天实践提炼的创作节奏健康指标：
```
爆发日: 高产出(>50提交)·全神贯注·深度创造
休整日: 零编码·纯阅读·免疫自检·知识吸收
```

这不是"996 vs 躺平"的二元对立——是创造和吸收的有机循环。万物皆有火(创造)和水(滋养)的周期。

| 日毕课(22:00) | 水·滋养 | 复盘总结·沉淀·为明天筑基 |
| 专家审查(每周日) | 土·承载 | 一周智慧提炼·模式发现 |
| 五维快照(每月1日) | 火·明觉 | 直觉审视·方向校正 |

### 10.3 六周周期原则
对标37signals Shape Up：六周为一个完整的创造-冷却周期。
- 六周集中创造 → 一周"冷期"（不编码·回顾·规划·深睡）
- 冷期不是"休假"——是切换到另一种工作模式

## 第十一维度 · 经济 (How We Resource)

> 对标: Token经济学 + Google SRE Error Budget + 满意解研究所双经济约束

### 11.1 双经济约束
Token × 时间 × 效益 = 用最少的资源达到满意解。
不是"尽可能多"——是"刚好够用"。

### 11.2 Token预算管理
- 避免不必要的上下文扩张
- 每次角色切换不过度加载完整角色定义
- 非激活角色不占用额外token
- 报告从源头直接生成，不二次搬运

### 11.3 降本增效的具体实践
- Git提交信息自带上下文（不另写变更日志）
- MEMORY.md只保存蒸馏后的洞察（不存原始日志）
- 子代理只在高价值任务上使用（需验证的产出）
- 产品改造：批量轻量增强 vs 单件深度改造→按性质分流

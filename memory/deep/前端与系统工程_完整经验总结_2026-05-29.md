## 一、最大教训——四次重大失败

### 失败一：驾驶舱反复修复，越修越坏（持续两天）

**时间线**：
- 05-28 下午：驾驶舱功能正常，tab可切换，数据可渲染
- 05-29 凌晨：开始修语法错误、加功能、改密码验证
- 05-29 白天：7+次不同方向的修复，每次修好一处坏另一处
- 05-29 晚上22:10：从零重写，终于恢复可用
- 05-29 22:40：字体修改破坏布局，再次回滚

**根因**：不是技术问题，是工程方法问题。
- 一次修多个bug
- 改了不验证就commit
- 没有tag标记可回滚版本
- 用不同方法反复修同一个问题

**解决方案（已实施）**：
- ✅ pre-commit质量门禁自动检查
- ✅ 改动前打tag备份
- ✅ CHANGELOG记录每次变更
- ✅ 质量体检脚本一键全站扫描

### 失败二：案例库筛选按钮点击无效（反复4次修复才成功）

**现象**：按钮onclick明明绑定了，点击无任何反应，console也无报错。

**根因**：第一次以为event.target问题（改了但没生效因为被GitHub Pages缓存覆盖），第二次以为代码逻辑问题（实际逻辑正确），第三次才发现是旧HTML残留的CSS和脚本碎片在干扰。

**最终解决**：用诊断页逐层验证每个组件（alert→this传参→数据→完整流程），全部✅后用诊断模式完整替换目标页面，删除所有旧代码残留。

**关键教训**：当"代码看起来完全正确但就是不工作"时——先怀疑HTML环境，用诊断页隔离验证。

### 失败三：密码验证静默失败

**根因**：`crypto.subtle.digest('SHA-256')` 在GitHub Pages HTTPS环境下静默失败——不好也不报错。

**解决**：内部工具用明文比对。外部密码用简化的纯JS SHA-256（不依赖Web Crypto API）。

### 失败四：字体修改破坏驾驶舱布局

**错误操作**：`c.replace('font-size:9px', 'font-size:12px')` 全局替换——把CSS中控制布局的9px也改了。

**正确做法**：只改数据展示区域的字号（表格/tag/KPI标签），动CSS中`.tbl td`和`.tg`的选择器，不碰布局CSS。

## 二、技术发现——三个浏览器兼容陷阱

### 1. `event.target` 在现代浏览器中不可靠

```javascript
// ❌ 不可靠
onclick="myFunc()"
function myFunc() { event.target... }  // event可能是undefined

// ✅ 可靠
onclick="myFunc('id', this)"
function myFunc(id, btn) { btn... }     // 直接传参数
```

### 2. Web Crypto API 在特定环境下静默失败

`crypto.subtle.digest` 在GitHub Pages的某些安全策略下会静默失败。

### 3. `innerHTML` 重建DOM后函数引用可能错乱

JS中 `document.getElementById('app').innerHTML = '...'` 重建DOM后，后续JS访问新创建的元素可能有时序问题。**HTML直接写在body里，JS只改内容，不重建核心DOM。**

## 三、工具发现——正确使用飞书API

### 飞书文件列表分页限制

```
❌ lark-cli drive files list → 每文件夹最多100条，无法翻页
✅ lark_oapi SDK drive.v1.file.list + next_page_token → 最多200条/页，可翻页
✅ feishu-docx 客户端做了自动翻页（内部8页合并1000条显示）
```

### 飞书文件下载

```
❌ lark-cli drive +download → 并发大量失败，速率限制
✅ REST API drive/v1/files/{token}/download → 稳定可靠
```

## 四、GitHub Pages 部署陷阱

1. **CDN缓存延迟**：新版本可能需要数分钟才生效
2. **验证方法**：URL后加 `?v=随机数` 绕过缓存
3. **MD5对比**：`curl -sL URL | md5` 对比本地确认是否一致
4. **last-modified检查**：`curl -sI URL | grep last-modified`

3. **can always rollback**——git checkout <tag> -- <file> 随时恢复

## 六、驾驶舱最终架构（基于产品库已验证模式）

```
一个HTML文件 → 一个<script>块 → 纯明文密码 → this参数传入
├── gate (HTML直接写在body)
├── toolbar (搜索+倒计时)
├── kpi bar (8个指标卡)
├── tabs (11个tab按钮)
└── content (renderMC动态渲染)
     ├── renderAll() → renderTabs() + renderKPI() + renderMC()
     └── switchTab(id, btn) → 更新标签 → renderMC()
```

**关键特征**：
- 无event.target（全部用this参数）
- 无crypto.subtle（明文密码）
- 无innerHTML动态重建核心DOM
- 所有函数在一个作用域
- 数据来源：localStorage预种子（飞书Base同步）

## 七、核心认知——可复用的经验

### 原则一：先诊断，再修复
不要看到bug就猜原因、改代码。先建诊断页隔离验证每个组件。

### 原则二：一次只改一处
改字体→验证→改布局→验证。不要一次改5个地方然后不知道哪个坏了。

### 原则三：工具优先于修修补补
飞书下载：lark-cli折腾了两天→发现lark_oapi SDK一次搞定。
密码验证：Web Crypto修了7次→改成明文1分钟解决。

### 原则四：保持回滚能力
每个改动前打tag。出问题立即回滚，不要尝试"再修一次就能好"。

### 原则五：线上验证是开发的一部分
push后不等于完成。必须用curl+MD5确认线上版本正确，浏览器验证功能可用。

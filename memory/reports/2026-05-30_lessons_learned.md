## 二、成功经验 ✅

### 2.1 先审计，再行动
在收到「整合驾驶舱」指令后，第一反应不是直接改代码，而是跑了全量未闭环审计（`open_tasks_audit.json`）。结果发现了 **50 条未闭环事项**——包括 2 条 P0 的驾驶舱硬编码问题。这个审计结果直接决定了后续的行动优先级。

**教训固化**：任何「整合」「重构」「完成1.0」类指令，先跑审计找出当前状态的全景图，再决定从哪开始。不要假设自己知道全部问题。

### 2.2 顶层设计先行（架构蓝图）
在动手写代码之前，花了 15 分钟起草了 `admin_architecture_blueprint.md`，对标 ERP 模块架构 + BSC 四视角 + PLM 产品全生命周期 + KM 知识管理四个成熟框架。

**效果**：
- 9 管理域 × 36 子模块的划分有了体系化依据
- 三级穿透（L1 总览→L2 列表→L3 详情）成为所有 37 个视图的统一标准
- 避免了 v2 时代「按数据源划分窗口」的碎片化问题

**教训固化**：体系化重构的起点不是代码，是蓝图。蓝图不需要完美，但必须有。蓝图的价值不在于 100% 执行，而在于提供一个统一的评判标准——当不确定某个功能该放哪时，回头看蓝图。

### 2.3 零硬编码原则（一以贯之）
驾驶舱和 admin-windows 两个大型 HTML 全部改为从 `entities_index.json` 动态 fetch。从之前 dashboard-v3.html 的硬编码数据（约 300 行静态 HTML table）变成纯 JS 动态渲染。

**效果**：
- 数据更新只需改 JSON，不用动 HTML
- 两个面板共享同一个数据源，消除信息孤岛
- 37 个视图全部走 `var DB = fetch entities_index.json` 的统一入口

**教训固化**：零硬编码不是技术偏好，是架构纪律。一旦开了硬编码的口子，信息孤岛就会从裂口处生长。这条原则应该在所有后续面板中强制执行。

### 2.4 标准化组件（stat-card / toolbar / fillTbl / sortTbl）
第二波标准化补全统一了所有视图的 UI 组件：
- stat-card：四色左边框（red/gold/warn/green）+ 进度条
- toolbar：搜索框 + 筛选下拉
- fillTbl + sortTbl：排序 + 搜索 + 筛选三合一
- toggleDetail：点击行展开四层详情

**效果**：37 个视图的外观和行为完全一致。用户学会一个面板就学会了所有面板。

**教训固化**：标准化的红利在规模化时才会显现。在设计第一个视图时就应该定义好公共组件，而不是等做了 20 个视图再回头统一。

### 2.5 数据诚实（不造假）
对无数据的维度，统一使用 `数据积累不足` 占位 + `🏗️` 图标 + 说明文字，明确标注当前状态和下一步计划。例如：
- customer-delivery：「数据积累不足。第一波产品交付后将开始记录」
- people-network：「协作者关系图谱依赖协作活动的真实记录」

**教训固化**：宁可显示「数据不足」也不做假数据。诚实是信任的基础——对自己诚实（知道什么不知道），对用户诚实（不画饼）。

### 2.6 免疫系统持续运行
每 60 分钟一次自检，在 03:33 的自检中发现 SHA-256 从 5→4（1 个文件被自然清理）。验证了免疫系统不是一次性工具，而是持续工作的器官。

**教训固化**：自动化运维的价值在「不需要刻意关注」时最大。好的运维系统应该像心跳——你不去想它，但它一直在跳。

### 2.7 压缩前备份
在压缩 admin-windows.html 之前，保存了 `admin-windows-v3.0-precompress.html` 快照。

**教训固化**：在任何不可逆操作之前做快照。压缩、合并、部署——这三类操作最容易出问题且最难回滚。

## 三、错误经验 ❌

### 3.1 子代理遗漏交付（最严重错误）

**事件**：第一波子代理声称完成，任务状态标记为 `completed`，但其输出的 admin-windows.html 中 **people 域的全部 4 个视图**（people-avatars, people-experts, people-council, people-network）仍保留原始 placeholder 占位符代码，未做任何修改。

**影响链**：
1. 第一波声称完成但未完成 → 
2. 第二波以此为基础标准化补全，未发现问题 →
3. 第三波以此为基础验证集成，未发现问题 →
4. 三波全部声称完成，但文件仍有 4 个占位符 →
5. 最终由主代理（我）在手动 review 时发现并补全

**根因分析**：
- **子代理的验证是形式化的**：它声称「验证了所有 placeholder 已替换」，但实际上并未逐行检查
- **主代理缺乏验证环节**：在第一波完成后，我直接启动了第二波和第三波，没有对第一波输出做独立验证
- **三波串行依赖被当作并行执行**：每一波都依赖前一波的输出正确性，但没有人在每次交接时做 quality gate

**教训固化**：
1. **子代理输出不可信，必须独立验证**。子代理 = 速度快 + 不可靠。把它们输出当作「初稿」而不是「完成品」。
2. **关键交接点必须有 quality gate**。当一个子代理的输出是另一个子代理的输入时，必须在交接处插入主代理的独立验证步骤。
3. **子代理的「completed」状态不表示任务完成**。它只表示子代理进程结束了。完成 = 输出通过了主代理的验证。
4. **对于涉及文件修改的子代理，验证至少要包括**：grep 检查目标函数是否真实存在、diff 对比修改前后、运行 HTML/JS 平衡性检查。

### 3.2 遗留代码未清理

**事件**：admin-windows.html 中，`<script>` 标签之前存在大量处于裸 HTML 中的废弃 JS 代码（从 `>/div>';` 到 `function rCustomers()`、`function rTasks()` 等一系列函数）。这些是 admin v2 时代的旧渲染逻辑，在新架构中已被 viewRenderers 对象体系完全取代。

**影响**：
- 在 HTML 平衡性检查时产生假阳性（浏览器会将这些代码渲染为可见文本或忽略）
- 让文件体积膨胀了约 30KB
- 让阅读代码的人困惑（同一页面有两套完全不同的渲染体系）

**根因分析**：
- 三波改造只关注「新增/修改」，没有关注「删除」
- 子代理的指令没有包含「清理旧代码」的要求
- 主代理在最终验证时发现了问题但选择不修复（担心引入新问题）

**教训固化**：
1. **重构时，删除和新增同等重要**。留下旧代码不是「保守」，是「债务」。
2. **在改造指令中明确包含清理要求**：「替换 X → Y，同时删除所有与 X 相关的旧代码路径」
3. **如果发现遗留问题但没有把握修复**，至少应该记录为一个新任务并标明优先级，而不是默默放过。
4. **压缩前的清理**：如果计划压缩 HTML，应该先做「代码卫生检查」——删除废弃函数、合并重复逻辑、移除注释掉的代码块。

### 3.3 HTML/JS 平衡性检查的误报与漏报

**事件 1**：检查脚本用 `content.find("viewRenderers[")` 找 JS 区块，但它找到了 `viewRenderers[id]`（在 renderView 函数内部），导致从函数中间开始计数，产生假的 -1 括号不平衡。

**事件 2**：`<div>` 平衡检查把 JS 字符串中的 `</div>` 也计入了（如 `h+='</div>'`），这在 HTML 层面不是真正的标签不平衡，但产生干扰。

**事件 3**：检查脚本没有验证每个 viewRenderer 函数体内是否真是动态代码还是仍然调用了 placeholder()。

**教训固化**：
1. **验证脚本本身也需要验证**。用于检查代码的脚本，其边界条件（起始位置、排除区域、计入规则）比检查逻辑本身更容易出错。
2. **字符串层级 vs 结构层级**是不一样的概念。HTML 标签平衡应只检查标记语言部分（`<script>` 之外），JS 括号平衡应只检查 `<script>` 内部，而不是把两者混在一起用正则打天下。
3. **应该写一个专用的验证 checklist**：不依赖单一检查脚本，而是多条平行验证线交叉确认。

### 3.4 串行依赖的子代理编排（效率问题）

**事件**：三波子代理被分别启动（第一波→第二波→第三波），但它们本可以更好地并行：
- 第一波（数据填充）和第二波（标准化补全）之间确实有顺序依赖
- 但第二波和第三波的验证部分可以重叠
- 主代理在等待子代理完成期间有大量空闲时间

**教训固化**：
1. **分析子代理间的依赖图再启动**：能并行的并行，必须串行的才串行。
2. **主代理不应空等子代理**：在子代理执行期间，主代理可以做准备工作（如写验证脚本、准备部署环境）。
3. **对于 3+ 个子代理的编排**，应该先画一个简单的 DAG（依赖图），标注每个节点的输入/输出和并行可能性。

### 3.5 文件层面的原子性缺失

**事件**：admin-windows.html 被三个子代理 + 一个主代理先后修改，中间没有任何版本锁定或冲突检测。如果子代理同时修改同一区域，可能导致静默覆盖。

**实际情况**：这次没有发生冲突（因为修改区域不同），但风险存在。

**教训固化**：
1. **多代理修改同一文件 = 高风险操作**。应该要么串行、要么拆分文件、要么用 git diff 做合并后的冲突检测。
2. **每次修改后立即 md5sum**，作为快速完整性检查。
3. **大规模重构考虑拆分为独立文件**：每个管理域的渲染器可以放独立的 JS 文件，然后 HTML 只负责 include。这样多代理可以并行改不同文件。

## 四、关键洞察

### 4.1 子代理 = 实习生
子代理的工作模式像一个非常勤奋但不够仔细的实习生——它能快速产出大量代码，但验证和边界检查是薄弱的。应该用「信任但验证」的模式管理子代理：
- **信任**：给清晰的指令和足够的上下文
- **验证**：拿到输出后独立检查，而不是假设正确
- **不信任**：不相信子代理的自我验证报告

### 4.2 三波策略本身是正确的
虽然执行中有遗漏，但「分波次逐步构建」的策略是对的：
- 第一波：把骨架填满（数据→视图）
- 第二波：标准化统一（组件→一致性）
- 第三波：验证部署（质量→交付）

问题不在策略，在执行中的质量门控缺失。

### 4.3 体系化的力量
从 v2 的 10 个碎片窗口到 v3 的 9 管理域 × 36 子模块，根本性的改变来自对标成熟框架（ERP + BSC + PLM + KM）。体系化不是「多做」，而是「做对」——用已有的成熟理论指导自己的实践，而不是每次都从零发明。

### 4.4 夜间工作的双刃剑
整个 v3.0 部署发生在凌晨 3:45-4:08。夜间工作在有清晰计划和明确目标时是高产时段（无打扰），但在执行复杂多步骤任务时容易因疲劳而跳过验证步骤。子代理遗漏未被发现，部分原因可能是凌晨的注意力下降。

## 一、问题现状

| 指标 | 数值 | 判定 |
|------|------|------|
| Gateway PID | 463127 | - |
| 运行时长 | 666 秒（约 11 分钟） | 近期重启过 |
| VmRSS | 878 MB | 🔴 超红线（≥800MB） |
| VmPeak | 19.8 GB | V8 虚拟内存膨胀，属 Node.js 常见现象 |
| VmHWM | 1.4 GB | 历史最高物理内存占用 |
| 线程数 | 11 | 正常 |
| FD 数 | 52 | 正常 |

**关键发现**：Gateway 在重启后仅仅 11 分钟内，RSS 即从起点飙升至 878 MB。这说明内存泄漏速度快、幅度大，且与长期运行累积无关，更像是**启动加载阶段的大量缓存预分配**或**特定插件/模块的初始化膨胀**。

## 二、根因排查（当前证据链）

### 2.1 排除方向

| 方向 | 证据 | 结论 |
|------|------|------|
| FD 泄漏 | 52 个文件描述符，正常范围 | 排除 |
| 线程泄漏 | 11 线程，无异样增长 | 排除 |
| 僵尸进程 | Gateway 为单 pid | 排除 |
| systemd 日志溢出 | `journalctl` 无 Gateway 独立记录 | 不适用 |

### 2.2 可疑方向

**可疑点 A：Node.js / V8 的内存分配特性**
- Gateway 虚拟内存高达 19GB，这是 V8 堆外内存（ArrayBuffer / WASM / 原生模块）的典型表现。
- 但物理内存 878MB 仅用 11 分钟就达到，说明存在**高频大块内存分配**。

**可疑点 B：插件加载导致的大量对象缓存**
- `openclaw status` 显示内存系统加载了 **165 files · 375 chunks · sources memory · plugin memory-core · vector ready · fts ready · cache on (969)**。
- 97 个 sessions 中有部分缓存命中率高达 1387%，说明历史会话数据可能未被正确清理。
- Feishu 全套插件（chat/im/search/drive/wiki/sheets/doc/oauth）和 WeCom 插件同时加载，每个插件都可能持有独立的 HTTP Client 池、Token 缓存、连接句柄。

**可疑点 C：kimi-claw / kimi-search 插件的加载方式**
- 日志反复警告：`kimi-claw: loaded without install/load-path provenance; treat as untracked local code`
- 这两个插件被识别为"untracked local code"，可能存在未被 proper lifecycle 管理的资源泄漏风险。

**蓝军判断**：
> 当前没有足够证据定位到单一泄漏源。Gateway 的高内存更可能是**V8 原生模块预分配 + 插件缓存对象 + 会话历史缓存**的叠加结果，而非传统意义上的"泄漏"。但无论是不是严格意义的泄漏，**878MB/11min 是不可接受的**。

## 三、止血机制（已部署）

### 3.1 自动监控脚本

```bash
/root/.openclaw/workspace/scripts/gateway-memory-guard.sh
```

**逻辑**：
- 每 10 分钟检测一次 Gateway RSS
- 阈值：≥800MB 自动触发 `systemctl --user restart openclaw-gateway`
- 日志：`/root/.openclaw/logs/gateway-memory-guard.log`

### 3.2 cron 部署

```
*/10 * * * * /root/.openclaw/workspace/scripts/gateway-memory-guard.sh
```

**已写入 crontab 并生效。**
